# 区块链基础知识

> **最后更新**：2026年10月19日

## 本文涵盖的内容

- 为什么有些账本会复制验证过程，以及全节点、轻客户端和许可型模型有何不同
- 共识、Merkle 树、P2P 和最终性的作用，以及它们分别给基础设施运维带来的限制
- 为什么区块链节点必须区别于普通有状态服务来管理

## 问题陈述：在没有可信仲裁者的情况下达成一致

理解区块链的起点不是技术，而是**约束条件**。

以普通的分布式系统为例，比如 Kubernetes etcd 集群。etcd 也会让各节点达成共识，但前提是：**参与节点由同一个组织运行，节点可能发生故障，但不会说谎**。它能处理节点宕机和网络分区（崩溃故障），但不能处理节点故意提出不同的值。

区块链的前提则不同。

| 项目 | etcd (Raft) | 区块链 |
|---|---|---|
| **参与方** | 同一组织，成员已知 | 彼此未知的各方，成员不断变化 |
| **假定的故障** | 崩溃故障（宕机、分区） | **拜占庭故障**（说谎、串通、攻击） |
| **参与资格** | 由运营方指定 | 公有链上是**任何人** |
| **能否回滚** | 运营方可以介入 | 只能按协议允许的方式进行 |

许多公有链的**全节点**会独立验证交易和共识规则。轻客户端、经过修剪或通过快照同步的节点，以及许可型设计，采用不同的验证和数据分发模型。许可型成员资格本身并不意味着共识算法具备拜占庭容错能力。

由此可知区块链的一项根本属性。

> **区块链不是为吞吐量而设计的系统**。它会**刻意接受冗余**，以换取可验证性和防篡改能力。

理解这一点，下面的各种运维特性就都顺理成章了。

## 区块与链：为什么叫“链”

一组交易构成一个**区块**，每个区块都包含**紧邻其前一个区块的哈希值**。

```text
Block N-1               Block N                 Block N+1
┌──────────────┐       ┌──────────────┐        ┌──────────────┐
│ prev_hash:.. │       │ prev_hash: ──┼────────│ prev_hash: ──┤
│ merkle_root  │   ┌───│ merkle_root  │        │ merkle_root  │
│ transactions │───┘   │ transactions │        │ transactions │
└──────────────┘       └──────────────┘        └──────────────┘
      hash ────────────────┘
```

由此带来的特性是**篡改会沿链传播**。修改区块 N 中的一笔交易 → 区块 N 的哈希值改变 → 区块 N+1 的 `prev_hash` 不再匹配 → 后续所有区块都无效。

对于 PoW 链，要改写历史就必须重新构建足够多的、已被接受的工作量；其他链则采用不同的最终性和治理假设。哈希链接可以让篡改行为被检测出来，但仅凭哈希链接并不能确立最终性，也不能让每条区块链都在经济意义上不可篡改。

### Merkle 树：为什么需要它

问题在于如何概括一个区块中的交易。你可以简单地把所有交易串联起来再计算哈希，但这样一来，**要检查“这笔交易是否属于这个区块”，就必须获取整个区块。**

Merkle 树是一种二叉树，它逐对向上计算交易的哈希值。

```text
                merkle_root
               /            \
         H(AB)                H(CD)
        /     \              /     \
     H(A)    H(B)         H(C)    H(D)
      |        |            |        |
     tx A     tx B         tx C     tx D
```

由此产生的特性是**Merkle 证明**。要证明交易 C 属于这个区块，只需要 **`H(D)` 和 `H(AB)`**，而不需要整个区块。接收方计算 `H(C)` → `H(CD)` → `merkle_root`，然后进行比较。

证明大小随交易数量 N 按 **log N** 增长。即使一个区块包含一百万笔交易，证明也只需要大约 20 个哈希值。

**实际意义**：正是这种机制让轻客户端成为可能。你可以在不持有整条链的情况下，验证某笔特定交易是否包含在链中。将区块链集成到现有系统时，“运行全节点，还是轻量验证就足够？”这一选择就以此为基础。

## 共识：谁来写入下一个区块

共识算法要决定两件事：**谁提出区块**，以及**发生冲突时哪一方是规范链**。

### 主要方法

| 方法 | 提议者的选择 | 实际成本 | 示例 |
|---|---|---|---|
| **PoW**（工作量证明） | 第一个解出计算难题的节点 | **电力和硬件** | Bitcoin |
| **PoS**（权益证明） | 按质押权益的比例随机选择 | **质押资本 + 违规时的罚没** | Ethereum |
| **BFT 系列** | 在明确的拜占庭故障阈值下投票 | 成员资格/验证者和法定人数假设 | Tendermint；Fabric 3.x SmartBFT |
| **CFT 许可型排序** | 已知副本使用崩溃故障容错共识 | 无法容忍任意的拜占庭排序行为 | Fabric Raft |

### 为什么需要付出成本

这个问题是理解共识的关键。**如果提出区块不需要付出成本，就可以无限创建候选区块，让网络陷入瘫痪**。在允许匿名参与的环境中，单凭身份无法阻止这种情况（女巫攻击：一方创建大量身份）。

PoW 将成本设为**计算**；PoS 将成本设为**资本加上罚没风险**。BFT 系列则**首先限制参与者**，从而绕开这个问题，这也是它适用于联盟链的原因。

### 公有链与私有链的分野

| 类型 | 参与方式 | 共识 | 吞吐量 | 主要用途 |
|---|---|---|---|---|
| **公有链**（无需许可） | 任何人 | PoW/PoS | 低 | 公共资产、互操作性 |
| **私有链/联盟链**（许可型） | 经批准的成员 | BFT/Raft | 相对较高 | 企业间账本、受监管环境 |

许可型设计可以采用已知成员和明确治理，并根据实际威胁模型选择 CFT 或 BFT。金融应用可以使用具有不同控制措施的许可型或公有网络；无论成员资格还是共识类型的名称，都不能证明其符合监管要求。

## 最终性：运维中最重要的概念

**最终性描述的是在协议安全假设下的结算状态**。它并非对所有攻击、治理干预或应用层补偿交易的无条件保证。要区分概率置信度、经济最终性和确定性共识保证。

### 概率最终性与绝对最终性

| 类型 | 含义 | 示例 |
|---|---|---|
| **概率型** | 区块堆叠得越多，回滚概率就按指数衰减。**但永远不会恰好为零** | Bitcoin 的 PoW |
| **经济型** | 已最终确认的检查点受到质押/罚没假设的保护；回滚并非物理上不可能 | Ethereum PoS |
| **即时型** | 在共识轮次结束时完成结算 | BFT 系列 |

### 为什么这是一个运维问题

**节点返回的数据可能尚未最终确认。**

向区块链节点询问“告诉我这笔交易的结果”，节点会**根据它所知道的最新链来回答**。如果最新区块之后发生重组（reorg），答案就会改变。

由此产生的实际事故模式如下：

| 模式 | 结果 |
|---|---|
| 根据最新区块确认存款并采取行动 | 提款已经发出后，重组抹去了这笔存款 |
| 健康检查只确认“节点仍在运行” | 同步落后的节点会**返回过时数据** |
| 负载均衡器将请求分发到多个节点 | 各节点的链高度不同 → **对同一个问题给出不同答案** |

**因此，应用设计必须包含“经过 N 次确认后再处理”的规则（确认深度），而这个值取决于链的最终性特征**。这不能只靠基础设施解决，而是需要与应用约定。

基础设施可以做的事：

- **在健康检查中纳入同步状态**：将就绪定义为“与链头相差不超过 N 个区块”，而不是“节点正在运行”
- **监控各节点之间的链高度差异**：差异增大时，将节点移出负载均衡
- **将发生重组的情况作为指标公开**，以便应用作出响应

## P2P 网络：为什么它不同于普通服务

区块链节点通过**点对点而非客户端-服务器模式进行通信**。这与 Kubernetes 的网络模型存在摩擦。

### Gossip 协议

出现新区块或新交易时，它会**传播给相邻节点**，这些节点再将其传播给各自的相邻节点。所有节点就是这样逐渐获知相关信息的。

特点：

- 没有中央代理 → 没有单点故障
- **同一份数据通过多条路径冗余到达** → 带宽被重复数据占用
- 传播需要时间 → 各节点对“最新状态”的认知不同（这会再次引出上文的最终性问题）

### 在 Kubernetes 环境中的摩擦

| 区块链 P2P 所需条件 | Kubernetes 默认情况 |
|---|---|
| **稳定的对等节点身份**（节点 ID、地址） | Pod 重启后 IP 会变化 |
| **接受入站连接**（其他节点连接到我） | 默认情况下，Pod 无法从外部直接访问 |
| **持久保存对等节点列表** | Pod 被替换后状态会丢失 |
| **公布固定端口** | Service 端口映射 |

因此，区块链节点通常默认使用 **StatefulSet + 无头 Service**，因为它们需要稳定的名称和顺序。接受入站 P2P 连接还需要额外设计暴露方式。[在 EKS 上运行区块链节点](./02-nodes-on-eks.md)介绍了具体做法。

## 状态与存储：为什么重建很困难

区块链节点会保存两类数据。

| 数据 | 特性 | 大小 |
|---|---|---|
| **区块历史** | 只追加日志。历史记录不可变 | 持续增长 |
| **当前状态** | 余额、合约存储。可通过重放区块推导得出 | 持续增长，但小于历史数据 |

**关键特性：状态可以从历史记录重放出来，但重放需要很长时间。**

从创世区块开始重放并验证每个区块（全量同步）所需的时间与链的历史长度成正比。因此才会出现其他同步方法。

| 方法 | 操作 | 权衡 |
|---|---|---|
| **全量同步** | 从创世区块开始验证并重放所有数据 | 置信度最高，**速度最慢** |
| **快照/快速同步** | 获取状态，并使用已接受的状态根进行证明检查；历史记录检查取决于客户端/模式 | 速度更快，但明确依赖共识/检查点和实现方面的信任假设；并非盲目信任任意对等节点 |
| **检查点同步** | 从可信检查点开始 | 速度最快，但需要信任检查点的来源 |
| **快照恢复** | 恢复由运营方保存的数据目录 | 速度快，但需要管理快照的新鲜度和一致性 |

**运维结论**：替换 Pod 时不能丢失状态。丢失状态意味着需要长时间同步，在此期间该节点无法提供服务。这就是为什么区块链节点的持久卷**不是可选项，而是必需项**。

### 2026年10月更新：AWS 上的区块链快照

根据 [2026年10月14日的公告](https://aws.amazon.com/about-aws/whats-new/2026/10/blockchain-snapshots-node-bootstrapping/)，AWS 推出了 **AWS 区块链快照**，用于发布已预先同步的公有区块链节点链数据。快照涵盖 Ethereum 和 Solana，可免费使用，并与上游提供方保持相同的刷新频率。这为缩短引导时间提供了一种选择——可用于扩充 RPC 集群容量、恢复故障节点或重新同步损坏的数据库——它会以针对并行提取优化的格式重新发布各网络的快照。该服务在美国东部（弗吉尼亚北部）、欧洲（爱尔兰）和亚太地区（东京）提供；访问需要在同一 Region 中使用带有 S3 网关 VPC 端点的 EC2 实例。这属于上表中的“快照恢复”，因此同样需要考虑快照来源和新鲜度方面的信任假设。

### 归档节点：需要单独考虑

能够查询“任意过去时点的状态”的节点就是归档节点。它会保留所有中间状态，因此比普通节点需要**多得多的存储空间**。

**这里需要做出设计判断**：首先确认你是否真的需要归档能力。大多数应用只需要近期状态；如果需要历史查询，用索引服务或数据仓库处理会更划算。

## 密钥管理：密钥一旦丢失，一切就结束了

在区块链中，**身份和权限就是私钥**。这与现有系统有着决定性的不同。

| 现有系统 | 区块链 |
|---|---|
| 忘记密码后可以重置 | **密钥一旦丢失，资产/权限就会永久消失** |
| 管理员可以冻结遭到入侵的账户 | 没有任何一方能够撤销操作（除非协议允许） |
| 审计日志可以用于事后追踪 | 交易一旦签名并最终确认，就无法撤销 |

**因此，备份策略的性质也有所不同**。链数据可以从网络重新获取，因此备份它的价值较低。相反，密钥**必须备份**，而且**备份本身也有暴露风险**。

这就是 HSM 和 AWS KMS/CloudHSM 在区块链基础设施中如此重要的原因。验证者尤其面临相互矛盾的要求：**密钥必须在线才能签名，但又绝不能泄露。**[金融服务视角](./04-financial-services.md)探讨了这一问题。

## 运维特性：由此得出的结论

汇总这些概念所带来的运维特性：

| 区块链设计 | 相应的运维特性 | 对 Kubernetes 的影响 |
|---|---|---|
| 复制全节点验证 | 增加副本本身不会提升底层链的写入能力 | 可以提高整体 RPC/读取能力和可用性 |
| 状态在本地累积 | **替换 Pod 的代价很高** | 必须使用 StatefulSet + 持久卷，并考虑节点亲和性 |
| 链同步存在延迟 | **“正在运行”和“能够提供服务”并不相同** | 在就绪检查中纳入同步状态 |
| 最终性不是即时的 | **最新数据不等于最终数据** | 将确认深度作为应用约定 |
| P2P Gossip | **需要入站连接和稳定身份** | 无头 Service，另行设计暴露方式 |
| 硬分叉会在指定时点启用新规则 | 在启用前升级到兼容的二进制文件 | 可以通过金丝雀和滚动升级提前做好集群准备 |
| 密钥即权限 | **密钥丢失 = 永久损失** | 使用 KMS/HSM，分别制定密钥和数据的备份策略 |
| 冗余验证是设计目的 | **持续消耗 CPU 和 IOPS** | 不适合面向突发负载的资源配置 |

**本节的核心就是这张表**。文档 2 中的每条具体建议都由此推导而来。

## 硬分叉：与 Kubernetes 运维模式的最大冲突

不向后兼容的协议更改称为**硬分叉**。整个网络会在指定区块高度或时间切换到新规则，而**未切换的节点会留在另一条链上**。

与 Kubernetes 常见做法的冲突之处：

| Kubernetes 惯例 | 硬分叉时的情况 |
|---|---|
| 通过滚动更新逐步切换 | 在启用前可行，但前提是所有必需节点都能在截止时间前支持新规则 |
| 先对一部分节点进行金丝雀发布 | 在启用前测试兼容分叉的二进制文件，并在适当的测试网/主网阶段比较其行为 |
| 出现问题时回滚 | 回滚会使该节点留在旧链上 |
| 按运维团队的计划安排升级 | **时间表由外部设定** |

**实际建议**：不要把硬分叉当作一次部署，而要把它视为**有截止期限的迁移**。订阅客户端发布说明，在分叉日期前尽早升级，并先在测试网上验证。

Ethereum 于 2025 年推出了 Pectra 和 Fusaka，并且一直在推进更频繁的升级。规划维护时，**应以已公布的启用日期和客户端发布说明为准，而不要假定每年一定升级两次**。

## 总结

- 比较所选共识机制和信任模型：**etcd/Raft 可容忍崩溃故障**；有些区块链使用 BFT，许可型 Fabric 可以使用 CFT Raft 或 SmartBFT。仅凭“区块链”这一名称不能推断其具备拜占庭容错能力。
- 许多全节点设计会复制验证过程；轻客户端和许可型模型则有所不同，而 RPC/读取能力可以与底层链的写入能力分别扩展。
- `prev_hash` 链会传播篡改，**Merkle 树**支持大小为 log N 的包含性证明（这是轻客户端的基础）。
- 共识需要付出成本，是因为需要**防范女巫攻击**。限制参与者（联盟链）就不再需要这种成本，因此能够以牺牲去中心化为代价，采用吞吐量和最终性更好的 BFT。
- **最终性是运维中最重要的概念**。最新数据不等于最终数据，因此要在就绪检查中纳入同步状态，并将确认深度作为应用约定。
- 状态可以重放，但**重放需要很长时间**，因此持久卷是必需项。
- 硬分叉有外部协调的启用时点；要提前准备兼容的客户端，并单独评估启用后的回滚方案。

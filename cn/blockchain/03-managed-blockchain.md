# Amazon Managed Blockchain

> **最后更新**：2026 年 10 月 12 日

## 本文涵盖内容

- Amazon Managed Blockchain（AMB）可以接管[自运维](./02-nodes-on-eks.md)中的哪些工作，又有哪些事情无法替你完成
- 选择托管服务还是自运维的标准，以及评估时必须纳入的一项变量
- AWS 在账本和区块链产品组合上的变化对架构决策意味着什么

## AMB 由哪些部分组成

AMB 并非单一服务，而是由特性各异的多个组件组成。

| 产品 | 提供的功能 | 成本 / 运维边界 |
|---|---|---|
| **Hyperledger Fabric** | 许可网络 / 成员 / peer 资源 | 按组件 / 节点 / 存储和网络计费；客户仍负责应用、channel 和身份管理 |
| **专用 Ethereum 节点** | 为受支持网络提供托管节点访问 | 适用时收取节点 / 存储 / 网络费用 |
| **无服务器 AMB Access** | 无需预置专用节点即可访问受支持的公有链 RPC | 按请求计费；请核实当前支持的链、方法和区域 |
| **AMB Query** | 索引后的区块链数据 API | 按 API / 请求计费，查询覆盖范围有限；不能替代任意全节点 RPC |

这些产品的预置、API、计费和责任模型各不相同。应先选择所需的网络和访问方法；不要把 AMB 当作普遍适用于所有情况、都按节点计费的单一服务。

::: warning 需要核实
AMB 的**支持框架和区块链、区域可用性以及预览 / 正式发布状态会因组件不同而随时间变化**。已确认的变化包括：Ethereum Goerli 测试网于 2024 年 4 月 1 日结束支持，Polygon Mumbai 测试网于 2024 年 4 月 15 日结束支持；Polygon PoS 主网曾一度以**公开预览**形式提供。

**定稿前，请直接查看 [AMB 官方文档](https://docs.aws.amazon.com/managed-blockchain/)和区域可用性。本文不声称任何特定链目前的支持状态**。
:::

## AMB 接管的工作

与[自运维文档](./02-nodes-on-eks.md)中介绍的工作量对比，可以看清职责边界。

| 自运维时的工作 | 使用 AMB |
|---|---|
| StatefulSet、卷和 StorageClass 设计 | **由 AMB 处理** |
| 监控磁盘增长和扩展卷 | **由 AMB 处理** |
| 初始同步和快照管理 | **由 AMB 处理** |
| P2P 暴露和通告地址配置 | **由 AMB 处理** |
| 客户端版本升级 | **由 AMB 处理** |
| 硬分叉响应 | **由 AMB 处理**（托管节点） |
| Fabric 证书签发基础设施 | **大部分由 AMB 处理**（托管 CA） |
| 节点可用性和监控基础 | **由 AMB 处理** |

托管提供商负责维护所选产品承诺管理的节点 / 服务。请验证受支持的网络、升级通知、API 行为和你仍需承担的应用责任；协议自身的升级节奏并不等同于 AWS 的服务保证。

## AMB 无法处理的工作

这是决策的关键。

| 项目 | 限制 |
|---|---|
| **客户端选择** | 只能使用 AMB 提供的客户端和版本。无法直接控制[客户端多样性](./02-nodes-on-eks.md)策略 |
| **细粒度调优** | 无法调整缓存大小、裁剪模式或内核参数 |
| **支持的区块链** | 仅限 AMB 支持的区块链；新的或规模较小的区块链通常不受支持 |
| **归档模式** | 支持范围可能有限 |
| **验证节点运行** | 托管节点通常用于**查询和提交交易**。质押验证节点是另一类需求 |
| **区域和网络配置** | 仅限 AMB 支持的区域和连接选项 |
| **成本结构** | 取决于产品：预置节点 / 组件费用，或无服务器请求 / API 费用；应测量相同覆盖范围和用量下的成本 |

**验证节点运行是一个特别重要的区别**。AMB Access 公有链节点用于读取链上数据和提交交易；**作为 PoS 验证节点参与验证并赚取质押奖励需要另一套能力**（密钥管理、签名可用性和罚没风险）。如果目标是质押，AMB 无法满足这项需求。

## 选择标准

| 情况 | 建议 |
|---|---|
| **只读**链上数据 | **AMB Query**（完全不需要节点） |
| 查询并提交交易，运维人员有限 | **AMB Access 托管节点** |
| 需要特定客户端或调优能力 | **自运维** |
| **验证节点 / 质押** | **自运维**（或使用专门的质押服务） |
| AMB 不支持的区块链 | **自运维** |
| 联盟 Fabric，需快速启动 | **AMB Access Fabric** |
| 需要细粒度控制 Fabric | **使用 Operator 自运维** |
| 流量很高，目标是优化成本 | **自运维**（需比较） |

### 决策顺序

**第 1 步：你真的需要节点吗**？如果只需查询数据，AMB Query 或第三方 RPC 提供商可能就够了。运行节点成本高且运维繁重，因此**先确认是否确实需要节点**。

**第 2 步：你需要控制权吗**？如果需要选择客户端、调优、归档或参与验证节点中的任何一项，就应自运维。

**第 3 步：成本如何**？根据所选产品为专用资源、无服务器请求或 Query API（如适用）估算费用。在覆盖范围和可用性相同的前提下，比较 EC2 / EKS、存储、传输、冗余和人员成本。不能仅根据节点数量得出一个经过测量且普遍适用的成本临界点。

**第 4 步：能否混合使用**？通常可以，实践中也往往合理；例如，普通查询使用托管服务，特殊用途使用自运维节点。

## AWS 账本和区块链产品组合的变化：必须考虑的变量

这是本文最重要的部分。**只做技术对比会忽略一种风险。**

### Amazon QLDB 终止服务

Amazon QLDB（Quantum Ledger Database）是一种托管账本数据库，提供**可进行加密验证且不可变的交易日志**。它于 2018 年 re:Invent 公布，并于 2019 年正式发布。

| 日期 | 事件 |
|---|---|
| 2018 | 在 re:Invent 公布 |
| 2019 | 正式发布 |
| 2024 年 7 月 | 宣布结束支持 |
| **2025 年 7 月 31 日** | **服务终止** |

AWS 提供的迁移路径是**Amazon Aurora PostgreSQL**。但需要注意：**迁移到 Aurora PostgreSQL 会失去 QLDB 的核心价值——加密可验证性**。可以通过扩展实现类似账本的功能，但无法替代“以数学方式证明数据从未被篡改”这一特性。

### 这意味着什么

QLDB 和 AMB 是不同的服务，**QLDB 结束支持本身并不意味着 AMB 也会结束支持**；AMB 自身的结束支持是在另外的公告中宣布的（见下文）。不过，QLDB 的案例仍然给架构决策带来了值得借鉴的教训。

| 教训 | 实际应用 |
|---|---|
| **托管服务也可能停止提供** | 尤其是采用率较低或用途特殊的服务 |
| **迁移路径的功能可能不等价** | “存在替代品”并不等于“替代品提供相同功能” |
| **通知期可能较短** | 提前计算自己的迁移所需时间 |
| **基于标准技术的方案更容易迁移** | 建立在开源协议之上，便可迁移到自运维方案 |

::: warning 已宣布结束支持
**AWS 已宣布 Amazon Managed Blockchain（AMB）将结束支持**。自 **2026 年 10 月 29 日**起不再接受新客户。现有客户可使用至 **2027 年 9 月 29 日**；此后访问将终止。

对于 AMB Access Ethereum / Bitcoin / Polygon，[AMB 迁移指南](https://docs.aws.amazon.com/managed-blockchain/latest/ethereum-dev/migrating-node-rpc-workloads.html)建议使用 AWS 上的自管理节点（在有对应蓝图的情况下使用 AWS Blockchain Node Runners），或改用第三方 RPC 提供商。[AMB 结束支持页面](https://docs.aws.amazon.com/managed-blockchain/latest/hyperledger-fabric-dev/managed-blockchain-end-of-support.html)列出的 AMB Access Hyperledger Fabric 迁移选项包括其他托管 Fabric 网络、在 Amazon EC2 或 Amazon EKS 上自运维 Fabric，或使用 AWS 数据库；AMB Query 则可迁移至托管区块链数据提供商（截至 2026 年 10 月 12 日检查）。

**现在，任何依赖 AMB 的设计都需要有固定截止日期的迁移计划**。在金融服务等系统生命周期较长的环境中，这会直接影响技术方案比较。
:::

### 设计时降低服务终止风险

无法彻底消除此风险，只能**减轻风险**。

| 缓解方式 | 内容 |
|---|---|
| **坚持使用标准协议** | 如果使用 Ethereum 或 Fabric 等开放协议，托管产品消失后可以改为自运维或迁移到其他提供商 |
| **抽象层** | 避免应用直接依赖 AMB API。抽象 RPC 接口有助于轻松切换后端 |
| **数据独立性** | 同时将链上数据保存在自己的索引或数据仓库中。这样即使更换提供商，历史数据仍然保留 |
| **密钥恢复和退出** | KMS 私有签名密钥不可导出。为某个身份充值或注册之前就规划恢复 / 退出；区分公钥下载、导入密钥备份、CloudHSM 备份 / 包装规则以及账户 / 合约轮换选项 |
| **估算迁移时间** | 测量节点重新同步和数据迁移耗时，据此判断能否在通知期内完成迁移 |

“**抽象层”是最有效的应对方式**。如果应用使用标准 RPC 接口（如 Ethereum JSON-RPC），后端就可以是 AMB、自运维节点或第三方服务。直接耦合到 AMB 专用 API 会失去这种灵活性。

## 与 AWS 服务的集成

AMB 的一项实质性优势是与 AWS 生态系统集成。

| 集成 | 用途 |
|---|---|
| **IAM** | 对链节点访问进行控制：通过 IAM policy 管理访问权限 |
| **CloudWatch** | 指标和日志 |
| **CloudTrail** | 审计管理 API 调用 |
| **VPC endpoints / PrivateLink** | 私有连接 |
| **KMS** | 密钥管理 |

**IAM 集成尤其有用**。自运维节点的 RPC 端点需要自己的身份验证机制（或者仅使用网络层控制）；而 AMB 可通过 IAM 控制，从而与内部权限模型保持一致。

对于私有连接，[VPC Lattice 章节](../service-mesh/vpc-lattice/README.md)中的概念可能适用，不过**AMB 是否能与 Lattice 直接集成仍须单独确认**（与 [VPC Lattice 限制](../service-mesh/vpc-lattice/06-constraints.md)中尚未确认的事项性质相同）。

## 与自运维方案比较

| 项目 | AMB | 自运维（EKS / EC2） |
|---|---|---|
| **初始构建时间** | 短 | 长（包括同步） |
| **运维人员** | 少 | 多 |
| **硬分叉响应** | AWS 负责 | **你负责** |
| **磁盘增长管理** | AWS 负责 | **你负责** |
| **客户端选择** | 有限 | **自由** |
| **可调范围** | 有限 | **全部可调** |
| **验证节点运行** | 困难 | **可行** |
| **支持的区块链** | AMB 支持的列表 | **不受限制** |
| **成本结构** | 取决于产品：预置节点 / 组件费用或无服务器请求 / API 费用；应测量相同覆盖范围和用量下的成本 |
| **IAM 集成** | **内置** | 自行构建 |
| **服务生命周期风险** | 托管产品的可用性 / 支持可能变化 | 仍需承担开源 / 客户端维护、协议和基础设施依赖 |
| **可移植性** | 在标准协议上具备可移植性 | - |

## 总结

- AMB 提供 **AMB Access Fabric**（联盟网络）、**AMB Access 公有链节点**（卸载节点运维）以及 **AMB Query**（无需节点即可查询数据），分别解决不同问题。
- 托管维护可以减少节点运维工作，但仍需关注各产品自身的职责、升级通知和应用验证。
- AMB 无法提供的能力中，最重要的区别是**验证节点运行**。托管节点用于查询和交易提交；质押需要另一套条件。
- 决策顺序：**① 是否真的需要节点 → ② 是否需要控制权 → ③ 成本 → ④ 能否混合使用**。许多场景在第 1 步就可以排除运行节点。
- **QLDB 于 2025 年 7 月 31 日终止服务**，其迁移路径 Aurora PostgreSQL **不提供加密可验证性**。这是托管服务终止、替代品又不具备功能等价性的案例。
- 最有效的缓解方式是**标准协议加抽象层**。避免直接耦合 AMB 专用 API，就可以更换后端。
- **AWS 已宣布 AMB 将结束支持**：2026 年 10 月 29 日后不再接受新客户，2027 年 9 月 29 日后停止访问。任何依赖 AMB 的设计都需要有明确日期的迁移计划。

# 延迟影响分析测验

本测验检查你对 Lattice 迁移中导致延迟上升或下降的因素，以及如何设计 PoC 测量的理解。

## 单选题

1. 为什么不能预先笼统地说 Lattice 迁移“会增加 N 毫秒延迟”？
   - A) AWS 不会发布延迟数据
   - B) 代理处理、网络路径、TLS 复用和身份验证会同时变化，因此应测量实际工作负载
   - C) Lattice 尚未正式发布
   - D) 延迟完全由区域决定

<details>

<summary>显示答案</summary>

**答案：B) 代理处理、网络路径、TLS 复用和身份验证会同时变化，因此应测量实际工作负载**

**解释：**
这里没有提供任何 Lattice 延迟测量结果。延迟变化的方向和幅度取决于测试配置；不要把微秒级估算或保证的性能改善当作实测结果。
</details>

2. p50 和 p99 受不同因素影响，这意味着什么？
   - A) p99 总是比 p50 差，因此只看 p50 就够了
   - B) 中位数和尾延迟对资源争用、冷启动和路由的反应可能不同，因此两者都要测量
   - C) p50 和 p99 受相同因素影响，因此测量其中一个就够了
   - D) p99 都是噪声，应该忽略

<details>

<summary>显示答案</summary>

**答案：B) 中位数和尾延迟对资源争用、冷启动和路由的反应可能不同，因此两者都要测量**

**解释：**
不同分位数的响应是需要调查的假设，并不保证 p50 会变差而 p99 会改善。还应在延迟分布之外记录错误、吞吐量和工作负载条件。
</details>

3. 哪种客户端设置被指出可能比多经过一个代理跳点的影响更大？
   - A) DNS 缓存 TTL
   - B) keepalive 和连接池设置
   - C) 日志级别
   - D) 请求超时值

<details>

<summary>显示答案</summary>

**答案：B) keepalive 和连接池设置**

**解释：**
引用的基准测试表明，在该工作负载中，连接复用会产生影响。建立新的 TCP 连接会增加连接设置开销；只有使用 TLS 时才会发生 TLS 握手。这并不是 Lattice 延迟测量结果。
</details>

4. 在 PoC 测量矩阵中，`IAM Auth on` 与 `IAM Auth off` 的差值说明什么？
   - A) 跨 AZ 路径的成本
   - B) 条件匹配时，签名、凭证处理和已启用策略评估的综合影响
   - C) 移除 Envoy CPU 争用的影响
   - D) 单纯由路径变更带来的影响

<details>

<summary>显示答案</summary>

**答案：B) 条件匹配时，签名、凭证处理和已启用策略评估的综合影响**

**解释：**
开启/关闭身份验证并不能单独隔离 HMAC 的影响。应在匹配条件下重复运行，保持负载和连接设置不变，并报告凭证刷新、失败情况和吞吐量。
</details>

5. 关于跨 AZ 流量，哪项说法正确？
   - A) 它既会增加延迟，也会产生单独的额外费用
   - B) 它会增加延迟，但通过 Lattice 的流量不另收跨 AZ 费用；该费用已包含在数据处理费用中
   - C) 它既不影响延迟，也不影响费用
   - D) Lattice 总会选择调用方所在 AZ 中的 Target，因此无需考虑跨 AZ

<details>

<summary>显示答案</summary>

**答案：B) 它会增加延迟，但通过 Lattice 的流量不另收跨 AZ 费用；该费用已包含在数据处理费用中**

**解释：**
跨 AZ 流量会因物理距离而增加延迟（已测得的基线：同 AZ 为 0.339 ms，跨 AZ 为 0.544 ms）。但计费方面，Lattice 不会单独收取跨 AZ 费用，而是将其计入数据处理费用。D 不正确：官方文档尚未确认 Lattice 选择 Target 时是否会考虑调用方所在 AZ，必须通过 PoC 测量；这正是矩阵中加入 AZ 维度的原因。
</details>

6. 为什么测量设计需要预热？为什么还应单独记录首个请求的延迟？
   - A) 不需要预热；测量首个请求就够了
   - B) 冷凭证或连接池可能增加初始化开销，因此应分别记录首个请求和预热后的延迟，并在冷启动频繁时同时评估
   - C) 预热只会改善 p50，不会影响 p99
   - D) 首个请求总会失败

<details>

<summary>显示答案</summary>

**答案：B) 冷凭证或连接池可能增加初始化开销，因此应分别记录首个请求和预热后的延迟，并在冷启动频繁时同时评估**

**解释：**
缓存或连接池为空时，首个请求可能包括获取凭证和建立连接的开销。凭证获取路径取决于提供方：IRSA 使用 STS，而 EKS Pod Identity 使用节点代理和 EKS Auth。只有 TLS 连接才会有 TLS 握手开销。应分别记录首个请求和预热后的延迟，并注明提供方/缓存/传输状态；不要假设每个首个请求都会直接调用 STS 或执行 TLS 握手。如果冷启动频繁，应评估这两种情况。
</details>

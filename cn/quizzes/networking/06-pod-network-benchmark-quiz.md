# Pod 网络基准测试测验

以下问题针对 2026 年 9 月 2 日的报告，不代表普遍的性能或计费保证。

1. 使用 `ping -c 200 -i 0.05` 测量时，Pod 到 Pod 的平均 RTT 从同一节点 → 同一 AZ 中的不同节点 → 不同 AZ 如何变化？
   - A) 0.040 ms → 0.544 ms → 0.339 ms：跨 AZ 比同一 AZ 更快
   - B) 三条路径都在约 0.3 ms 的噪声范围内
   - C) 在本次运行中，0.040 ms → 0.339 ms → 0.544 ms：相邻放置方式之间分别约增加 +0.30 ms 和 +0.21 ms
   - D) 0.040 ms → 0.339 ms → 5.4 ms：AZ 边界使 RTT 增至整毫秒级

<details>
<summary>显示答案</summary>

**答案：C) 在本次运行中，0.040 ms → 0.339 ms → 0.544 ms：相邻放置方式之间分别约增加 +0.30 ms 和 +0.21 ms**

**解释：**
报告中的 ping 均值基于每条路径 200 次探测，丢包数为 0/200。跨 AZ 减去同一 AZ 的差值为 0.205 ms，四舍五入后为 0.21 ms；跨 AZ 减去同一节点的差值为 0.504 ms。HTTP p50 为 0.259 → 0.461 → 0.704 ms。用 ping 均值减去 HTTP 中位数，无法单独分离出用户空间开销。5.4 ms 是高负载 TCP RTT 的数值，其队列位置并未测量。另一份 Istio 报告中的 +1.29 ms，是不同硬件和工作负载下整个场景的 p50 差值，并非测得的单个代理开销，不能将其加到这些数值上。

</details>

2. 单个 iperf3 TCP 流（`-P 1`）在同一 AZ 和跨 AZ 路径上都停在 4.96 Gbps，而 8 个流（`-P 8`）在两条路径上都达到 9.94 Gbps。对这两个数值，哪种解释最恰当？
   - A) 4.96 Gbps 是一个客户端 CPU 核达到饱和；8 个流更快是因为使用了更多核心
   - B) 通常的 5 Gbps 单流上限与 4.96 Gbps 相符；并行流接近了这台 m5.xlarge 的 10 Gbps 突发峰值
   - C) 4.96 Gbps 是 m5.xlarge 的基准带宽，8 个流消耗突发积分以达到峰值
   - D) 单个流未启用巨型帧（MTU 9001）

<details>
<summary>显示答案</summary>

**答案：B) 通常的 5 Gbps 单流上限与 4.96 Gbps 相符；并行流接近了这台 m5.xlarge 的 10 Gbps 突发峰值**

**解释：**
m5.xlarge 的基准带宽为 1.25 Gbps，尽力而为的突发峰值为 10 Gbps；20 秒的测试无法证明峰值带宽可以持续提供。在节点间路径上，客户端进程 CPU 使用率为 19.5 % / 20.0 %；相比之下，同一节点的单流测试达到 29.97 Gbps 时为 99.8 %。这些数值支持带宽受限的解释，但不能排除所有主机瓶颈。重传数从 4 / 2 增加到 5,874 / 5,979；由于未收集 ENA 计数器，因此无法证实存在流量整形。AWS 还说明，在集群置放群组内最高可达 10 Gbps，符合条件的同一 AZ ENA Express 流最高可达 25 Gbps：5 Gbps 并非普遍适用的上限。

</details>

3. 为什么固定并发池 HTTP 吞吐量的报告值会有差异，即使两项八流 iperf3 测试都达到 9.94 Gbps？
   - A) 跨 AZ 链路会将请求/响应流量的带宽减半
   - B) 跨 AZ 路径上的错误和重试有所增加
   - C) 承载 srv-b 的节点 CPU 比承载 srv-a 的节点慢
   - D) 稳态闭环中约有 16 个在途请求，这与吞吐量 ≈ 16 / 平均延迟相符；观测到的速率相差 33.5 %，但这不能证明存在普遍的 AZ 惩罚

<details>
<summary>显示答案</summary>

**答案：D) 稳态闭环中约有 16 个在途请求，这与吞吐量 ≈ 16 / 平均延迟相符；观测到的速率相差 33.5 %，但这不能证明存在普遍的 AZ 惩罚**

**解释：**
报告中的均值为 0.355 / 0.415 / 0.624 ms。用 16 除以这些时长，得到 45,070 / 38,554 / 25,641 qps，与报告中的 44,991 / 38,507 / 25,602 接近。(38,507 − 25,602) / 38,507 ≈ 33.5 %。利特尔定律描述了所述稳态条件下的并发数、吞吐量和平均耗时；它不能确定延迟的唯一原因。报告记录的错误数为零，且两台服务器使用相同实例类型，没有证据支持选项 B 或 C。CPU 争用可能导致同一节点的尾延迟更差，但分析性能剖析并未证实这一点。

</details>

4. 在 100 qps / 4 个连接不变的情况下，改用 `-keepalive=false`（每个请求都建立新的 TCP 连接）后，跨 AZ HTTP p50 如何变化？
   - A) 0.704 ms → 1.517 ms（+0.813 ms），增至两倍以上；建立连接会增加开销，但本实验无法单独分离各项开销
   - B) 没有变化；内核无论如何都会复用连接
   - C) 0.704 ms → 0.813 ms，小幅增加
   - D) p50 没有变化；只有 p99 变差

<details>
<summary>显示答案</summary>

**答案：A) 0.704 ms → 1.517 ms（+0.813 ms），增至两倍以上；建立连接会增加开销，但本实验无法单独分离各项开销**

**解释：**
禁用 keepalive 后的中位数为 0.664 / 1.079 / 1.517 ms，分别增加了 0.405 / 0.618 / 0.813 ms。最后一个数值是增量，而不是新的中位数，因此 C 错误。建立连接会带来开销，但用 ping RTT 做减法并不能独立测出固定的 0.3 ms 套接字开销。值得结合应用测试连接复用。未测量 TIME_WAIT；它取决于关闭连接的一端以及连接终止行为。

</details>

5. 对于 223,376,179,200 字节的载荷，按报告明确采用的十进制 GB 换算方式，并在每个 EC2 端点按 $0.01/GB 计费，报告估算的费用是多少？
   - A) $0（Region 内流量免费）
   - B) $2.23（每 GB $0.01，只计费一次）
   - C) 按报告的十进制 GB 载荷模型，发送端和接收端均按 $0.01/GB 计费，费用约为 $4.47；未核实实际账单
   - D) 不超过 1.25 Gbps 基准带宽的流量免费；只有超过基准的突发流量才计费

<details>
<summary>显示答案</summary>

**答案：C) 按报告的十进制 GB 载荷模型，发送端和接收端均按 $0.01/GB 计费，费用约为 $4.47；未核实实际账单**

**解释：**
载荷的确切大小为 223,376,179,200 字节。历史模型将其除以 10⁹，再乘以 $0.01 两次，得出约 $4.47；三次跨 AZ iperf3 运行的总数据量为 260,633,264,128 字节，按同一模型计算约为 $5.21。单个方向的载荷可能在两端都产生费用。公开的 `get-products` 定价并不是账户实际支付的账单；本次审计也未证明计费的 EC2 单位等同于十进制载荷 GB。请核对 CUR 计量单位、协议开销、两端流量以及适用的折扣。18 个区间内达到的 9.92–9.94 Gbps 并不会形成免费的基准传输层级。

</details>

6. 在默认 `ndots:5` 的 Pod（glibc 2.41）中，对 `sts.ap-northeast-2.amazonaws.com`（3 个点）进行一次冷解析时，tcpdump 中出现了多少次 DNS 查询和 NXDOMAIN 应答？
   - A) 2 次查询，0 个 NXDOMAIN：因为有 3 个点，名称会立即作为绝对名称查询
   - B) 在记录的查询中，共 10 次查询、8 个 NXDOMAIN：四个失败的搜索候选项各自执行 A+AAAA 查询，然后绝对名称查询成功
   - C) 5 次查询，4 个 NXDOMAIN：每个候选项只执行一次 A 查询
   - D) 4 次查询，2 个 NXDOMAIN

<details>
<summary>显示答案</summary>

**答案：B) 在记录的查询中，共 10 次查询、8 个 NXDOMAIN：四个失败的搜索候选项各自执行 A+AAAA 查询，然后绝对名称查询成功**

**解释：**
该 Pod 使用记录中的四项搜索列表，并采用 glibc AF_UNSPEC 行为。前四个候选项查询失败，产生 8 个 NXDOMAIN；随后绝对名称查询返回 A 记录 10.0.3.84 / 10.0.2.129。4.37 ms 的时间线在该 A 应答处结束，并不代表整个首次进程调用；表中未计时 AAAA 查询完成时间。报告中的预热中位数为 3.78 ms，而名称末尾加点时为 0.80 ms。`cache 30` 是 TTL 上限，并不能证明没有上游查询。在相同应答模式下，每秒 1,000 次解析意味着每秒 10,000 次查询和 8,000 个 NXDOMAIN；这并不意味着 CoreDNS CPU 使用率为 80 %。其他名称可能更早成功，例如 `kubernetes.default` 只用了四次查询。

</details>

7. 在同一个 `ndots:5` Pod 中，看起来像 FQDN 的 `kubernetes.default.svc.cluster.local`（末尾没有点）也产生了 10 次查询和 8 个 NXDOMAIN。为什么它会遍历完整个搜索列表？
   - A) CoreDNS 的 `kubernetes` 插件只会立即应答 `cluster.local` 区域之外的名称
   - B) glibc 总是将以 `svc.cluster.local` 结尾的名称视为 Service 名称
   - C) `.ap-northeast-2.compute.internal` 后缀在搜索列表中排第一，因此会先尝试它
   - D) 四个点少于 ndots 5，因此该解析器先尝试搜索候选项；候选项失败后，原始名称才查询成功，而末尾加点的查询会跳过扩展

<details>
<summary>显示答案</summary>

**答案：D) 四个点少于 ndots 5，因此该解析器先尝试搜索候选项；候选项失败后，原始名称才查询成功，而末尾加点的查询会跳过扩展**

**解释：**
解析器会统计点的数量；它不会识别 Kubernetes Service 后缀并据此跳过搜索。本例中，所有四个扩展后的候选项都查询失败。报告给出的数值为：转发候选项耗时 2.2 ms，该 DNS 查询过程耗时 5.6 ms；名称末尾不加点时的预热中位数为 3.63 ms，加点时为 0.46 ms。单独报告的首次进程调用耗时为 7.40 ms。末尾加点会使 DNS 名称成为绝对名称，但若将其放入应用 URL，还需要兼容的 Host/SNI、证书和签名行为。不要假设它适用于每一种 HTTPS 或 AWS SDK 端点配置。

</details>

8. 在配置了 `dnsConfig.options` `ndots:1` 的 Pod 中，外部名称的查询次数从 10 次降至 2 次，但集群内部短名称 `kubernetes.default` 的表现变差（6 次查询、4 个 NXDOMAIN；中位数为 2.04 ms，而 `ndots:5` 时为 1.71 ms）。发生了什么？
   - A) 在该解析器中，`ndots:1` 会先将含一个点的名称作为绝对名称查询；收到 NXDOMAIN 后再回退到搜索列表，从而将这个看起来像内部名称的名称泄露到上游
   - B) `ndots:1` 会禁用 CoreDNS 缓存
   - C) `ndots:1` 时 `kubernetes.default` 完全无法解析
   - D) glibc 会按顺序发送 A 和 AAAA 查询，从而使耗时加倍

<details>
<summary>显示答案</summary>

**答案：A) 在该解析器中，`ndots:1` 会先将含一个点的名称作为绝对名称查询；收到 NXDOMAIN 后再回退到搜索列表，从而将这个看起来像内部名称的名称泄露到上游**

**解释：**
观测到的顺序是 `kubernetes.default.`（转发后，在报告的 1.6 ms 后收到 NXDOMAIN），接着是 `kubernetes.default.bench-net.svc.cluster.local`（NXDOMAIN），最后是 `kubernetes.default.svc.cluster.local`（172.20.0.1）。因此查询次数为 6 次 / 4 个 NXDOMAIN，而 `ndots:5` 下为 4 次 / 2 个。`ndots` 会改变客户端的查询顺序，不会决定 CoreDNS 是否启用缓存。这次 glibc 查询使用了 A/AAAA 查询对，但地址族和解析器选项可能改变这种行为。对于 `ndots:1`，完整 Service 名称可以减少失败的绝对名称尝试。末尾加点会跳过搜索，但不能保证所有解析器和故障情况下的查询次数或延迟都相同。

</details>

9. 对使用 `-r 0.00001` 重新运行 Fortio 测试的报告，哪种解读正确？
   - A) 第一次运行的错误率很高
   - B) 默认的 1 ms 最低桶分辨率对于所需的比较来说过于粗糙；报告用 10 µs 分辨率重新运行，但单个桶并不意味着 p50 普遍等于 0.5 ms
   - C) 使用默认分辨率时，Fortio 不会计算 p99.9
   - D) 第一次运行时意外禁用了 keepalive

<details>
<summary>显示答案</summary>

**答案：B) 默认的 1 ms 最低桶分辨率对于所需的比较来说过于粗糙；报告用 10 µs 分辨率重新运行，但单个桶并不意味着 p50 普遍等于 0.5 ms**

**解释：**
在 Fortio 1.69.5 中，`-r` 的单位是秒：最小桶分辨率为 0.001，即 1 ms；而 0.00001 即 10 µs。较大的直方图桶可能会更宽。百分位数会在桶的边界内插值，观测到的最小值和最大值也会影响第一个和最后一个桶。因此，原先“所有亚毫秒响应都意味着 p50 = 0.5 ms”的说法是错误的。keepalive 测试的中位数为 0.259–0.704 ms，属于亚毫秒级，但某些尾延迟和新建连接测试的中位数超过 1 ms。应保留报告中的重新运行历史、平均值、完整直方图和错误计数，而不要将插值本身贴上毫无意义的标签。

</details>

10. 为什么历史应用基准测试没有比较 Service/流量分配？
   - A) Fortio 无法将 Service DNS 名称作为目标
   - B) kube-proxy 处于 IPVS 模式，因此没有可测量的 iptables 跳转
   - C) 根据报告，LBC 准入 webhook 故障，拒绝了基准测试创建 Service 的请求；应用测试使用 Pod IP，且没有绕过该 webhook
   - D) 测试过但未列入表格，因为结果与 Pod IP 的数值一致

<details>
<summary>显示答案</summary>

**答案：C) 根据报告，LBC 准入 webhook 故障，拒绝了基准测试创建 Service 的请求；应用测试使用 Pod IP，且没有绕过该 webhook**

**解释：**
历史诊断报告称，LBC v3.2.1 有两个副本，连续 48 天处于 CrashLoopBackOff 状态，重启 9,250 次，并出现 `no matches for kind "ListenerSet" in version "gateway.networking.k8s.io/v1"`，随后在约 2m18s 后发生缓存同步超时。这些是归因于该事件的详细信息；本次审计未独立找回原始日志，也未检查运行中的集群。故障中的 `failurePolicy: Fail` webhook 会拒绝符合其规则、选择器和条件的请求；仅凭 `namespaceSelector: {}` 不能证明每个 Service CREATE 请求都会被拦截。应用基准测试未使用 Service，而 DNS 使用的是预先存在的 `kube-dns`。`PreferClose` 现已弃用，并作为 `PreferSameZone` 的别名；两者均未在此处测试。测试也未收集 ENA 计数器，且没有进行独立的重复测试。

</details>

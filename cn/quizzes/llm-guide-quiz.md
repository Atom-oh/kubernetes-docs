# 使用 LLM 阅读：llms.txt 测验

1. 本指南的 `llms.txt` 文件包含什么，用途是什么？
   - A) 完整的韩文 Markdown 内容，供用户整份粘贴到上下文窗口
   - B) 每个内容页的标题、摘要和原始 Markdown URL 索引，使 LLM 能选择并只获取所需页面
   - C) 测验答案集合，用于自动评分
   - D) 图表 PNG 文件包，用于制作幻灯片
<details>
<summary>显示答案</summary>

**答案：B) 每个内容页的标题、摘要和原始 Markdown URL 索引，使 LLM 能选择并只获取所需页面**

**说明：**
端点表中说明，`llms.txt` 是每个内容页的分组、标题、摘要和原始 Markdown URL 索引，用于让 LLM 选择并只获取所需页面。每个内容链接都使用 `/llms/<locale>/<source path>.md`，因此模型读取的是文档源文件，不会包含渲染页面的侧边栏或脚本。完整 Markdown 内容存储在单独的 `llms-full-ko.txt`/`llms-full-en.txt` 文件中。索引不会逐页列出测验和实验；`## Optional` 部分针对每种语言各包含一个测验索引链接和一个实验索引链接。

</details>

2. 完整内容文件以哪些语言发布？
   - A) 仅韩文（`llms-full-ko.txt`）
   - B) 韩文和英文：两个文件（`llms-full-ko.txt`、`llms-full-en.txt`）
   - C) 五种语言：韩文、英文、中文、日文和西班牙文
   - D) 一个合并所有语言的 `llms-full.txt` 文件
<details>
<summary>显示答案</summary>

**答案：B) 韩文和英文：两个文件（`llms-full-ko.txt`、`llms-full-en.txt`）**

**说明：**
按语言提供的完整文件是 `llms-full-ko.txt` 和 `llms-full-en.txt`。索引、清单、分节文件包和单文档 Markdown 也是其他端点，均通过 `https://www.atomai.click/kubernetes-docs/` 提供。建议将韩文文件用于“整本书上下文或 RAG 索引”，将英文文件用于“英文工具和流水线”。

</details>

3. 成功部署网站时，`llms.txt` 和完整文件如何生成？
   - A) 作者每次编辑后都要手动重新上传这三个文件
   - B) 每周的新闻摘要工作流会刷新它们
   - C) 网站构建会从同一份源内容生成这些文件，并一起部署
   - D) 服务器会针对每个 LLM 请求即时转换文档
<details>
<summary>显示答案</summary>

**答案：C) 网站构建会从同一份源内容生成这些文件，并一起部署**

**说明：**
页面指出：“网站构建会从同一份源内容生成这些文件，并一起部署，因此它们始终与已发布内容保持一致。”这些文件是部署流水线的构建产物，并非手动上传，也不是按请求即时转换。

</details>

4. 在 `llms.txt` 和完整文件中如何处理测验文档？
   - A) 每个测验页面都会出现在索引和完整文件中，包括答案
   - B) `llms.txt` 的 `## Optional` 下只链接测验索引页（每种语言一个链接）；单个测验页及其答案都不会放入索引或完整文件
   - C) 索引会列出每个测验页，但完整文件会将其排除
   - D) 测验页会出现在完整文件中，但不在索引中
<details>
<summary>显示答案</summary>

**答案：B) `llms.txt` 的 `## Optional` 下只链接测验索引页（每种语言一个链接）；单个测验页及其答案都不会放入索引或完整文件**

**说明：**
页面说明：“`llms.txt` 中只会在 `## Optional` 下放置测验索引页的链接（每种语言一个）；单个测验页（包括答案）不会放入索引或完整文件；答案不应进入 LLM 的上下文。”因此，LLM 可以发现测验存在并找到各语言的测验索引，但扁平索引和全书文件都不会包含任何单独测验页或答案。实验指南有所不同：`llms.txt` 也只提供其实验索引链接，但完整文本会纳入完整文件。

</details>

5. 鉴于完整文件的大小，页面建议如何将它们与 LLM 配合使用？
   - A) 每次提示都粘贴数 MiB 的完整文件；这是最准确的方式
   - B) 将完整文件拆成多个部分，每次都附上所有部分
   - C) 将模型指向索引，让它获取特定页面；这对大多数工具效果更好
   - D) 只提供图表查看器 URL，让 LLM 自行推断其余内容
<details>
<summary>显示答案</summary>

**答案：C) 将模型指向索引，让它获取特定页面；这对大多数工具效果更好**

**说明：**
“大小”说明指出，完整文件有数 MiB，并且“对大多数工具来说，将模型指向索引并让它获取特定页面，比在一次提示中粘贴整本书效果更好”。第一个示例提示（“阅读……/llms.txt，查找……文档并总结……”）正是这种用法。完整文件适合先下载完整文件再分块使用，例如用于 RAG 索引。

</details>

6. 为什么说按文档对 `llms-full-*.txt` 进行分块非常简单？
   - A) 每篇文档都存储为单独的 ZIP 条目
   - B) 每篇文档前都有一个包含 `Source: <URL>` 的分隔块
   - C) 每篇文档都会截断到固定的 4,096 个字符
   - D) 文档在 JSON 数组中各占一个元素
<details>
<summary>显示答案</summary>

**答案：B) 每篇文档前都有一个包含 `Source: <URL>` 的分隔块**

**说明：**
“格式说明”指出，“每篇文档前都有一个分隔块”：一行虚线、一条类似 `Source: https://www.atomai.click/kubernetes-docs/en/core/01-cluster-architecture` 的 URL，以及另一行虚线。RAG 示例中的注释也重复说明：“文档通过 `Source: <URL>` 块分隔，因此按文档分块非常简单。”该文件是纯 Markdown 文本，而不是 ZIP 或 JSON。

</details>

7. 页面如何描述 LLM 和用户分别如何使用完整文件中的图表信息？
   - A) LLM 直接分析 PNG 图像，而用户阅读替代文本
   - B) LLM 阅读图表描述（替代文本）来理解图表；用户则打开交互式查看器 URL，并使用 Export 菜单下载 PNG/JPEG/WebP、SVG、WebM 或 Share Card
   - C) LLM 和用户都无法从完整文件中获取任何图表信息
   - D) LLM 从查看器 URL 渲染 WebM 动画并交给用户
<details>
<summary>显示答案</summary>

**答案：B) LLM 阅读图表描述（替代文本）来理解图表；用户则打开交互式查看器 URL，并使用 Export 菜单下载 PNG/JPEG/WebP、SVG、WebM 或 Share Card**

**说明：**
“图表面向用户：导出链接”一节说明，由于完整文件会原样包含每篇文档的 Markdown，因此文本中包含每张图表的替代文本及其查看器 URL（`https://www.atomai.click/kubernetes-docs/archmaps/<name>.html`）。“文本 LLM 会使用替代文本和周围的说明文字，但无法可靠推断仅存在于图像中的节点/边；用户则打开 URL，并使用查看器的 **Export** 菜单下载 PNG/JPEG/WebP、双主题 SVG、6 秒轨迹动画 WebM 或 1200×630 Share Card。”每个图表的使用指导位于《指南路线图》的“分享图表”一节。

</details>

8. 页面对从查看器导出的图表文件（PNG、SVG、WebM、Share Card）有什么限制说明？
   - A) 导出文件可用作架构已通过验证的正式证据
   - B) 导出文件是沟通素材，而不是架构已经过验证的证据
   - C) 导出文件只供 LLM 使用，用户无法打开
   - D) 导出文件是文档的正式发布形式，会取代源 HTML
<details>
<summary>显示答案</summary>

**答案：B) 导出文件是沟通素材，而不是架构已经过验证的证据**

**说明：**
该节最后指出：“导出文件是沟通素材，而不是架构已通过验证的证据。”导出图表可用于分享，例如发布到 LinkedIn 或放入演讲幻灯片；但图像存在与否并不能说明其中描绘的架构是否经过验证。

</details>

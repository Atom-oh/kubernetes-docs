# LLM 게이트웨이(Inference Gateway) 퀴즈

이 퀴즈는 LLM 게이트웨이의 동작 원리 — 컨트롤/데이터 플레인 분리, 2단계 거버넌스, 캐시 불변식, 자동 라우팅 계층, PII 가드, 정책 프롬프트 주입과 프롬프트 인젝션 방어, 컨텍스트 인식 라우팅 — 에 대한 이해를 테스트합니다.

## 퀴즈 개요
- API 게이트웨이와 LLM 게이트웨이의 차이
- 데이터 플레인 / 컨트롤 플레인 분리와 예산 리스
- 2단계 거버넌스 (PreCheck / Settle)
- 캐시 불변식과 원문 그대로 전달
- 자동 라우팅 7계층과 불변식
- PII 가드 파이프라인
- 시스템 프롬프트 주입과 프롬프트 인젝션 방어
- 컨텍스트 인식 (프리픽스 친화성, 컨텍스트 창)

## 객관식 문제

### 1. LLM 게이트웨이의 거버넌스가 "사전 검사(PreCheck) → 사후 정산(Settle)"의 2단계로 설계되는 근본적인 이유는 무엇인가요?

A. 스트리밍 응답은 압축되어 있어 한 번에 파싱할 수 없기 때문
B. 요청 비용(특히 출력 토큰)은 모델이 응답을 끝낸 뒤에야 알 수 있지만, 거부는 모델을 호출하기 전에 결정해야 하기 때문
C. 제공자 API가 요청당 두 번의 인증을 요구하기 때문
D. 감사 레코드를 두 번 써야 해시 체인이 성립하기 때문

</details>

### 2. 다음 중 "캐시 불변식(cache invariant)"을 올바르게 설명한 것은 무엇인가요?

A. 게이트웨이는 모든 응답을 캐시해 동일한 질문에 재사용해야 한다
B. ingress 프로토콜과 제공자 프로토콜이 같으면 요청 본문을 바이트 그대로(RawBody) 전달해야 프롬프트 캐시 프리픽스가 깨지지 않는다
C. 캐시 히트율은 항상 90% 이상이어야 한다
D. `cache_control` 필드는 게이트웨이가 항상 제거해야 한다

<details>
<summary>정답 보기</summary>

**정답: B. ingress 프로토콜과 제공자 프로토콜이 같으면 요청 본문을 바이트 그대로(RawBody) 전달해야 프롬프트 캐시 프리픽스가 깨지지 않는다**

**설명:**
Anthropic 프롬프트 캐시와 vLLM 프리픽스 캐시는 요청 본문의 **정확한 프리픽스**(tools → system → messages)를 해시해 히트를 판정합니다. 게이트웨이가 JSON을 파싱해 다시 직렬화하기만 해도(키 순서, 공백, 숫자 표현 변경) 프리픽스가 달라져 캐시가 통째로 미스납니다. 코딩 에이전트 트래픽은 90% 이상이 캐시 히트이고 캐시 읽기는 기본 입력 단가의 10%이므로, 이 불변식을 깨면 청구서가 최대 10배로 뛸 수 있습니다. 이 때문에 본문을 바꾸는 필터(PII 마스킹, 정책 프롬프트 주입)는 명시적 옵트인과 비용 경고를 동반해야 합니다.

</details>

### 3. 자동 라우팅에서 폴백(fallback)이나 비용 티어 치환 뒤에 RBAC를 **다시** 검사해야 하는 이유는 무엇인가요?

A. 치환된 모델의 가격이 다르기 때문에 예산을 재계산해야 한다
B. 폴백·치환으로 체인에 추가된 대상은 원래의 허용 목록 검사를 거치지 않았으므로, 재검사하지 않으면 폴백 경로가 권한 우회 통로가 된다
C. 서킷 브레이커가 열리면 RBAC 캐시가 무효화된다
D. 제공자가 바뀌면 가상 키를 재발급해야 한다

<details>
<summary>정답 보기</summary>

**정답: B. 폴백·치환으로 체인에 추가된 대상은 원래의 허용 목록 검사를 거치지 않았으므로, 재검사하지 않으면 폴백 경로가 권한 우회 통로가 된다**

**설명:**
허용 목록 검사는 클라이언트가 요청한 모델에 대해 실행됩니다. 그 뒤 L1(미등록 모델 폴백), L3(비용 티어 치환), L6(업스트림 404 시 체인 확장)이 새 대상을 추가하면 그 대상은 검사를 받은 적이 없습니다. 예를 들어 팀에 `haiku`만 허용됐는데 폴백이 `opus`를 추가하면 재검사 없이는 그대로 전달됩니다. 그래서 모든 ingress 핸들러는 라우팅 뒤에 `FilterModelAllowed` 같은 재검사를 반드시 실행해야 하며, 치환은 "좁히기만 하고 넓히지 않는다"는 불변식을 지켜야 합니다.

</details>

### 4. 스트리밍 응답에서 게이트웨이의 페일오버(다른 제공자로 재시도)가 "첫 토큰(TTFT) 이전에만" 허용되는 이유로 가장 적절한 것은?

A. 제공자마다 SSE 프레임 형식이 달라 중간에 바꿀 수 없기 때문
B. 첫 토큰 이후에 재시도하면 클라이언트가 이미 본 부분이 중복되고 토큰이 두 번 과금되며, 두 응답이 이어 붙기 때문
C. 서킷 브레이커가 첫 토큰 이후에는 상태를 바꾸지 않기 때문
D. 감사 레코드가 이미 기록되어 수정할 수 없기 때문

<details>
<summary>정답 보기</summary>

**정답: B. 첫 토큰 이후에 재시도하면 클라이언트가 이미 본 부분이 중복되고 토큰이 두 번 과금되며, 두 응답이 이어 붙기 때문**

**설명:**
스트림 중간 실패 시 클라이언트는 이미 응답의 일부를 렌더링한 상태입니다. 새 제공자에서 처음부터 다시 생성하면 (1) 같은 입력 토큰이 두 번 과금되고, (2) 두 모델의 서로 다른 출력이 이어 붙어 일관성이 깨지고, (3) 이미 방출된 `tool_use` 블록과 충돌할 수 있습니다. 올바른 동작은 `error` 프레임을 보내고 스트림을 닫는 것이며, 재시도 여부는 클라이언트가 결정합니다. 서킷 브레이커와 우선순위 체인은 첫 바이트가 나가기 전까지만 개입합니다.

</details>

### 6. Amazon Bedrock Guardrails와 관련해 게이트웨이가 반드시 처리해야 하는 "우회(bypass)" 문제는 무엇인가요?

A. 가드레일이 스트리밍 응답에서는 동작하지 않는다
B. 가드레일은 `InvokeModel`/`Converse` API 호출의 파라미터이므로, 게이트웨이가 SDK 호출에 `guardrailIdentifier`를 붙이지 않으면 콘솔에서 만든 가드레일이 전혀 적용되지 않는다
C. 가드레일은 리전마다 이름이 달라 라우팅과 충돌한다
D. 가드레일은 가상 키를 인식하지 못한다

<details>
<summary>정답 보기</summary>

**정답: B. 가드레일은 `InvokeModel`/`Converse` API 호출의 파라미터이므로, 게이트웨이가 SDK 호출에 `guardrailIdentifier`를 붙이지 않으면 콘솔에서 만든 가드레일이 전혀 적용되지 않는다**

**설명:**
Bedrock Guardrails는 프록시가 바이트를 전달하기만 하면 "공짜로" 적용되는 것이 아니라 API 호출 파라미터(`guardrailIdentifier`, `guardrailVersion`)입니다. 중간에 게이트웨이가 있으면 데이터 플레인의 실제 SDK 호출이 그 파라미터를 설정해야 합니다. 안전한 설계는 제공자 수준 기본 가드레일을 강제하고, 팀별로 *다른* 가드레일로 바꾸는 것은 허용하되 *끄는* 옵션은 제공하지 않는 것입니다. 게이트웨이 측 PII 마스킹과 제공자 측 가드레일은 대체 관계가 아니라 보완 관계입니다.

</details>

### 7. 게이트웨이가 조직 정책 프롬프트를 요청에 주입할 때, Anthropic Messages 요청의 `system` 배열에서 정책 블록을 **맨 앞**에 두어야 하는 이유는?

A. 모델은 배열의 첫 블록만 시스템 프롬프트로 인식하기 때문
B. 프롬프트 캐시 프리픽스는 앞에서부터 계산되므로 맨 앞에 항상 같은 바이트를 두면 프리픽스가 안정되고, 클라이언트가 지정한 `cache_control` 브레이크포인트도 무력화되지 않기 때문
C. Bedrock Converse는 첫 블록 이후를 무시하기 때문
D. OpenAI 호환 API는 `system` 배열을 지원하지 않기 때문

<details>
<summary>정답 보기</summary>

**정답: B. 프롬프트 캐시 프리픽스는 앞에서부터 계산되므로 맨 앞에 항상 같은 바이트를 두면 프리픽스가 안정되고, 클라이언트가 지정한 `cache_control` 브레이크포인트도 무력화되지 않기 때문**

**설명:**
프리픽스는 tools → system → messages 순으로 계산됩니다. 정책 블록을 맨 앞에 바이트 동일하게 두면 첫 요청은 캐시 쓰기(1.25배), 이후는 읽기(0.1배)로 정상화됩니다. 클라이언트의 `cache_control` 블록 **뒤에** 넣으면 클라이언트가 의도한 브레이크포인트가 무력화됩니다. 함께 지켜야 할 규칙은 멱등성(같은 해시의 블록이 있으면 다시 붙이지 않음), 클라이언트 시스템 프롬프트 절대 삭제 금지(Claude Code 등 하네스가 의존), 정책 버전·해시의 감사 기록, 그리고 "시스템 프롬프트는 넛지일 뿐 보안 경계가 아니다"는 인식입니다.

</details>

### 8. 프롬프트 인젝션 방어의 5개 층 중 "진짜 강제력"을 가진 층은 무엇이며 그 이유는?

A. 정책 프롬프트 주입 — 모델이 지시를 따르기 때문
B. 신뢰 경계 표시(spotlighting) — 구분자가 있으면 모델이 절대 속지 않기 때문
C. 도구 사용 허용 목록 — 모델이 무엇을 결심했든 응답의 `tool_use` 블록이 게이트웨이를 통과하지 못하면 실행되지 않기 때문
D. 인젝션 스캐너 — 모든 공격 패턴을 정규식으로 잡을 수 있기 때문

<details>
<summary>정답 보기</summary>

**정답: C. 도구 사용 허용 목록 — 모델이 무엇을 결심했든 응답의 `tool_use` 블록이 게이트웨이를 통과하지 못하면 실행되지 않기 때문**

**설명:**
모델은 요청 안의 신뢰 수준(운영자·앱·사용자·외부 데이터)을 구분하지 못하므로 정책 프롬프트 주입과 신뢰 경계 표시는 확률을 높이는 넛지이고, 인젝션 스캐너는 오탐·미탐이 있습니다. 반면 도구 사용 허용 목록은 **응답**의 `tool_use` 블록을 검사해 팀 정책에 없는 도구 이름이나 위험한 인자 패턴(`curl … | sh`)을 거부합니다. 이는 모델의 판단과 무관하게 게이트웨이가 집행하는 경계이므로, 간접 인젝션이 모델을 완전히 설득했더라도 실행 명령이 클라이언트에 도달하지 않습니다. 스트리밍에서는 해당 `tool_use` 블록의 `input_json_delta`가 모두 모일 때까지 그 블록만 버퍼링합니다.

</details>

### 9. 노드마다 데이터 플레인을 두는 분산 구조에서 팀 예산 하드 캡을 "유계(bounded)"로 지키는 예산 리스(lease) 방식의 특징으로 옳은 것은?

A. 모든 데이터 플레인이 매 요청마다 컨트롤 플레인에 동기 호출해 정확한 잔액을 확인한다
B. 각 데이터 플레인이 컨트롤 플레인에서 일정 금액의 allowance를 리스로 받아 로컬에서 차감하고, 최악의 과소비는 미결 리스의 합(Σ outstanding grants)으로 한정된다
C. 예산 카운터를 Redis에 두어 정확히 일치시킨다
D. 컨트롤 플레인이 죽으면 모든 예산 제한이 해제된다

<details>
<summary>정답 보기</summary>

**정답: B. 각 데이터 플레인이 컨트롤 플레인에서 일정 금액의 allowance를 리스로 받아 로컬에서 차감하고, 최악의 과소비는 미결 리스의 합(Σ outstanding grants)으로 한정된다**

**설명:**
매 요청 동기 호출(A)은 컨트롤 플레인을 요청 경로에 넣어 SPOF를 만듭니다. 리스 방식은 하트비트마다 "이번 주기 소비"를 보고하고 새 allowance를 받으므로 요청 경로는 로컬에서 끝나고, 과소비 상한은 `N × 한도`가 아니라 `Σ outstanding grants`입니다. 컨트롤 플레인이 죽으면 리스가 만료되고 하드 캡 팀의 요청은 402로 fail-closed됩니다 — 이것이 "SPOF 없음"의 의도된 예외이므로, 하드 캡을 리스로 걸 팀과 소프트 한도(warn)만 둘 팀을 정책에서 구분해야 합니다.

</details>

### 10. 컨텍스트 인식 게이트웨이에서 "인프라 컨텍스트"(제공자 지연, 서킷 브레이커 상태, Pod KV 캐시 사용률)가 들어가도 되는 라우팅 계층과 들어가면 안 되는 계층은?

A. 정책(RBAC) 계층에 들어가 느린 리전을 자동으로 우회해야 한다
B. 가용성(L6)과 엔드포인트 선택(L7) 계층에만 들어가야 하며, 정책(L2) 판단을 바꾸면 안 된다
C. 이름 해석(L1) 계층에서 별칭을 바꿔야 한다
D. 모든 계층에 자유롭게 들어갈 수 있다

<details>
<summary>정답 보기</summary>

**정답: B. 가용성(L6)과 엔드포인트 선택(L7) 계층에만 들어가야 하며, 정책(L2) 판단을 바꾸면 안 된다**

**설명:**
인프라 신호는 "어느 제공자/리전/Pod가 지금 건강한가"라는 가용성 질문에 답합니다. 이것이 "이 팀이 이 리전을 쓸 수 있는가"라는 정책 질문을 바꾸면, "Bedrock이 느려서 허용되지 않은 리전으로 보냈다"는 결과가 되는데 이는 장애가 아니라 데이터 주권 규정 위반입니다. 같은 원리로 의도 분류기(L4)가 죽으면 요청한 모델로 그냥 보내야 하고(라우터가 SPOF가 되면 안 됨), 세션 프리픽스 친화성은 같은 대화를 같은 캐시 도메인(Pod 또는 제공자)에 고정해 콜드 캐시를 피합니다.

</details>

### 11. `count_tokens` 계열 엔드포인트를 게이트웨이가 프록시할 때 지켜야 할 규칙으로 옳은 것은?

A. 예산 초과 시 402를 반환해 클라이언트가 요청을 포기하게 한다
B. RBAC와 라우팅은 적용하되 거버넌스 카운터는 건드리지 않고, 실패해도 200과 추정치를 반환한다
C. 항상 제공자로 전달하지 않고 게이트웨이가 바이트 수를 4로 나눠 반환한다
D. 컨텍스트 창을 넘으면 400을 반환한다

<details>
<summary>정답 보기</summary>

**정답: B. RBAC와 라우팅은 적용하되 거버넌스 카운터는 건드리지 않고, 실패해도 200과 추정치를 반환한다**

**설명:**
일부 코딩 에이전트는 `count_tokens` 호출이 non-200을 받으면 세션 자체가 죽습니다. 토큰 세기는 소비가 아니므로 레이트·쿼터·예산 카운터를 차감하지 않으며, 업스트림 실패 시에도 200과 휴리스틱 추정치를 돌려줍니다. 컨텍스트 창 초과에 대한 빠른 400 실패(양쪽 숫자 명시)는 실제 생성 요청(`/v1/messages`)에서 사전 검사보다 앞에 두는 것이고, `count_tokens`에는 적용하지 않습니다.

</details>

### 12. `/metrics` 엔드포인트 설계에서 "키 ID나 사용자 ID를 라벨에 넣지 않는다"는 규칙이 지키는 두 가지 속성은?

A. 응답 속도와 압축률
B. 카디널리티 폭발 방지와 시크릿/식별 정보 유출 방지
C. Grafana 대시보드 호환성과 색상 일관성
D. OTLP 변환 가능성과 트레이스 연결

<details>
<summary>정답 보기</summary>

**정답: B. 카디널리티 폭발 방지와 시크릿/식별 정보 유출 방지**

**설명:**
`/metrics`는 보통 인증 없이 노출됩니다. 라벨 값이 키 ID·사용자 ID·정규화 전 요청 모델명처럼 무한히 늘어나는 값이면 Prometheus 시계열이 폭발하고, 동시에 누가 어떤 모델을 쓰는지가 인증 없이 드러납니다. 그래서 라벨 값은 설정에 선언된 값(팀, 정식 모델명, 제공자)으로 한정하고, 해석 전에 거부된 요청은 `_rejected` 같은 센티널로 접습니다. 같은 이유로 트레이스 스팬 속성에 프롬프트 원문을 넣지 않고, 업스트림 에러 본문(ARN 포함 가능)은 스크러빙해 전달합니다.

</details>

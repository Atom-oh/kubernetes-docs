# 레이턴시 영향 분석 퀴즈

이 퀴즈는 Lattice 전환의 레이턴시 악화·개선 요인과 PoC 측정 설계에 대한 이해도를 테스트합니다.

## 객관식 문제

1. Lattice 전환의 레이턴시 영향을 사전에 "몇 ms 늘어난다"로 단정할 수 없는 이유는?
   - A) AWS가 레이턴시 수치를 공개하지 않기 때문이다
   - B) 프록시 통과 횟수 감소(개선)와 네트워크 경유 추가(악화)가 같은 크기 대에서 경쟁하며, 어느 쪽이 이기는지가 환경에 따라 달라지기 때문이다
   - C) Lattice가 아직 GA가 아니기 때문이다
   - D) 레이턴시는 리전에 따라서만 결정되기 때문이다

<details>

<summary>정답 보기</summary>

**정답: B) 프록시 통과 횟수 감소(개선)와 네트워크 경유 추가(악화)가 같은 크기 대에서 경쟁하며, 어느 쪽이 이기는지가 환경에 따라 달라지기 때문이다**

**설명:**
두 요인이 수백 마이크로초에서 수 밀리초라는 같은 크기 대에서 경쟁합니다. 어느 쪽이 이기는지는 현재 Envoy sidecar의 노드 CPU 소비량, 요청 길이(고정 오버헤드의 상대적 비중), keepalive 사용 여부, IAM Auth 활성화 여부, AZ를 넘는 비율에 달려 있고 이 값들은 조직마다 다릅니다. 그래서 결론은 "측정하라"이며, 부호가 환경에 따라 바뀔 수 있습니다.
</details>

2. p50과 p99의 요인 구성이 다르다는 것은 무엇을 의미하는가?
   - A) p99는 항상 p50보다 나쁘므로 p50만 보면 된다
   - B) p50은 경로 추가(악화)가 우세할 가능성이 높고, p99는 Envoy CPU 경합 해소(개선)가 우세할 가능성이 있어 평균 하나로 판단하면 구조를 놓친다
   - C) p50과 p99는 같은 요인의 영향을 받으므로 하나만 측정하면 된다
   - D) p99는 노이즈이므로 무시해야 한다

<details>

<summary>정답 보기</summary>

**정답: B) p50은 경로 추가(악화)가 우세할 가능성이 높고, p99는 Envoy CPU 경합 해소(개선)가 우세할 가능성이 있어 평균 하나로 판단하면 구조를 놓친다**

**설명:**
Envoy sidecar의 CPU 경합은 평균에는 잘 나타나지 않고 꼬리에 크게 나타납니다. 대부분의 요청은 즉시 스케줄되지만 일부가 수 밀리초에서 수십 밀리초를 기다립니다. sidecar를 제거하면 이 경합이 사라져 노드 CPU가 빡빡한 클러스터에서는 p99가 개선될 수 있습니다. 반면 VPC 경유 추가는 p50에도 그대로 반영됩니다. 따라서 두 백분위를 함께 측정해야 전환의 실제 영향을 파악할 수 있습니다.
</details>

3. 레이턴시 관점에서 "프록시 홉 하나보다 큰 영향을 줄 수 있다"고 언급된 클라이언트 설정은?
   - A) DNS 캐시 TTL
   - B) keepalive와 connection pool 설정
   - C) 로그 레벨
   - D) 요청 타임아웃 값

<details>

<summary>정답 보기</summary>

**정답: B) keepalive와 connection pool 설정**

**설명:**
Pod 네트워크 실측 벤치마크에서 keepalive를 끄면 p50이 같은 AZ 0.461 → 1.079 ms, 다른 AZ 0.704 → 1.517 ms로 두 배 넘게 늘었습니다. 새 커넥션은 요청마다 RTT와 TLS handshake를 추가로 발생시킵니다. AS-IS에서는 Envoy가 대신 연결을 관리해주었으나 그 구조가 사라지면서 애플리케이션의 HTTP 클라이언트 설정이 노출됩니다. 이것은 Lattice의 특성이 아니라 클라이언트 설정 문제입니다.
</details>

4. PoC 측정 매트릭스에서 `IAM Auth on`과 `IAM Auth off`의 차이가 알려주는 것은?
   - A) Cross-AZ 경유 비용
   - B) SigV4 서명·검증의 순수 비용
   - C) Envoy CPU 경합 해소 효과
   - D) 경로 변경의 순수 효과

<details>

<summary>정답 보기</summary>

**정답: B) SigV4 서명·검증의 순수 비용**

**설명:**
매트릭스는 요인을 분리하기 위해 설계됩니다. `IAM Auth on`과 `off`의 차이는 인증 도입만의 비용이고, `AS-IS(App Mesh)`와 `IAM Auth off`의 차이는 경로 변경만의 효과입니다. 이 두 값을 분리해서 얻는 것이 매트릭스의 목적이며, 그래서 IAM Auth를 축으로 넣습니다. 참고로 SigV4의 실질 비용은 암호 연산 자체보다 credential 갱신이 요청 경로를 블로킹할 때 p99 꼬리에 나타나는 부분일 수 있습니다.
</details>

5. Cross-AZ에 대한 설명으로 올바른 것은?
   - A) 레이턴시 악화 요인이면서 동시에 별도의 추가 과금 요인이다
   - B) 레이턴시 악화 요인이지만, Lattice 경유 트래픽에는 별도의 inter-AZ 요금이 없고 data processing 요금에 포함된다
   - C) 레이턴시와 과금 모두에 영향이 없다
   - D) Lattice는 항상 호출자와 같은 AZ의 Target을 선택하므로 고려할 필요가 없다

<details>

<summary>정답 보기</summary>

**정답: B) 레이턴시 악화 요인이지만, Lattice 경유 트래픽에는 별도의 inter-AZ 요금이 없고 data processing 요금에 포함된다**

**설명:**
Cross-AZ는 물리적 거리로 인해 레이턴시를 늘리지만(실측 기준선: 같은 AZ 0.339 ms vs 다른 AZ 0.544 ms), 과금 측면에서는 Lattice가 별도의 inter-AZ 요금을 청구하지 않고 data processing 요금에 포함시킵니다. D는 틀렸습니다 — Lattice의 Target 선택이 호출자 AZ를 고려하는지는 공식 문서로 확인되지 않았으므로 PoC에서 실측해야 하며, 그래서 측정 매트릭스에 AZ 축이 있습니다.
</details>

6. PoC 측정 설계에서 웜업이 필요한 이유와, 그럼에도 첫 요청 지연을 따로 기록해야 하는 이유는?
   - A) 웜업은 불필요하며 첫 요청만 측정하면 된다
   - B) 웜업 없이 측정하면 credential 획득과 연결 수립 비용이 섞여 정상 상태를 대표하지 못하지만, 콜드 스타트가 잦은 워크로드에서는 첫 요청 값이 오히려 중요하기 때문이다
   - C) 웜업은 p50만 개선하고 p99에는 영향이 없기 때문이다
   - D) 첫 요청은 항상 실패하기 때문이다

<details>

<summary>정답 보기</summary>

**정답: B) 웜업 없이 측정하면 credential 획득과 연결 수립 비용이 섞여 정상 상태를 대표하지 못하지만, 콜드 스타트가 잦은 워크로드에서는 첫 요청 값이 오히려 중요하기 때문이다**

**설명:**
첫 요청은 STS 호출과 TLS handshake를 모두 포함하므로 정상 상태의 대표값이 아닙니다. 따라서 충분히 웜업한 뒤의 값을 정상 상태 측정치로 써야 합니다. 다만 Lambda나 스케일 아웃이 빈번한 서비스처럼 콜드 스타트가 잦은 워크로드에서는 사용자가 실제로 경험하는 지연이 첫 요청 값에 가깝기 때문에, 이를 별도 항목으로 기록해 함께 평가해야 합니다.
</details>

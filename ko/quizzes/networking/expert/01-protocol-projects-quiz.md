# 프로토콜 프로젝트 퀴즈

> **마지막 업데이트**: 2026년 9월 15일

[프로토콜 프로젝트](../../../networking/expert/01-protocol-projects.md)를 먼저 읽으세요.
문항마다 가장 적절한 답 하나를 선택하고 어떤 추가 증거가 결론을 바꿀지 설명합니다.

1. 2026년 9월 15일의 접근 확인 결과에 맞는 학습 계획은?
   - A) 구성 중인 CS168 Fall 2026 사이트를 완성된 고정 과제 일정으로 취급한다.
   - B) 공식 Summer 2026 아카이브를 사용하고 학기를 기록하며 과제 접근 조건을 별도로 확인한다.
   - C) 이 워크북 완료에 무료 최신 CS144 채점기 사용을 요구한다.
   - D) 모든 실습을 위해 게스트 Python을 3.7로 바꾼다.

<details>
<summary>정답 보기</summary>

**정답: B**

**설명:** Summer 아카이브는 접근 가능하지만 Fall 사이트는 구성 중입니다. 명세 공개가 학교 채점기 접근을 보장하지는 않습니다. CS144는 선택 사항이며 과거 진입 주소는 404를 반환했습니다. 아카이브의 Python 테스트 기록은 그 과제 환경에 관한 것이지 Python 3.9 이상인 이 워크북의 게스트 요구사항이 아닙니다.

</details>

2. UDP 프로브는 `192.0.2.10:41000 → 198.51.100.20:33452`입니다. ICMP Time Exceeded 응답은 같은 포트이지만 목적지 `198.51.100.99`를 인용합니다. 원장은 어떻게 처리해야 하나요?
   - A) 두 포트가 같으므로 대응시킨다.
   - B) 바깥쪽 라우터 주소가 그럴듯하면 대응시킨다.
   - C) 해당 프로브와 무관하다고 표시하고 다른 목적지를 보존한다.
   - D) 응답에 맞게 송신 원장을 고친다.

<details>
<summary>정답 보기</summary>

**정답: C**

**설명:** 대응에는 인용된 원래 패킷의 주소와 프로토콜도 사용합니다. 포트가 같아도 목적지가 다르면 해당 프로브를 충족하지 못합니다. 바깥쪽 발신자는 오류 송신자이지 원래 프로브의 식별자가 아닙니다. 기록은 보존하되 예상 응답을 충족한 것으로 처리하지 않습니다.

</details>

3. TTL-2 프로브와 대응하는 응답은 없지만 TTL-3 UDP 프로브에는 목적지의 Port Unreachable이 대응합니다. 적절한 결론은?
   - A) 두 번째 라우터가 모든 애플리케이션 트래픽을 버린다.
   - B) TTL-3 프로브의 목적지 도착은 뒷받침되며 TTL-2는 미관측이다.
   - C) 누락된 라우터의 RTT는 0이다.
   - D) TTL-1 중복 응답으로 빠진 홉을 채울 수 있다.

<details>
<summary>정답 보기</summary>

**정답: B**

**설명:** 마감 내 응답 부재는 관측 한계입니다. 필터, 응답 속도 제한, 반환 경로 동작이 중간 응답을 숨길 수 있습니다. 뒤의 목적지 증거가 중간 라우터를 식별하거나 고정된 애플리케이션 경로를 증명하지는 않습니다. 중복 응답은 그대로 중복입니다.

</details>

4. 길이 필드가 2바이트인 자신의 프로토콜에 같은 완전한 입력이 네 가지 `recv()` 분할로 도착합니다. 필수 결과는?
   - A) `recv()`마다 애플리케이션 레코드 하나를 만든다.
   - B) 완전한 모든 분할에서 같은 논리 레코드가 나온다.
   - C) 길이 필드가 나뉘면 즉시 연결을 끝내야 한다.
   - D) 본문 중간 EOF를 본문 완료로 처리한다.

<details>
<summary>정답 보기</summary>

**정답: B**

**설명:** TCP는 메시지 경계가 아닌 바이트 스트림을 제공합니다. 해석기는 부분 헤더·본문을 보존하고 완전한 레코드를 일관되게 출력해야 합니다. 본문 중간 EOF는 잘림 실패이며 상한 초과 길이는 무제한 할당 전에 거절합니다. 이는 대학 과제 해답이 아니라 독립 연습 프로토콜의 속성입니다.

</details>

5. 광고 수신 윈도는 크지만 송신자의 혼잡 윈도는 작습니다. 송신이 느릴 수 있는 이유는?
   - A) 수신 여유가 크면 송신 제한이 모두 사라진다.
   - B) 혼잡 제어는 수신 흐름 제어와 별도로 전송 중인 데이터를 제한할 수 있다.
   - C) 수신 윈도와 혼잡 윈도는 같은 필드의 두 이름이다.
   - D) CS168 Project 3에 이를 판단할 모든 혼잡 제어기가 구현되어 있다.

<details>
<summary>정답 보기</summary>

**정답: B**

**설명:** 수신 흐름 제어는 수신 측을 보호하고 혼잡 제어는 경로 부하를 제한합니다. 이미 전송 중인 바이트, 페이싱, 애플리케이션이 준비한 데이터도 영향을 줍니다. 아카이브의 CS168 Project 3은 혼잡 제어를 명시적으로 제외하므로 과제 완료만으로 운영용 제어기를 검증할 수 없습니다.

</details>

6. 연결의 SYN 시퀀스 번호가 1000이고 데이터 6바이트가 1001부터 시작합니다. 누락 없이 받았을 때 다음 바이트를 나타내는 ACK는?
   - A) 1006
   - B) 1007
   - C) 순수 ACK도 한 위치를 소비하므로 1008
   - D) 세그먼트 수로 결정한다

<details>
<summary>정답 보기</summary>

**정답: B**

**설명:** SYN은 시퀀스 위치 하나를 소비합니다. 데이터는 1001부터 1006까지 차지하므로 다음 예상 바이트는 1007입니다. 순수 ACK는 시퀀스 공간을 소비하지 않으며 FIN이 있다면 한 위치를 추가 소비합니다. 캡처가 패킷을 묶는 방식이 아니라 스트림 바이트로 계산합니다.

</details>

7. `--fail` 없이 실행한 `curl`이 성공 종료하면서 `/missing`의 HTTP 404를 표시했습니다. 확인한 것은?
   - A) HTTP 서버에 도달하지 못했다.
   - B) 요청한 리소스가 존재한다.
   - C) HTTP 통신이 완료되었으며 리소스 조회 결과는 실패다.
   - D) TCP 체크섬이 반드시 틀렸다.

<details>
<summary>정답 보기</summary>

**정답: C**

**설명:** 전송·도구 성공과 애플리케이션 상태는 별개입니다. 없는 경로는 정상 HTTP 연결로 전달되는 의도한 애플리케이션 실패입니다. 종료 코드 0만 보지 말고 상태와 본문을 확인합니다. `--fail`을 추가하면 HTTP 오류 상태에 대한 curl의 처리가 바뀌며 서버 결과 자체가 바뀌지는 않습니다.

</details>

8. HTTP/3라는 주장을 가장 잘 뒷받침하는 증거는?
   - A) 목적지 포트가 443인 임의 UDP 패킷
   - B) 폴백·지원 여부와 관계없이 `--http3`가 포함된 명령
   - C) 클라이언트 기능 기록과 종단에서 확인한 QUIC·HTTP/3 협상 증거
   - D) 루프백 실습 서버의 HTTP/1.1 출력

<details>
<summary>정답 보기</summary>

**정답: C**

**설명:** 포트와 요청한 모드만으로 협상 결과를 증명할 수 없습니다. `--http3`는 폴백할 수 있고 `--http3-only`는 동작이 다르며 둘 다 지원 빌드가 필요합니다. QUIC은 UDP 위에 스트림을 제공하고 HTTP/3는 그 위에 HTTP를 대응시킵니다. 독립 스트림이 TCP의 스트림 간 전달 지연을 피하더라도 공유 혼잡 제어는 남습니다.

</details>

9. ICMP 원장을 IPv6로 확장할 때 필요한 변화는?
   - A) TTL 이름만 바꾸고 헤더 오프셋·ICMP 유형은 그대로 둔다.
   - B) Hop Limit, IPv6 확장 헤더·ICMPv6 유형을 고려하고 주소 계열·범위를 기록한다.
   - C) 라우터가 전달 IPv6 패킷을 단편화한다고 기대한다.
   - D) AAAA 응답을 게스트의 IPv6 경로 존재 증거로 취급한다.

<details>
<summary>정답 보기</summary>

**정답: B**

**설명:** IPv6 해석과 ICMPv6 오류 유형은 다릅니다. 라우터는 전달 패킷을 단편화하지 않으며 Packet Too Big은 Time Exceeded와 다른 진단을 뒷받침합니다. AAAA는 이름 결과이지 사용 가능한 라우팅이 아닙니다. IPv6 이웃 탐색도 ARP와 다릅니다.

</details>

10. 연결 종료를 보기 전에 캡처가 20초 마감에 도달했습니다. 올바른 완료 기록은?
   - A) 서버가 연결을 닫지 못한다고 선언한다.
   - B) timeout 상태를 숨기고 없는 FIN을 추정해 넣는다.
   - C) 타이머 결과와 부분 수집을 기록하고 자신의 도우미를 종료한 뒤 수신 대기를 확인한다.
   - D) TCP 사용 프로세스를 전부 종료하고 무제한 재캡처한다.

<details>
<summary>정답 보기</summary>

**정답: C**

**설명:** 캡처 마감은 수집 경계입니다. 종료 상태와 캡처 카운터를 보존하고 종료 동작을 실패가 아닌 미관측으로 표시합니다. 소유한 포그라운드 도우미만 종료하거나 타이머 만료 후 수신 대기 필터를 확인합니다. 권한 제약으로 오프라인 분석만 했다면 그 사실도 유지해야 합니다.

</details>

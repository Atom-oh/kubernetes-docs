# ClickHouse on EKS 실측 벤치마크 퀴즈

1. 벤치마크에서 1시간 창의 `namespace + timestamp` 범위 카운트(Q1)가 1억 행 테이블에서 4ms 만에 끝난 핵심 이유는 무엇인가요?
   - A) 결과가 이미 쿼리 캐시에 저장되어 있었기 때문에
   - B) PARTITION BY(일)와 ORDER BY(namespace, timestamp)의 프루닝으로 1억 행 중 16,385행만 읽었기 때문에
   - C) gp3 볼륨의 3,000 IOPS가 충분히 높았기 때문에
   - D) LowCardinality 타입이 비교 연산을 벡터화했기 때문에
<details>
<summary>정답 보기</summary>

**정답: B) PARTITION BY(일)와 ORDER BY(namespace, timestamp)의 프루닝으로 1억 행 중 16,385행만 읽었기 때문에**

**설명:**
쿼리 조건이 파티션 키(일 단위)와 정렬 키(namespace, timestamp)에 정확히 겹치면 ClickHouse는 primary index로 granule 단위 프루닝을 수행합니다. 이 벤치마크에서는 1억 행 중 granule 두 개(16,385행, 0.016%)만 읽었습니다. ClickHouse 성능의 대부분은 이런 "읽지 않는 설계"에서 나옵니다.

</details>

2. 컬럼별 압축 결과에서 trace_id는 1.0×(압축 불가), namespace는 약 201×로 나타났습니다. 이 차이를 만든 원인으로 옳은 것은?
   - A) trace_id 컬럼에만 압축 코덱이 지정되지 않았기 때문에
   - B) namespace가 문자열 길이가 더 짧기 때문에
   - C) trace_id는 고엔트로피(32자 hex 난수)라 압축 여지가 없고, namespace는 카디널리티가 낮은 데다 ORDER BY 첫 키라 같은 값이 길게 이어지기 때문에
   - D) namespace만 사전(dictionary) 파일이 별도로 생성되기 때문에
<details>
<summary>정답 보기</summary>

**정답: C) trace_id는 고엔트로피(32자 hex 난수)라 압축 여지가 없고, namespace는 카디널리티가 낮은 데다 ORDER BY 첫 키라 같은 값이 길게 이어지기 때문에**

**설명:**
난수 기반 ID는 정보 엔트로피가 높아 어떤 범용 압축기로도 줄지 않습니다(3.08 GiB → 3.07 GiB). 반면 namespace는 값이 10종뿐인 LowCardinality 컬럼이며 정렬 첫 키라서 동일 값이 연속 블록으로 저장되어 96 MiB가 0.5 MiB로 줄었습니다. 로그 스키마에서 "ID를 어떻게 저장할 것인가"가 저장 비용의 최대 변수인 이유입니다.

</details>

3. LZ4(기본)와 ZSTD(3)의 실측 비교 결과로 옳은 것은?
   - A) ZSTD(3)가 저장 공간과 스캔 속도 모두 우수했다
   - B) 저장 공간은 ZSTD(3)가 47% 작았지만, CPU-bound 풀스캔은 LZ4보다 약 1.9배 느렸다
   - C) 두 코덱의 저장 공간 차이는 5% 이내였다
   - D) LZ4가 저장 공간은 작았지만 스캔이 더 느렸다
<details>
<summary>정답 보기</summary>

**정답: B) 저장 공간은 ZSTD(3)가 47% 작았지만, CPU-bound 풀스캔은 LZ4보다 약 1.9배 느렸다**

**설명:**
실측에서 LZ4는 7.82 GiB(1.97×), ZSTD(3)는 4.16 GiB(3.7×)로 저장이 47% 절감됐지만, `LIKE '%timeout%'` warm 풀스캔은 2.63초 → 4.9초로 느려졌습니다. 그래서 로그 워크로드의 정석은 "최근 파티션은 LZ4, 오래된 파티션은 TTL로 ZSTD 재압축"입니다.

</details>

4. `LIKE '%timeout%'` 풀스캔(Q3)이 페이지 캐시를 우회한 디스크 직행에서 31.5초 걸렸습니다. 이 수치가 말해주는 병목은 무엇인가요?
   - A) ClickHouse의 문자열 검색 알고리즘이 비효율적이다
   - B) message 컬럼 압축본 약 4 GiB ÷ 31.5초 ≈ 130 MiB/s로, gp3 베이스라인 처리량(125 MiB/s)에 막힌 것이다
   - C) m5.xlarge의 4 vCPU가 포화된 것이다
   - D) EBS CSI 드라이버의 오버헤드가 지배적이다
<details>
<summary>정답 보기</summary>

**정답: B) message 컬럼 압축본 약 4 GiB ÷ 31.5초 ≈ 130 MiB/s로, gp3 베이스라인 처리량(125 MiB/s)에 막힌 것이다**

**설명:**
같은 쿼리가 페이지 캐시에서는 2.63초(CPU-bound, 초당 약 3,800만 행)로 끝났습니다. 디스크 직행에서 12배 느려진 것은 데이터베이스가 아니라 볼륨 처리량 설정의 문제라는 실측 증거입니다. gp3는 추가 비용으로 처리량을 최대 1,000 MiB/s까지 올릴 수 있습니다.

</details>

5. trace_id 점 조회(Q5)에 bloom filter skip index를 추가했을 때의 실측 변화로 옳은 것은?
   - A) 조회 시간 1.13초 → 0.036초(31배), 읽은 행 1억 → 108만(98.9% 스킵), 인덱스 크기는 테이블의 약 1.5%
   - B) 조회 시간은 그대로였지만 메모리 사용량만 줄었다
   - C) 조회 시간이 절반이 되었고 인덱스가 테이블 크기의 30%를 차지했다
   - D) ORDER BY 키를 바꾼 것과 동일한 효과로, 저장 공간도 함께 줄었다
<details>
<summary>정답 보기</summary>

**정답: A) 조회 시간 1.13초 → 0.036초(31배), 읽은 행 1억 → 108만(98.9% 스킵), 인덱스 크기는 테이블의 약 1.5%**

**설명:**
`bloom_filter(0.01) GRANULARITY 4` skip index는 각 granule 묶음에 대해 "이 값이 없다"를 확률적으로 보장해 대부분의 granule을 건너뜁니다. 실측에서 읽은 데이터가 3.82 GiB → 42.6 MiB로 줄었고, 인덱스 자체는 119.7 MiB(테이블의 1.5%), 기존 데이터 적용(MATERIALIZE)은 약 20초였습니다.

</details>

6. 이 벤치마크의 ingest 수치(초당 약 94만 행)를 해석할 때 반드시 붙여야 하는 단서는 무엇인가요?
   - A) 복제본 3개 구성에서 측정한 값이라는 것
   - B) 서버 내부 INSERT…SELECT로 측정했으므로 네트워크 전송과 텍스트 파싱 비용이 빠진 상한선이라는 것
   - C) 메모리에만 쓰고 디스크에는 기록하지 않았다는 것
   - D) 압축을 끄고 측정한 값이라는 것
<details>
<summary>정답 보기</summary>

**정답: B) 서버 내부 INSERT…SELECT로 측정했으므로 네트워크 전송과 텍스트 파싱 비용이 빠진 상한선이라는 것**

**설명:**
데이터를 서버 안에서 생성해 바로 삽입했기 때문에 실제 외부 클라이언트가 TSV/Native로 밀어넣는 경로보다 유리한 조건입니다. 디스크 기록·정렬·압축은 모두 포함된 값이지만, 외부 ingest 처리량의 상한으로 읽어야 합니다.

</details>

7. Q4(namespace별 duration p50/p99)는 1억 행 전체를 스캔하는데도 warm 기준 약 1초에 끝났습니다. 어떤 특성 덕분인가요?
   - A) 쿼리 결과가 머티리얼라이즈드 뷰에 미리 계산되어 있었기 때문에
   - B) 컬럼 지향 저장이라 duration_ms(289 MiB)와 namespace(0.5 MiB) 두 컬럼만 읽고, 테이블 전체 7.8 GiB는 읽지 않기 때문에
   - C) quantile 함수가 표본 추출(sampling)을 사용하기 때문에
   - D) 파티션 프루닝으로 하루치 데이터만 읽었기 때문에
<details>
<summary>정답 보기</summary>

**정답: B) 컬럼 지향 저장이라 duration_ms(289 MiB)와 namespace(0.5 MiB) 두 컬럼만 읽고, 테이블 전체 7.8 GiB는 읽지 않기 때문에**

**설명:**
행 지향 데이터베이스라면 전체 행을 읽어야 하는 쿼리지만, 컬럼 지향에서는 집계에 필요한 컬럼만 읽습니다. 전 기간 스캔(1억 행)이어서 파티션 프루닝은 없었고(D 오답), quantile은 실제 값 기반으로 계산됐습니다.

</details>

8. 이 가이드북의 판단 기준에 따를 때, ClickHouse를 관리형 서비스가 아니라 EKS에 self-hosted로 운영하는 선택이 특히 설득력을 갖는 경우는?
   - A) 전담 플랫폼 팀이 없고 데이터베이스 운영 경험이 전무할 때
   - B) 표준 관리형 서비스가 충분하고 테넌트가 하나뿐일 때
   - C) 관리형 제공이 제한적이거나 비용 배수가 크고, 플랫폼 팀이 Operator 기반 운영(백업·복구 리허설 포함)을 감당할 수 있을 때
   - D) 데이터가 100 GiB 미만으로 작을 때
<details>
<summary>정답 보기</summary>

**정답: C) 관리형 제공이 제한적이거나 비용 배수가 크고, 플랫폼 팀이 Operator 기반 운영(백업·복구 리허설 포함)을 감당할 수 있을 때**

**설명:**
ClickHouse는 관리형(ClickHouse Cloud) 대비 self-hosted 채택률이 특히 높은 데이터베이스입니다. 다만 전제는 성숙한 Operator(Altinity)와 이를 운영할 팀입니다. 반대로 운영 인력이 부족하거나 관리형으로 충분하면 관리형이 정답입니다 — "StatefulSet 직접 운영"은 애초에 선택지가 아닙니다.

</details>

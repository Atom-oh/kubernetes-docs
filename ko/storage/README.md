## 스토리지 스택 한눈에 보기

파드가 볼륨에 쓰기까지의 경로를 이해하면 성능 문제를 어느 계층에서 찾아야 할지 보입니다:

```text
애플리케이션 write()
  → 컨테이너 파일시스템 (ext4/xfs)
    → 커널 블록 레이어 (io scheduler, page cache 여부)
      → EBS 볼륨 (볼륨 타입별 IOPS/처리량 한도)
        → EC2 인스턴스의 EBS 대역폭 한도  ← 자주 잊는 병목
```

볼륨 자체의 한도와 **인스턴스 레벨의 EBS 대역폭/IOPS 한도**는 별개입니다. 예를 들어 m5.xlarge는 베이스라인 약 6,000 IOPS이므로, gp3 볼륨 3개를 각 3,000 IOPS로 붙이면 볼륨 스펙과 무관하게 인스턴스에서 먼저 병목이 걸립니다.

## AWS 스토리지 선택 가이드

| 서비스 | 액세스 모드 | 특성 | 적합한 워크로드 |
|--------|------------|------|----------------|
| **EBS (gp3/io2)** | RWO (단일 노드) | 블록, ~수백 µs 레이턴시 | 데이터베이스, 단일 파드 상태 저장 |
| **EFS** | RWX (다중 노드) | NFS, ms급 레이턴시, 탄력적 용량(사전 프로비저닝 불필요) | 공유 설정/콘텐츠, ML 학습 데이터 공유 |
| **FSx for Lustre** | RWX | 병렬 파일시스템, 고처리량 | HPC, 대규모 ML 학습 |
| **S3 (Mountpoint CSI)** | RWX (읽기 중심) | 객체, 높은 처리량/높은 레이턴시 | 데이터 레이크, 모델/아티팩트 저장 |
| **인스턴스 스토어** | 노드 로컬 | NVMe, 최저 레이턴시, **비영속** | 캐시, 셔플 데이터, 임시 스크래치 |

## 왜 실측이 필요한가

스토리지는 스펙 시트와 실제 체감이 가장 크게 벌어지는 영역입니다. 대표적인 함정:

1. **gp2의 버스트 크레딧** — 새 볼륨은 잠시 3,000 IOPS로 동작하다가 크레딧이 마르면 기본 성능(3 IOPS/GiB)으로 추락합니다. 부하 테스트를 30분 이내로 끝냈다면 절벽을 못 본 채 통과한 것입니다.
2. **볼륨 한도 vs 인스턴스 한도** — 위 스택 다이어그램 참고.
3. **iodepth(동시성)에 따라 다른 결론** — 큐 깊이 1의 레이턴시 측정과 큐 깊이 32의 IOPS 측정은 전혀 다른 특성을 보여줍니다.

[EBS gp2 vs gp3 실측 벤치마크](./01-ebs-gp2-gp3-benchmark.md)에서 이 함정들을 fio로 직접 확인합니다.

# 09. エッジセキュリティ：WAF と DDoS 防御クイズ

> **最終更新日**: 2026年11月19日

[ワークブック](../../../networking/expert/09-edge-security-waf-ddos.md)に戻ってください。
各質問につき回答を1つ選び、ワークブックのどのルールが根拠になるか説明してください。
これらは設計上の推論を行う演習であり、Web ACL がデプロイされたことを示すものではありません。

1. ボットネットが、VPC origin 経由で内部 ALB に接続されている CloudFront ディストリビューションに SYN flood を仕掛けています。なぜ ALB は SYN flood を受けないのでしょうか？
   - A) エッジでは、Shield TCP SYN プロキシがサービスに接続が到達する前にハンドシェイクを検証し（ステートレスな SYN cookie）、CloudFront はオリジンへの独自の永続的な接続を維持する。
   - B) WAF Web ACL がレートベースのルールで SYN パケットをブロックする。
   - C) ALB のセキュリティグループが、短時間に大量に到着する SYN パケットを破棄する。

<details>
<summary>回答を表示</summary>

**回答: A) エッジでは、Shield TCP SYN プロキシがサービスに接続が到達する前にハンドシェイクを検証し（ステートレスな SYN cookie）、CloudFront はオリジンへの独自の永続的な接続を維持する。**

**説明:** SYN flood は、リスナーのハーフオープン接続用バックログを使い果たします。この場合のリスナーは CloudFront であり、Shield の SYN プロキシはハンドシェイクを完了した接続のみを通過させます。ビューワーからの新しい接続は、新しいオリジン接続ではありません。AWS WAF が検査するのは HTTP リクエストであり、TCP セグメントではありません。また、セキュリティグループはレートリミッターではありません。

</details>

2. UDP リフレクション攻撃を行うには攻撃者に何が必要で、どのネットワーク対策によってそれを取り除けますか？
   - A) リフレクターとの TCP ハンドシェイクの完了。どこでも TLS を使えば取り除ける。
   - B) 被害者のアドレスを送信元として偽装する能力。送信元アドレス検証（BCP 38）によって取り除ける。
   - C) 有効な HTTP リクエスト。WAF のレートベースのルールによって取り除ける。

<details>
<summary>回答を表示</summary>

**回答: B) 被害者のアドレスを送信元として偽装する能力。送信元アドレス検証（BCP 38）によって取り除ける。**

**説明:** 攻撃者は、被害者のアドレスを送信元として指定した小さな UDP リクエスト（DNS、NTP、SSDP、CLDAP、Memcached など）を送信します。するとリフレクターは、はるかに大きな応答を被害者に送信します。DNS の場合、AWS のホワイトペーパーでは増幅率が28～54倍とされています。送信元アドレスを検証するネットワークであれば、このアドレス偽装を防げます。

</details>

3. リクエストが CAPTCHA アクションのルールに一致し、有効期限内の有効な CAPTCHA トークンを含んでいます。AWS WAF はどうしますか？
   - A) リクエストをブロックし、新しいパズルを送信する。
   - B) リクエストを直ちに許可し、評価を終了する。
   - C) Count と同様にリクエストを処理し、残りのルールの評価を続ける。

<details>
<summary>回答を表示</summary>

**回答: C) Count と同様にリクエストを処理し、残りのルールの評価を続ける。**

**説明:** 有効期限内の有効なトークンがある場合、CAPTCHA と Challenge は非終端処理となります。トークンがない、無効、または期限切れの場合は終端処理（パズルまたはサイレントチャレンジを伴うブロック）となります。Allow と Block は常に評価を終了し、Count は終了しません。ブロックされたリクエストのデフォルトの応答は `403 (Forbidden)` です。

</details>

4. 次のうち、**無効な**レートベースのルール設定はどれですか？
   - A) 評価ウィンドウ300秒、上限100、アクションBlock。
   - B) 評価ウィンドウ600秒、上限10、アクションCount。
   - C) 評価ウィンドウ300秒、上限100、アクションAllow。

<details>
<summary>回答を表示</summary>

**回答: C) 評価ウィンドウ300秒、上限100、アクションAllow。**

**説明:** レートベースのルールでは、Allow 以外の任意のルールアクションを使えます。評価ウィンドウは60、120、300、600秒（デフォルトは300秒）で、設定できる最小の上限は10です。そのため、A と B はどちらも有効です。

</details>

5. HTTP flood の発生中、エンジニアがすでにトラフィックをブロックしているレートベースのルールの上限を引き下げます。変更直後にチームが想定すべきことは何ですか？
   - A) 新しい上限が即時に適用され、これまでのカウントは保持される。
   - B) 変更によってルールのカウントがリセットされ、最大1分間、レート制限が一時停止することがある。
   - C) 次の評価ウィンドウが完全に経過するまで、ルールは無効のままになる。

<details>
<summary>回答を表示</summary>

**回答: B) 変更によってルールのカウントがリセットされ、最大1分間、レート制限が一時停止することがある。**

**説明:** 上限、評価ウィンドウ、集約、転送された IP の設定、またはスコープを変更すると、カウントがリセットされます。レート制限は概算でもあります。レートが上限を超えてから制限が始まるまでに数分かかることがあり、レートが下がった後も制限が短時間続く場合があります。レート制限の変更は、インシデント発生中ではなく、その前に計画してください。

</details>

6. `AWSManagedRulesCommonRuleSet` の各ルールが何をブロックするか、適用前に確認したい場合、どの設定を使えばよいですか？
   - A) ルールグループの返却アクションを Count にオーバーライドする。
   - B) Web ACL のデフォルトアクションを Count に設定する。
   - C) `RuleActionOverrides` を使って、各ルールのアクションを Count にオーバーライドする。

<details>
<summary>回答を表示</summary>

**回答: C) `RuleActionOverrides` を使って、各ルールのアクションを Count にオーバーライドする。**

**説明:** ルールごとにオーバーライドすると、一致したリクエストはそのルールのアクションが Count だった場合と同じように処理され、グループは他のルールの評価を続けます。ルールグループの返却アクションを Count にオーバーライドしても、グループ内の評価方法は変わりません。グループは最初に終端処理となる一致があった時点で停止するため、そのリクエストについてグループ内の後続ルールは実行されません。デフォルトアクションに指定できるのは Allow または Block のみです。

</details>

7. 優先度50のルール `block-bad-ua` は、`awswaf:managed:aws:core-rule-set:NoUserAgent_Header` に対するラベル一致ステートメントです。コアルールセットは優先度100にあり、そのルールは Count にオーバーライドされています。なぜ `block-bad-ua` は決して一致しないのでしょうか？
   - A) マネージドルールグループはラベルを追加しない。
   - B) ラベルを利用できるのは、それを追加したルールより後に評価されるルールだけであり、優先度50のルールは優先度100より先に実行される。
   - C) Count ルールによるラベルは破棄される。

<details>
<summary>回答を表示</summary>

**回答: B) ラベルを利用できるのは、それを追加したルールより後に評価されるルールだけであり、優先度50のルールは優先度100より先に実行される。**

**説明:** AWS WAF は数値の小さい優先度から順に評価します。ラベルは評価の残りの間リクエストに付与されたままとなり、その後に評価されるルールがラベル一致ステートメントで読み取ります。すべての AWS Managed Rules ルールグループはラベルを追加します。ルールを Count に設定してラベル付けのみを行うのが、主なラベル活用パターンです。ラベル一致ルールをグループより後に移動してください。

</details>

8. CloudFront ディストリビューションを保護するため、CLI で Web ACL を作成します。正しい説明はどれですか？
   - A) `--scope=CLOUDFRONT --region=us-east-1` を使う。このグローバル Web ACL は ALB にも関連付けることはできない。
   - B) オリジン ALB のリージョンで `--scope=REGIONAL` を使い、同じ Web ACL を ALB にも関連付ける。
   - C) CloudFront はグローバルなので、任意のリージョンで `--scope=CLOUDFRONT` を使う。

<details>
<summary>回答を表示</summary>

**回答: A) `--scope=CLOUDFRONT --region=us-east-1` を使う。このグローバル Web ACL は ALB にも関連付けることはできない。**

**説明:** CloudFront 用の Web ACL はグローバルで、リージョンは US East（N. Virginia）に固定されています。API と SDK は `us-east-1` エンドポイントを使います。CloudFront ディストリビューションに関連付けられた Web ACL は、別の種類のリソースには関連付けられません。そのため、2つ目の検査を行いたい場合、ALB には独自の `REGIONAL` Web ACL が必要です。

</details>

9. ある Web ACL は、`AWSManagedRulesCommonRuleSet`（700 WCU）、`AWSManagedRulesSQLiRuleSet`（200 WCU）、`AWSManagedRulesKnownBadInputsRuleSet`（200 WCU）、および容量500 WCUで作成され、現在は120 WCU相当のルールを含むカスタムルールグループを使用しています。結果はどうなりますか？
   - A) 1,220 WCU。基本料金の範囲内。
   - B) 1,600 WCU。上限は5,000なので許可されるが、基本料金に含まれる1,500 WCUを超えるため、追加料金がかかる。
   - C) Web ACL は1,500 WCUを超えられないため、拒否される。

<details>
<summary>回答を表示</summary>

**回答: B) 1,600 WCU。上限は5,000なので許可されるが、基本料金に含まれる1,500 WCUを超えるため、追加料金がかかる。**

**説明:** Web ACL でルールグループを使う場合に計上されるのは、現在の内容ではなく、作成時に設定された変更不可のグループ容量です。そのため、カスタムグループは500として計上されます。700 + 200 + 200 + 500 = 1,600 です。基本料金には1,500 WCUが含まれ、それを超える容量には段階的な追加料金がかかります。上限は5,000 WCUです。

</details>

   - A) 追加で必要なものはない。加入すれば利用できる。
   - B) すべての ALB にリージョナル Web ACL を設定する。
   - C) SRT の利用には Business Support または Enterprise Support プランが必要であり、保護対象リソースに対して Route 53 ヘルスチェックを使ったヘルスベースの検出を設定する。

<details>
<summary>回答を表示</summary>

**回答: C) SRT の利用には Business Support または Enterprise Support プランが必要であり、保護対象リソースに対して Route 53 ヘルスチェックを使ったヘルスベースの検出を設定する。**

**説明:** SRT の利用には、これらのいずれかのサポートプランが必要です。プロアクティブな対応が利用できるのは、Route 53 ヘルスチェックを使ったヘルスベースの検出を設定したリソースに限られます。また、Shield Advanced は明示的に追加したリソースのみを保護します。Shield Standard は自動で適用される無料の保護レイヤーです。

</details>

11. あるチームは、オリジンとしてパブリック ALB を提案しており、そのセキュリティグループでは CloudFront のオリジン向けマネージドプレフィックスリストからのアクセスを許可しています。このコースでは、なぜこの構成は内部 ALB への VPC origin よりも弱いと説明しているのでしょうか？
   - A) プレフィックスリストは、攻撃者が作成したものも含め、あらゆる CloudFront ディストリビューションからのアクセスを許可する。一方、内部 ALB にはインターネットからの経路がまったくない。
   - B) プレフィックスリストには CloudFront の IPv4 アドレスが含まれていない。
   - C) パブリック ALB は TLS を使えない。

<details>
<summary>回答を表示</summary>

**回答: A) プレフィックスリストは、攻撃者が作成したものも含め、あらゆる CloudFront ディストリビューションからのアクセスを許可する。一方、内部 ALB にはインターネットからの経路がまったくない。**

**説明:** エッジの制御が適用されるのは、自分のディストリビューションを経由したリクエストだけです。別のディストリビューションからのリクエストは、Web ACL とレートベースのルールを迂回します。シークレットヘッダーの追加が有効なのは、そのシークレットが秘密に保たれている間だけです。内部 ALB による隠蔽はルーティング上の特性です。そのため、後からセキュリティグループの制限を緩めても、オリジンがインターネットから到達可能になることはありません。

</details>

12. Count モードでの試行中、マネージドルールグループ内のルールが一致したはずだと確実に判断できる証拠はどれですか？
   - A) WAF ログの `nonTerminatingMatchingRules` フィールドとラベル、およびラベルメトリクス。
   - B) Web ACL ビューのサンプリングされたリクエストの表。
   - C) CloudFront 標準ログのステータスコード。

<details>
<summary>回答を表示</summary>

**回答: A) WAF ログの `nonTerminatingMatchingRules` フィールドとラベル、およびラベルメトリクス。**

**説明:** WAF ログには、Count による一致が `nonTerminatingMatchingRules` の下に記録され、各リクエストに追加されたラベルも記録されます。ルールグループ内の Count ルールについては、Web ACL ビューにサンプルが表示されません。また、ルールグループ内の Count アクションのルールは、Web ACL ディメンションメトリクスを出力しません。Count で一致しても、ステータスコードは変わりません。

</details>

13. 参照設計では、Pod の NetworkPolicy はクライアントアドレスではなく、ALB のサブネットを含む `ipBlock` からの ingress を許可しています。なぜでしょうか？
   - A) ALB はプロキシであり、Pod IP ターゲットが認識するのは ALB ノードのプライベートアドレスで、クライアントアドレスは `X-Forwarded-For` に含まれる。
   - B) NetworkPolicy では IPv4 CIDR ブロックを指定できない。
   - C) CloudFront がクライアントアドレスを VPC origin の ENI に書き換えるのは、HTTP/3 の場合だけである。

<details>
<summary>回答を表示</summary>

**回答: A) ALB はプロキシであり、Pod IP ターゲットが認識するのは ALB ノードのプライベートアドレスで、クライアントアドレスは `X-Forwarded-For` に含まれる。**

**説明:** ELB ガイドによると、サーバーアクセスログに含まれるのはロードバランサーのアドレスだけです。Kubernetes のドキュメントでは、書き換えが NetworkPolicy の処理前に起きるか後に起きるかは、プラグイン、クラウドプロバイダー、Service の実装によって異なると注意されています。そのため、使用している CNI で実際に観測される送信元を確認してください。

</details>

14. ワークブックの演習では、`rate-login`（ウィンドウ300秒、上限100、IPで集約、アクションCount）は、1時間静かな状態が続いた後、`198.51.100.20` から5分以内に `POST /login` リクエストが単発で640件送信されるのを検知します。このルールがそのアドレスからのリクエストをおよそ何件カウントするのか、また実際の件数が正確でない理由は何ですか？
   - A) 640件。スコープダウンステートメントに一致するリクエストはすべて Count がカウントするため。
   - B) およそ540件。上限を超えたリクエストであり、AWS WAF がレートを推定し、超過を遅れて検知するため概算となる。
   - C) 100件。上限がカウント数を制限するため。

<details>
<summary>回答を表示</summary>

**回答: B) およそ540件。上限を超えたリクエストであり、AWS WAF がレートを推定し、超過を遅れて検知するため概算となる。**

**説明:** レートベースのルールは、上限を超えたインスタンスからの、その後の一致リクエストにアクションを適用します。640 - 100 = 540 です。これは単発の急増の場合です。アドレスのレートが上限を超えたままなら、後続リクエストのほぼすべてがカウントされます。ルールは推定レートが上限を下回るまでアクションを適用し続けるためです。AWS WAF は直近のリクエストに重み付けをしているため、制限は設定値ちょうどではなく、その近辺で適用されます。この試行では誤検知（オフィスで共有されている NAT）が明らかになり、計画ではスコープダウン内の `NotStatement` に IP set を設定してこれを除外します。

</details>

完了条件：すべての回答について、ワークブックのルールを根拠に説明し、ルール計画に **検証用のシナリオであり、測定値ではない** と明記してください。

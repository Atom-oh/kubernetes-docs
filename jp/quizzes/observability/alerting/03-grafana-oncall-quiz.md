# Grafana OnCall クイズ

> **最終更新日**: 2026年9月13日

このクイズでは、アーカイブ済みの OnCall OSS 環境の見直しと移行を扱います。

Grafana OnCall についての理解を確認します。

**Cloud Connection は 2026-03-24 に終了しました。** Grafana IRM アプリ経由の OSS モバイルプッシュ通知と、Cloud Connection に依存する SMS/音声通知は、現在は機能しません。個別に設定した Twilio などの通知サービスは別の経路です。セルフホスト環境で使う電話/SMS の仕組みがすべて終了した、という意味ではありません。

---

1. Grafana OnCall の主要機能ではないものはどれですか？
   - A) オンコールスケジュールの管理
   - B) エスカレーションチェーンの設定
   - C) メトリクスの収集と保存
   - D) ChatOps との連携（Slack、Teams）

<details>
<summary>回答を表示</summary>

**回答: C) メトリクスの収集と保存**

**解説:**
OnCall はアラート、スケジュール、ルーティング、対応者のアクションを受信して管理しますが、メトリクスデータベースではありません。OSS は 2026-03-24 にアーカイブされました。既存環境で各チャネルや API が利用できるかどうかは、現在保守されている Cloud IRM とは分けて確認してください。

</details>

2. Grafana OnCall のエスカレーションポリシーで、`wait` タイプは何をしますか？
   - A) アラートを送信する前にデータ収集を待つ
   - B) 次のエスカレーションステップに進む前に待つ
   - C) ユーザーの応答を待ってから自動的に解決する
   - D) アラートのグループ化を待つ

<details>
<summary>回答を表示</summary>

**回答: B) 次のエスカレーションステップに進む前に待つ**

**解説:**
`wait` ステップは次のエスカレーションステップの実行を遅らせます。インシデントへの確認応答も解決も行いません。確認した公開シリアライザーでは、待機時間を秒単位で指定し、1分から24時間まで設定できます。チェーンやアラートグループの状態によって、実際に処理を止めるか再通知するかが変わります。

</details>

3. Grafana OnCall のオンコールスケジュールにおける「Override」とは何ですか？
   - A) スケジュールを完全に削除して作り直すこと
   - B) 既存スケジュールの特定期間だけ、対応者を一時的に変更すること
   - C) スケジュールのタイムゾーンを変更すること
   - D) ローテーション周期を変更すること

<details>
<summary>回答を表示</summary>

**回答: B) 既存スケジュールの特定期間だけ、対応者を一時的に変更すること**

**解説:**
Override（上書き）は指定した期間の担当体制を変更します。確認した API では `on_call_shifts` タイプとして扱われ、タイムゾーンの明示と対象スケジュールとの関連付けが必須です。既存のシフト ID、優先順位、担当の空白期間、最終的な対応者を確認してください。古いネスト形式の `overrides` エンドポイントが使えるとは限りません。

</details>

4. Grafana OnCall を Alertmanager と統合するとき、どの方法を使いますか？
   - A) Alertmanager が OnCall のメトリクスを直接収集する
   - B) Alertmanager の `webhook_configs` から OnCall にアラートを送る
   - C) OnCall が Alertmanager の API を定期的にポーリングする
   - D) 両システムでデータベースを共有する

<details>
<summary>回答を表示</summary>

**回答: B) Alertmanager の `webhook_configs` から OnCall にアラートを送る**

**解説:**
統合方式に応じて生成された URL を `webhook_configs` に設定します。適切な場合は、保護された `url_file` に保存してください。参照する receiver をすべて定義し、現行の matcher を使います。公開 API の raw-token 認証は webhook URL とは別の仕組みです。また、`send_resolved` を設定しても、OnCall が元のルールを更新するわけではありません。

</details>

5. Grafana OnCall でアラートをグループ化する主な目的は何ですか？
   - A) アラートを発生時刻順に並べる
   - B) 関連するアラートをまとめ、アラート疲れを軽減する
   - C) アラートを重要度別に分類する
   - D) 重複したアラートを自動削除する

<details>
<summary>回答を表示</summary>

**回答: B) 関連するアラートをまとめ、アラート疲れを軽減する**

**解説:**
グループ化により、対応者が重複して作業するのを減らせます。ただし、インシデントの範囲に合ったキーを使う必要があります。ラベルが少なすぎると無関係なインシデントが一つにまとまり、上限のない ID を使うとグループが細分化されます。Alertmanager 側の通知タイミングと、OnCall 側のグループ化・解決テンプレートは別の設定です。また、通知が厳密に一度だけ配信される保証はありません。

</details>

6. Grafana OnCall のエスカレーションポリシーで、`notify_on_call_from_schedule` の `important` フラグを true にすると何が起きますか？
   - A) アラートが最優先としてマークされる
   - B) ユーザーが設定した重要通知ルールのセットが選択される
   - C) エスカレーションチェーンを省略し、直ちに上司へアラートを送る
   - D) アラートが永続的に保存される

<details>
<summary>回答を表示</summary>

**回答: B) ユーザーが設定した重要通知ルールのセットが選択される**

**解説:**
`important` は、ユーザー個人の重要通知ルールを選択します。そのルールに設定された順序、待機時間、チャネル、利用可能性は引き続き適用されます。すべてのチャネルに自動送信するわけではなく、デフォルトのルールが常に Slack のみを使うわけでもありません。

</details>

7. 既存の OnCall 環境で Slack アクションを使う場合、適切な方法はどれですか？
   - A) どの環境でも `/oncall ack` が使えると仮定する
   - B) スラッシュコマンドを Bash コマンドとして扱う
   - C) インストール済みアプリのコマンド、権限、アクションボタンを確認する
   - D) 確認応答を行えば、元のモニターも解決すると仮定する

<details>
<summary>回答を表示</summary>

**回答: C) インストール済みアプリのコマンド、権限、アクションボタンを確認する**

**解説:**
インストール済み Slack アプリで実際に使われているルートコマンドやヘルプ、権限が付与されたアクションボタンを確認してください。確認したソースには、設定可能なルートコマンドと `/grafana` の例があり、従来の `/oncall` コマンド一覧を前提にはしていません。確認応答（Acknowledge）、解決（Resolve）、通知抑制（Silence）はそれぞれ別の操作です。デプロイ処理が自動的に実行されるわけでもありません。

</details>

8. 新しいオンコールツールの選定や移行は、何を根拠に判断すべきですか？
   - A) 過去の統合数だけで選ぶ
   - B) OSS には運用コストがないと仮定する
   - C) 保守状況、必要な機能、実際のコスト、移行・復旧方法を確認する
   - D) アーカイブ済みの OnCall OSS を標準として導入する

<details>
<summary>回答を表示</summary>

**回答: C) 保守状況、必要な機能、実際のコスト、移行・復旧方法を確認する**

**解説:**
現在の保守状況とライフサイクル、必要な機能、運用コスト、契約内容を確認してください。古い統合数やユーザー単価だけでは判断できません。OnCall OSS はアーカイブ済みです。Opsgenie は 2027年4月5日にサービスとサポートを終了すると発表しています。保守が続いている移行先を検討し、移行と復旧をテストしてください。

</details>

9. 既存の OnCall 環境で可用性を確保するには、何を確認する必要がありますか？
   - A) API レプリカが3つあれば可用性は保証される
   - B) 依存関係、状態、配信、障害時と復旧時の挙動
   - C) クラスター数だけ
   - D) 読み取り専用のデータベースレプリカだけ

<details>
<summary>回答を表示</summary>

**回答: B) 依存関係、状態、配信、障害時と復旧時の挙動**

**解説:**
レプリカ数だけでは、すべての障害点をなくせません。既存環境では、依存サービス、ブローカー、キャッシュ、データベース、スケジューラー、キー、TLS、通知の配信、復旧手順を検証してください。アーカイブ済みの OSS は、新しい本番環境に標準で選ぶものではありません。なお、このレビューでは HA 構成のデプロイ検証は行っていません。

</details>

10. Grafana OnCall でルートを設定する主な目的は何ですか？
    - A) ネットワークトラフィックを分散する
    - B) アラート条件に応じて異なるエスカレーションチェーンを適用する
    - C) データベースクエリを最適化する
    - D) ユーザー認証の経路を設定する

<details>
<summary>回答を表示</summary>

**回答: B) アラート条件に応じて異なるエスカレーションチェーンを適用する**

**解説:**
ルートは、統合から届く実際のペイロード、マッチング方式、評価順序、フォールバックに基づいて、エスカレーションや通知の動作を選択します。確認したシリアライザーでは、`slack.channel_id` と `enabled` が入れ子になっています。フィールドの欠落や競合をテストしてください。任意のメッセージ本文に対する正規表現マッチングが、すべてのプロバイダーで使えるとは限りません。

</details>

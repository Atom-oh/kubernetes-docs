# エンタープライズクラウドガバナンス概要クイズ

> このクイズでは、[エンタープライズクラウドガバナンス概要](../../governance/00-governance-overview.md)の理解度を確認します。

---

1. Account、VPC、EKS の境界を「個別に」判断するという中心的な考え方は何ですか？
   - A) チーム名に基づき、常に3つの境界をまとめて作成する
   - B) 異なる基準（セキュリティ/クォータ/所有権、ネットワーク/信頼ゾーン、ランタイムの障害範囲）に基づいて、それぞれの境界を個別に決定する
   - C) すべてのワークロードで、単一の共有 Account、VPC、クラスターを使用する
   - D) VPC の境界だけを決め、残りは自動的にそれに従わせる

<details>
<summary>回答を表示</summary>

**回答: B) 異なる基準（セキュリティ/クォータ/所有権、ネットワーク/信頼ゾーン、ランタイムの障害範囲）に基づいて、それぞれの境界を個別に決定する**

**解説:**
Account はセキュリティ/クォータ/コストの所有権/ライフサイクル、VPC はネットワークポリシーと信頼ゾーン、EKS はランタイムの障害範囲に基づいて判断します。ドメインと環境の組み合わせごとに3つの境界をまとめて作成する固定的な方式は単純ですが、根本的に異なる境界を1つのものとして扱います。

</details>

---

2. Pod Identity association のプライマリ IAM role はどこに存在する必要がありますか？
   - A) 任意の Account
   - B) クラスターと同じ Account
   - C) 管理 Account のみ
   - D) Region ごとに1つの Account

<details>
<summary>回答を表示</summary>

**回答: B) クラスターと同じ Account**

**解説:**
プライマリの association role はクラスターの Account に存在する必要があります。ターゲットロール機能はロールチェーンを使用し、サポート対象のリソースポリシーと IRSA は、その他のクロスアカウントアクセス経路を提供します。

</details>

---

3. 安定した Workload ID と変更可能なメタデータを区別するのはなぜですか？
   - A) AWS API 呼び出しのコストを削減するため
   - B) 組織再編やブランド統合などの定期的な変更が、そのままインフラストラクチャの移行につながらないようにするため
   - C) Kubernetes RBAC の設定を簡素化するため
   - D) すべてのワークロードを単一の Account に統合するため

<details>
<summary>回答を表示</summary>

**回答: B) 組織再編やブランド統合などの定期的な変更が、そのままインフラストラクチャの移行につながらないようにするため**

**解説:**
組織再編によってチームは頻繁に変わりますが、ドメイン（ビジネスケイパビリティ）は比較的安定しています。Account や VPC の境界をチーム名やブランド名に直接結び付けると、組織再編のたびに移行が必要になります。そのため、ドメイン、ブランド、チーム、CUJ などは、安定した Workload ID に変更可能なメタデータとして付与することを推奨します。

</details>

# 02. ルーティングポリシーと収束時間の測定

> **最終更新日**: 2026年9月15日
> **ラボの範囲**: 個別に準備し、所有権を持つ使い捨てのLinuxルーティングVMを1台使用します。FRRoutingコンテナはローカルでのみ実行します。
> **検証状況**: 上流ドキュメント、トポロジー、CLIの情報を確認しました。執筆中にルーティングラボは**実行していません**。

このワークブックを終えると、あるプレフィックスが選択された理由、そのネクストホップが使用可能であることの確認方法、制御した障害時にトラフィックが受けた影響の測定方法を説明できるようになります。
まず[初級編の8レッスン](../beginner/README.md)をすべて完了してください。[コンテナ／クラウドの総合演習](../beginner/08-container-cloud-capstone.md)も含まれます。
プロトコルのルーティングテーブルを見てもパケットの経路が分からない場合は、[Linuxのパケット転送](../../kernel/02-network-stack.md)を復習してください。

## 1. 問いを立てて読む

| 読む資料 | 自分の言葉で答える問い |
|---|---|
| [BGP Labsの概要](https://bgplabs.net/)と[FRRoutingの入門](https://bgplabs.net/basic/0-frrouting/) | Linuxシェルで行う操作と、`vtysh`で行う操作はそれぞれ何ですか。 |
| [Local Preferenceのラボ](https://bgplabs.net/policy/5-local-preference/) | 一方のエッジで設定した優先度が、もう一方のエッジにどう影響しますか。 |
| [FRR BGPマニュアル](https://docs.frrouting.org/en/latest/bgp.html) | 受信した経路は、いつ候補となり、選択・広告・インストールされますか。 |
| [FRR OSPFマニュアル](https://docs.frrouting.org/en/latest/ospfd.html) | 隣接関係が示すことは何ですか。また、IGPが運ぶプレフィックスはどれですか。 |
| [RFC 4271](https://www.rfc-editor.org/rfc/rfc4271.html)と[RFC 4456](https://www.rfc-editor.org/rfc/rfc4456.html) | 通常のiBGP広告ルールは、ルートリフレクションとどう異なりますか。 |

設定を始める前に、該当する節を読みます。ルーティングセッションとフォワーディングリンクを分けた図を作成してください。
BGPセッションはスピーカー間のTCP接続です。その接続を通じて広告されたすべての宛先に到達できる、という意味ではありません。

## 2. コントロールプレーンのモデルを作る

**IGPとBGPは異なる問題を解決します。** OSPFは管理ドメイン内でリンクステート情報を配布し、コストを使って経路を計算します。
このラボでは、iBGPで使用するループバックを含む内部到達性を提供します。
BGPは属性とポリシーを使って宛先への到達性を交換します。単純にOSPFを最短ホップで置き換えるものではありません。
両プロトコル間ですべての経路を無条件に再配布すると、余計な経路、ポリシーの曖昧さ、フィードバックループが生じるおそれがあります。

**eBGP**は通常、異なる自律システム間で経路を交換し、**iBGP**は同じAS内でBGP情報を配布します。
AS_PATHはASレベルのループ検出に役立ちます。また通常のiBGP広告制限により、内部での単純な再広告ループを防ぎます。
iBGPで学習した経路は、通常、別のiBGPピアには広告されません。フルメッシュ、ルートリフレクター、または意図的に設計した別の方式が必要です。
セッションの接続関係からフォワーディングのトポロジーを推測しないでください。

**ネクストホップの解決は、実際のフォワーディングに先立って必要です。** BGP経路が見えていても、そのネクストホップへの到達経路がなければ使用できません。
iBGPのネクストホップは、`next-hop-self`などで設計上変更しない限り、外部アドレスのままの場合があります。
実際に受信したNEXT_HOPを確認し、ルーティングテーブルをたどってインターフェースと隣接先まで再帰的に解決してください。
OSPFの隣接関係が確立しているだけでは、必要なネクストホップのプレフィックスが広告された証拠になりません。

| レイヤー | 確認できること | それだけでは確認できないこと |
|---|---|---|
| BGPセッション | 状態とネゴシエート済みアドレスファミリー | 目的のプレフィックスが受け入れられたこと |
| BGP RIB | 候補経路、属性、有効性、ベストパスの表示 | 選択された経路がフォワーディングプレーンに反映されたこと |
| Zebraのルーティングテーブル | 選択された経路とインストール状態 | パケットが意図したインターフェースから実際に送出されたこと |
| LinuxのFIB検索 | 宛先への経路、送出インターフェース、ネクストホップ | 戻り経路があること、またはパケットフィルタリングがないこと |
| パケット観測 | 送信元を指定したプローブとインターフェースキャプチャ | すべてのアプリケーション、パケットサイズ、ECMP経路が機能すること |

報告では両方を「ルーティングテーブル」と呼ばず、「BGPテーブル」と「カーネルのフォワーディングテーブル」を明記してください。
FRRはZebraを介してルーティング判断を渡します。この構成で選択したソフトウェアデータプレーンでは、Linuxがフォワーディングを実行します。

## 3. テスト前にポリシーを説明する

| 仕組み | 運用上の目的 | よくある誤解 |
|---|---|---|
| プレフィックスフィルター | 意図したプレフィックスとプレフィックス長だけを許可または広告する | `/24`を許可すると、より具体的な経路もすべて許可される |
| LOCAL_PREF | AS内部の出口の優先度を表す。値が大きい方が優先される | 外部ASにどの入口を使うか指示する |
| Weight | ルーター1台だけで使う、実装固有の優先度 | BGP属性として他のルーターにも伝わる |
| AS_PATH／プリペンド | ASの通過履歴を示し、ポリシーが許す範囲で経路選択に影響する | LOCAL_PREFが高くてもAS_PATHが短い経路が必ず勝つ |
| MED | 受信側の比較ルールに従って入口の優先度を提案する | 隣接するすべてのASとの間で必ず比較される |
| Community | 受信側のポリシーが解釈できるラベルを運ぶ | 対応するポリシーがなくてもラベル自体が動作を強制する |
| ルートリフレクター | 経路を反射してiBGPセッション数を減らす | 不足しているネクストホップ経路を補う、または必ず中継パケットを運ぶ |

リフレクターのORIGINATOR_IDとCLUSTER_LISTはループ防止に使われます。リフレクターの経路選択によって、クライアントから別候補が見えなくなることもあります。
反射された経路については、クライアント、リフレクター、ネクストホップへの到達性を分けて調べてください。
このワークブックのトポロジーにリフレクターを追加せず、後日、別途準備した演習として[ルートリフレクターのラボ](https://bgplabs.net/ibgp/3-rr/)を利用してください。

このフィルター設計を、設定を適用せずに記述します。上流に広告するのは`192.168.42.0/24`だけです。
完全一致の`/24`はこの経路を許可し、`192.168.42.0/25`と、学習したプロバイダー側プレフィックス`192.168.100.0/24`を拒否する必要があります。
別途明記した契約で許可されない限り、`0.0.0.0/0`も拒否します。
暗黙の拒否、評価順序、フィルターを適用する方向を説明してください。
実際のフィルター演習には[広告プレフィックスのフィルタリング](https://bgplabs.net/policy/3-prefix/)を続けてください。このラボの既存ポリシーが、ここで提案するフィルターを実装しているとは限りません。

## 4. このラボの準備

選択した上流ラボは、**`bgplab/bgplab`の`policy/5-local-preference/topology.yml`**、**リビジョン`5a9fab68658ce69317b147396481714ee3478482`です**。
4台のルーターは、AS65000のc1/c2とAS65100のx1/x2です。
トポロジーにはOSPF、eBGP、iBGP、経路広告が設定されており、学習者は顧客側のポリシーを変更します。
[トポロジーのソース](https://github.com/bgplab/bgplab/blob/5a9fab68658ce69317b147396481714ee3478482/policy/5-local-preference/topology.yml)には、**netlab 2.0.0以降**が必要です。

このワークブックを始める前に、別のVM上で[Ubuntuのインストール前提条件](https://netlab.tools/install/ubuntu/)に従います。

## 5. 準備状況とターミナルの使い分け

**同じラボディレクトリにいるVMシェル**から、次を実行します。

```bash
netlab defaults --project

netlab connect c1 --show version

netlab connect c2 --show bgp ipv4 unicast summary

```

`netlab defaults --project`にはnetlab 2.0.1以降が必要です。2.0.0では、クローンした`defaults.yml`を確認してください。
[接続方法のリファレンス](https://netlab.tools/netlab/connect/)では、単一ノードへの接続と`--show`の両方を説明しています。
このFRR／clab構成で`netlab connect c1`を実行すると**c1のLinuxシェル**が開き、そこから`vtysh`を実行すると**c1のFRR CLI**が開きます。
以下のプロンプトは表示例であり、入力する文字列ではありません。

```text
lab-vm$ netlab connect c1
c1-linux# vtysh
c1# show version
c1# show running-config
c1# exit
c1-linux# exit
```

`ip`、`ping`、シェルコマンドはLinux側で実行し、`c1#`では実行しません。
`configure terminal`でFRRの設定モードに入り、`end`でFRRの運用プロンプトに戻ります。
VMから`netlab connect c1 --show ip route`を実行すると、適切なFRRラッパーが使われます。Linuxシェルに`show`コマンドを直接送らないでください。

準備完了の条件は、iBGP／eBGPセッションが実際に確立していること、意図したOSPFネイバーが成立していること、c2でプロバイダー側の有効な経路候補が2つあること、上限時間を設定したプローブが成功することです。
記録したc1、c2、x1、x2のコンテナIDを1つずつ指定し、`docker inspect --format '{{.Config.Image}} {{.Image}}' CONTAINER`でイメージを確認してください。
ホスト全体のコンテナ一覧を、これらのノードのバージョンを示す証拠として代用しないでください。

## 6. ベースラインを予測し、観測して説明する

指定リビジョンでは、c1の外部ピアは`10.1.0.2`、c2の外部ピアは`10.1.0.6`です。
iBGPのループバックは`10.0.0.1`と`10.0.0.2`、顧客セグメントは`192.168.42.0/24`です。
使う前に、実行中の設定でこれらの値を確認してください。
プローブ先`192.168.100.10`は、シミュレーションされたプロバイダーセグメント上にあるx1のアドレスです。

```bash
netlab connect c2 --show bgp ipv4 unicast 192.168.100.0/24
netlab connect c2 --show ip route 10.0.0.1/32
netlab connect c2 --show ip route 192.168.100.0/24
netlab connect c2 ip route get 192.168.100.10
netlab connect c2 ping -I 192.168.42.2 -c 5 -W 1 192.168.100.10
netlab connect c1 --show bgp ipv4 unicast neighbors 10.1.0.2 advertised-routes
```

両方の候補経路、ネクストホップ、AS_PATH、LOCAL_PREF、ベストパスになった理由、カーネルの経路検索結果を記録してください。
c2が直接接続された上流を選んだのか、c1経由の出口を選んだのかを説明します。
広告出力にある実際の各プレフィックスを、提案したエクスポート許可リストに照らして分類してください。想定外の広告は調査対象であり、提案フィルターが動作した証拠ではありません。
応答がないときに送信側ポリシーのせいにする前に、x1に`192.168.42.0/24`への戻り経路があるか確認します。

## 7. 顧客側の出口優先度を1つ変更する

変更前の状態: c1のAS65000インスタンスには`bgp default local-preference`が**明示的に設定されておらず**、実効値は100であり、調べるプロバイダー経路に対する受信ポリシーの上書きもありません。
c2のベースライン実効値も100です。両方の設定を保持してください。
条件が異なる場合、既存のポリシーを削除せず、適切なベースラインを確立できるまで中止してください。

変更対象は**c1のAS65000 BGPインスタンス**です。元に戻すときは、ここで追加した設定だけを削除します。
c1の**FRR CLI**で次を実行します。

```text
configure terminal
router bgp 65000
 bgp default local-preference 200
end
show bgp ipv4 unicast 192.168.100.0/24
```

このFRRコマンドは[10.6.1のCLI実装](https://github.com/FRRouting/frr/blob/frr-10.6.1/bgpd/bgp_vty.c)で確認されています。この実装では、当該インスタンスで受信経路の再処理も行います。
共有環境で使う上流のワイルドカード付きclearコマンドを、そのままコピーしてはいけません。
6節の確認をc2で再実行します。c1経由の有効な経路はLOCAL_PREF 200となり、値100の経路より優先され、その後FIBとパケット経路にも反映される想定です。
属性が変化しない場合は、受信ポリシー、ネクストホップの有効性、実際の実行時バージョンを確認してください。設定行があるだけではPASSになりません。
このワークブックで変更するのはc1だけです。そのため、上流バリデーターが別途期待するc2=50は、ここでの合格基準ではありません。

## 8. 1つのピア障害を測定する

優先度の実験は有効なままにします。変更前の状態として、**c1のネイバー`10.1.0.2`が確立済みで**、`shutdown`設定がないことを確認してください。
元に戻すコマンドは、同じBGPインスタンスで実行する`no neighbor 10.1.0.2 shutdown`です。
これは管理操作によるピア障害であり、ケーブル切断、無通知のパケット損失、BFDの実験ではありません。

時刻付きプローブには、VM上でc2の**記録済みコンテナのネットワーク名前空間**内にあるiputilsを使います。
ラボのインベントリ／プロバイダーマッピングから名前を調べ、`ip netns list`で存在を確かめてください。曖昧なワイルドカードで選んではいけません。
2つ目のVMターミナルで使う前に、プレースホルダーを置き換えます。

```bash
routing_c2_ns='REPLACE_WITH_THIS_LABS_C2_NAMESPACE'
sudo ip netns exec "$routing_c2_ns" ip -br address
sudo ip netns exec "$routing_c2_ns" ping -D -O -n -I 192.168.42.2 -i 0.2 -c 150 -w 40 -W 1 192.168.100.10
```

表示されたアドレスがc2のものと一致することを確認してください。障害を発生させる前に、複数回のプローブ応答が成功する状態にします。
[iputilsの`-O`オプション](https://github.com/iputils/iputils/blob/master/doc/ping.xml)は、応答待ちのパケットを表示します。シーケンス番号と後続の応答を照合し、応答待ちの表示を恒久的な損失とみなさないでください。
c1のFRR CLIで操作時刻を記録してから、次を適用します。

```text
configure terminal
router bgp 65000
 neighbor 10.1.0.2 shutdown
end
```

上限時間を設定したプローブの実行中に、6節の手順でc2のBGPプレフィックスとカーネル経路をサンプリングします。
別のターミナルで、[キャプチャコマンド](https://netlab.tools/netlab/capture/)を使い、**c2のバックアップ用データインターフェースであることを確認してから**キャプチャしてください。指定リビジョンのFRRトポロジーでは`eth2`に対応します。

```bash
timeout 20s netlab capture c2 eth2 -nn -l -c 40 icmp
```

タイムアウトは収集時間に上限を設けます。該当パケットがない場合やアクセスエラーが起きた場合は、キャプチャ成功を意味しません。
c2はx2を選択し、その後、プロバイダー内部セグメント経由でx1に到達する想定です。
`t_action`、最初に観測された経路のwithdraw/change、FIBの変更、最後に失敗したプローブ、回復が継続し始めた時点を区別してください。
たとえば「連続5回の応答」など、回復が継続したとみなす条件を事前に定義し、サンプリング間隔と不確実性も報告します。
プローブと操作記録には同じVMの時計を使います。CLI操作の直前にVMシェルで`date -u +%FT%T.%NZ`を記録し、手動でターミナルを切り替える時間も不確実性に含めてください。
観測された損失がゼロなら、そのサンプリングレートでは停止時間を特定できなかったという意味であり、収束時間がゼロという意味ではありません。
ホールドタイマー、BFD、グレースフルリスタート、障害検出、経路処理、FIB登録はすべて結果に影響します。普遍的に適用できる固定の収束時間を断定しないでください。

## 9. 元に戻し、再試行して提出する

まずピアを戻します。c1のFRR CLIで実行してください。

```text
configure terminal
router bgp 65000
 no neighbor 10.1.0.2 shutdown
end
```

ピアが再確立し、優先経路が戻り、プローブが回復することを確認します。
次に**ポリシー設定**を元に戻します。

```text
configure terminal
router bgp 65000
 no bgp default local-preference
end
```

実行中の設定、両方の候補経路、実効優先度、FIB検索、元の送信元指定プローブを再確認します。
実験設定をスタートアップ設定に保存したり、FRRを再起動したり、広範囲なクリーンアップコマンドを実行したりしないでください。
回復しない場合は、以降の実験を中止し、異なる設定対象を報告してください。証跡をエクスポートした後、所有者はこの使い捨てVMだけに保存したチェックポイントを復元できます。
新しいクローンは証跡として残します。後日廃棄する場合も、所有者のライフサイクル手順に従い、この所有VMだけを対象にしてください。

| 段階 | 必要な肯定的証拠 | 保存すべき否定的／障害の証拠 |
|---|---|---|
| ベースライン | 有効な経路候補が2つあること、ネクストホップが使用可能なこと、プローブ成功 | 戻り経路の欠落、未解決のネクストホップ、セットアップエラー |
| 優先度変更 | c1由来のLOCAL_PREF 200、出口の選択、それに合致するフォワーディング | 属性が変わらない、RIBとFIBが一致しない |
| ピア障害 | 代替経路と、継続的なプローブ回復の観測 | 損失区間、代替経路なし、キャプチャエラー |
| 復元 | 元の設定とフォワーディング動作 | shutdownの残存、ポリシーのずれ、損失の継続 |

各復元の確認に合格した場合に限り、障害測定を3回繰り返します。個々の測定値と観測範囲を報告してください。
平均だけでなく、生のタイムスタンプと出力を保存します。各結果は「測定済み」「計画済み」「ブロック中」のいずれかとして明示してください。
経路がないこと、プローブ記録がないこと、キャプチャ結果が空であることは、肯定的な主張の証拠になりません。
ポリシー、ネクストホップの再帰的解決、「セッションが確立していればサービスも利用可能」という考えへの反例、測定の限界、復元確認について説明できれば、この章を完了です。

# ブロックチェーンの基礎

> **最終更新日**: 2026年10月19日

## このドキュメントで扱う内容

- 一部の台帳が検証を複製する理由と、フルノード、ライトクライアント、パーミッション型モデルの違い
- コンセンサス、Merkle tree、P2P、ファイナリティの役割と、それぞれがインフラ運用にもたらす制約
- ブロックチェーンノードを通常のステートフルサービスとは異なるものとして扱う必要がある理由

## 問題の定義: 信頼できる調停者なしで合意する

ブロックチェーンを理解する出発点は、技術ではなく**制約**です。

たとえば、Kubernetes の etcd クラスターのような一般的な分散システムを考えてみましょう。etcd もノード間でコンセンサスを形成しますが、それには次の前提があります。**参加ノードは同じ組織によって運用され、障害は起こしても嘘はつかない**。ノードの停止やネットワーク分断（クラッシュ障害）には対処しますが、ノードが意図的に異なる値を主張することには対処しません。

ブロックチェーンの前提は異なります。

| 項目 | etcd (Raft) | ブロックチェーン |
|---|---|---|
| **参加者** | 同じ組織の既知のメンバー | 相互に未知で、メンバー構成も変化する主体 |
| **想定する障害** | クラッシュ障害（停止、分断） | **ビザンチン障害**（虚偽、共謀、攻撃） |
| **参加資格** | オペレーターが指定 | パブリックチェーンでは**誰でも参加可能** |
| **取り消し可能か** | オペレーターが介入可能 | プロトコルが許可する範囲に限られる |

多くのパブリックチェーンの**フルノード**は、トランザクションとコンセンサスルールを個別に検証します。ライトクライアント、プルーニング済みノードやスナップショット同期ノード、パーミッション型の設計では、検証やデータ配布のモデルが異なります。パーミッション型であることだけでは、コンセンサスアルゴリズムがビザンチン障害耐性を持つとは限りません。

ここから、ブロックチェーンの基本的な特性が導かれます。

> **ブロックチェーンはスループットを高めるために設計されたシステムではありません**。検証可能性と改ざん耐性を得るために、**意図的に冗長性を受け入れる**システムです。

これを理解すれば、以下の運用上の特性はすべて自然に導かれます。

## ブロックとチェーン: なぜ「チェーン」なのか

複数のトランザクションが**ブロック**を構成し、各ブロックには**直前のブロックのハッシュ**が含まれます。

```text
Block N-1               Block N                 Block N+1
┌──────────────┐       ┌──────────────┐        ┌──────────────┐
│ prev_hash:.. │       │ prev_hash: ──┼────────│ prev_hash: ──┤
│ merkle_root  │   ┌───│ merkle_root  │        │ merkle_root  │
│ transactions │───┘   │ transactions │        │ transactions │
└──────────────┘       └──────────────┘        └──────────────┘
      hash ────────────────┘
```

この仕組みによって、**改ざんが連鎖的に波及します**。ブロック N のトランザクションを変更すると、ブロック N のハッシュが変わり、ブロック N+1 の `prev_hash` が一致しなくなり、それ以降のすべてが無効になります。

PoW チェーンで履歴を書き換えるには、十分に受け入れられた作業量を再構築する必要があります。他のチェーンでは、異なるファイナリティやガバナンスの前提が用いられます。ハッシュリンクによって改ざんを検出できますが、それだけでファイナリティが確立されるわけでも、すべてのブロックチェーンが経済的に不変になるわけでもありません。

### Merkle tree: なぜ必要なのか

ブロック内のトランザクションをどのように要約するかが問題になります。すべてを単純に連結してハッシュすることもできますが、そうすると、**「このトランザクションはこのブロックに含まれているか」を確認するためにブロック全体が必要になります。**

Merkle tree は、トランザクションをペアごとにハッシュしながら上位へまとめる二分木です。

```text
                merkle_root
               /            \
         H(AB)                H(CD)
        /     \              /     \
     H(A)    H(B)         H(C)    H(D)
      |        |            |        |
     tx A     tx B         tx C     tx D
```

ここから得られる特性が**Merkle proof**です。トランザクション C がこのブロックに含まれていることを証明するには、ブロック全体ではなく、**`H(D)` と `H(AB)`だけがあれば十分です**。受信側は `H(C)` → `H(CD)` → `merkle_root` の順に計算し、照合します。

証明のサイズは、トランザクション数 N に対して**log N**に比例して増加します。トランザクションが100万件あるブロックでも、証明に必要なのは約20個のハッシュです。

**実用上の意義**: これによってライトクライアントが実現します。チェーン全体を保持しなくても、特定のトランザクションが含まれていることを検証できます。既存システムにブロックチェーンを統合する際に、「フルノードを実行するか、それともライト検証で十分か」を選ぶための基礎となります。

## コンセンサス: 次のブロックを書き込むのは誰か

コンセンサスアルゴリズムは、**誰がブロックを提案するのか**、そして**競合が起きたとき、どちらの側を正規のチェーンとするのか**という2つのことを決定します。

### 主な方式

| 方式 | 提案者の選出 | 実際にかかるコスト | 例 |
|---|---|---|---|
| **PoW** (Proof of Work) | 計算パズルを最初に解いたノード | **電力とハードウェア** | Bitcoin |
| **PoS** (Proof of Stake) | ステークに比例する確率で選出 | **ステークされた資本 + 違反時のスラッシング** | Ethereum |
| **BFT 系** | 定義されたビザンチン障害のしきい値に基づく投票 | メンバーシップ/バリデーターとクォーラムに関する前提 | Tendermint; Fabric 3.x SmartBFT |
| **CFT パーミッション型順序付け** | 既知のレプリカがクラッシュ障害耐性のあるコンセンサスを使用 | 任意のビザンチン型順序付け動作には耐えられない | Fabric Raft |

### なぜコストが必要なのか

この問いは、コンセンサスを理解する鍵です。**ブロックの提案が無料なら、候補を無制限に作成してネットワークを麻痺させることができます**。匿名参加が可能な環境では、ID だけではこれを防げません（Sybil 攻撃: 1つの主体が多数の ID を作成すること）。

PoW ではコストが**計算**であり、PoS では**資本とスラッシングのリスク**です。BFT 系では、そもそも**参加者を制限する**ことでこの問題を回避します。そのため、コンソーシアムチェーンに適しています。

### ここでパブリックとプライベートに分かれる

| 種類 | 参加条件 | コンセンサス | スループット | 主な用途 |
|---|---|---|---|---|
| **パブリック** (パーミッションレス) | 誰でも参加可能 | PoW/PoS | 低い | パブリック資産、相互運用性 |
| **プライベート/コンソーシアム** (パーミッション型) | 承認されたメンバー | BFT/Raft | 比較的高い | 企業間台帳、規制対象の環境 |

パーミッション型の設計では、既知のメンバーシップと明示的なガバナンスを利用でき、実際の脅威モデルに応じて CFT または BFT を選択できます。金融アプリケーションでは、異なる制御を備えたパーミッション型ネットワークまたはパブリックネットワークを使う場合があります。メンバーシップやコンセンサスの名称だけでは、規制への準拠は確立されません。

## ファイナリティ: 運用上、最も重要な概念

**ファイナリティは、プロトコルのセキュリティ前提のもとでの決済の確定性を表します**。あらゆる攻撃、ガバナンスによる介入、アプリケーションレベルの補償トランザクションに対する無条件の保証ではありません。確率的な確信、経済的ファイナリティ、決定論的なコンセンサス保証を区別してください。

### 確率的ファイナリティと絶対的ファイナリティ

| 種類 | 意味 | 例 |
|---|---|---|
| **確率的** | ブロックが積み重なるほど、取り消される確率が指数関数的に減少する。**ただし、厳密にゼロにはならない** | Bitcoin の PoW |
| **経済的** | 確定したチェックポイントは、ステーク/スラッシングの前提のもとで保護される。取り消しが物理的に不可能というわけではない | Ethereum PoS |
| **即時** | コンセンサスラウンドの終了時に確定する | BFT 系 |

### なぜ運用上の問題なのか

**ノードが返すデータは、まだファイナライズされていない場合があります。**

ブロックチェーンノードに「このトランザクションの結果を教えて」と尋ねると、ノードは**自身が認識している最新のチェーンに基づいて**答えます。その最新ブロックが後から再編成（reorg）されると、答えも変わります。

これによって実際のインシデントでは、次のようなパターンが発生します。

| パターン | 結果 |
|---|---|
| 最新ブロックを基準に入金を確認して処理する | 出金がすでに実行された後で、reorg によって入金が消える |
| ヘルスチェックで「ノードが稼働中」であることだけを確認する | 同期が遅れているノードが**古いデータを返す** |
| ロードバランサーで複数のノードに分散する | ノードごとにチェーンの高さが異なり、同じ問いに対して**異なる答えが返る** |

**そのため、アプリケーションの設計には「N 回の承認後に処理する」というルール（確認深度）が必要であり、その値はチェーンのファイナリティ特性によって異なります**。これはインフラだけでは解決できません。アプリケーションとの取り決めが必要です。

インフラでできること:

- **ヘルスチェックに同期状態を含める**: 「稼働中」ではなく「チェーンの先頭から N ブロック以内」をレディネスの条件として定義する
- **ノード間のチェーンの高さの乖離を監視する**: 乖離が大きくなったら、ロードバランシングの対象から外す
- **reorg の発生をメトリクスとして公開する**: アプリケーションが対応できるようにする

## P2P ネットワーク: 通常のサービスとは何が違うのか

ブロックチェーンノードは、**クライアント/サーバー型ではなく、ピアツーピアで通信します**。これにより、Kubernetes のネットワーキングモデルとの間に摩擦が生じます。

### Gossip プロトコル

新しいブロックやトランザクションが現れると、**隣接するピアに伝播し、さらにそのピアから別のピアへと伝播します**。こうして全員が情報を知るようになります。

特性:

- 中央ブローカーがない → 単一障害点がない
- **同じデータが複数の経路から重複して届く** → 重複データに帯域幅を消費する
- 伝播には時間がかかる → 各ノードが認識する「最新」の状態が異なる（前述のファイナリティの問題につながる）

### Kubernetes 環境で生じる摩擦

| ブロックチェーン P2P が必要とするもの | Kubernetes のデフォルト |
|---|---|
| **安定したピア ID**（ノード ID、アドレス） | Pod の IP は再起動時に変わる |
| **インバウンド接続の受け入れ**（他のピアが自分に接続する） | Pod はデフォルトでは外部から直接到達できない |
| **ピアリストの永続化** | Pod の置き換え時に状態が失われる |
| **固定ポートの広告** | Service のポートマッピング |

そのため、ブロックチェーンノードでは、安定した名前と順序が必要となることから、デフォルトで**StatefulSet + headless Service**を使用します。インバウンド P2P 接続を受け入れるには、追加の公開設計が必要です。[EKS でのブロックチェーンノードの実行](./02-nodes-on-eks.md)では詳細を説明します。

## 状態とストレージ: 再構築が難しい理由

ブロックチェーンノードは、次の2つを保持します。

| データ | 性質 | サイズ |
|---|---|---|
| **ブロック履歴** | 追記専用ログ。過去のデータは不変 | 継続的に増加 |
| **現在の状態** | 残高、コントラクトストレージ。ブロックを再実行して導出できる | 増加するが、履歴より小さい |

**重要な特性は、状態は履歴から再実行できるものの、その再実行には長い時間がかかることです。**

ジェネシスからすべてのブロックを再実行して検証する（フル同期）には、チェーンの経過時間に比例した時間がかかります。そのため、別の同期方法が存在します。

| 方法 | 内容 | トレードオフ |
|---|---|---|
| **フル同期** | ジェネシスからすべてを検証して再実行する | 最も高い確信が得られるが、**最も遅い** |
| **スナップ/高速同期** | 受け入れ済みの状態ルートに照らして証明を検証し、状態を取得する。履歴の検証方法はクライアント/モードに依存する | 高速だが、コンセンサス/チェックポイントと実装の信頼に関する前提が明示される。任意のピアを無条件に信頼するわけではない |
| **チェックポイント同期** | 信頼できるチェックポイントから開始する | 最速だが、チェックポイントの提供元を信頼する |
| **スナップショットからの復元** | オペレーターが保持するデータディレクトリを復元する | 高速だが、スナップショットの新しさと整合性の管理が必要 |

**運用上の結論**: Pod を置き換えるときに、状態を失ってはいけません。状態を失うと、そのノードがサービスを提供できない状態で長時間の同期が必要になります。そのため、ブロックチェーンノードに永続ボリュームは**任意ではなく必須**です。

### 2026年10月の更新: AWS のブロックチェーンスナップショット

[2026年10月14日の発表](https://aws.amazon.com/about-aws/whats-new/2026/10/blockchain-snapshots-node-bootstrapping/)によると、AWS は、同期済みのパブリックブロックチェーンノードのチェーンデータを公開する **Blockchain Snapshots on AWS** を開始しました。スナップショットは Ethereum と Solana に対応し、無料で利用でき、上流プロバイダーと同じ頻度で更新されます。RPC フリートへの容量追加、障害が発生したノードの復旧、破損したデータベースの再同期など、ブートストラップ時間を短縮するための選択肢です。各ネットワークのスナップショットを並列抽出に最適化された形式で再公開します。米国東部 (バージニア北部)、欧州 (アイルランド)、アジアパシフィック (東京) で利用でき、アクセスには、同じリージョン内の EC2 インスタンスと S3 ゲートウェイ VPC エンドポイントが必要です。上の表では「スナップショットからの復元」に該当するため、スナップショットの出所と新しさに関する信頼の前提は同じです。

### アーカイブノード: 別途検討すべき点

「任意の過去の時点における状態」を照会できるノードは、アーカイブノードです。すべての中間状態を保持するため、通常のノードよりも**はるかに多くのストレージ**が必要です。

**ここでは設計上の判断が必要です**: まず、本当にアーカイブ機能が必要かを確認してください。ほとんどのアプリケーションに必要なのは最近の状態だけです。履歴照会が必要な場合は、インデックスサービスやデータウェアハウスで処理する方が費用対効果に優れています。

## 鍵管理: 失えば、それで終わり

ブロックチェーンでは、**ID と権限は秘密鍵です**。この点で既存システムとは決定的な違いがあります。

| 既存システム | ブロックチェーン |
|---|---|
| パスワードを忘れたらリセットする | **鍵を失うと、資産/権限は永久に失われる** |
| 管理者が侵害されたアカウントを凍結できる | 取り消しを行える主体は存在しない（プロトコルが許可する場合を除く） |
| 監査ログを使って事後に追跡できる | 署名されたトランザクションは、いったんファイナライズされると取り消せない |

**そのため、バックアップ戦略の性質も異なります**。チェーンデータはネットワークから再取得できるため、バックアップする価値は高くありません。一方、鍵は**必ずバックアップする必要があり**、その**バックアップ自体が漏えいリスクになります。**

ブロックチェーンインフラにおいて HSM と AWS KMS/CloudHSM が重要なのはそのためです。特にバリデーターには、**署名するために鍵をオンラインにしておく必要がある一方、鍵を漏えいさせてはならない**という相反する要件があります。[金融サービスの視点](./04-financial-services.md)では、この問題を扱います。

## 運用上の特性: ここまでの内容から導かれること

これらの概念から生じる運用上の特性をまとめると、次のようになります。

| ブロックチェーンの設計 | そこから生じる運用上の特性 | Kubernetes での意味 |
|---|---|---|
| フルノードによる検証の複製 | レプリカを増やしても、ベースチェーンの書き込み容量はそれだけでは増えない | RPC/読み取りの総容量と可用性は高められる |
| 状態がローカルに蓄積される | **Pod の置き換えには非常に大きなコストがかかる** | StatefulSet + 永続ボリュームが必須。ノードアフィニティも検討する |
| チェーンの同期が遅れる | **「稼働中」と「サービスを提供できる」は異なる** | レディネスに同期状態を含める |
| ファイナリティは即時ではない | **最新のデータは確定したデータではない** | 確認深度をアプリケーションとの取り決めにする |
| P2P gossip | **インバウンド接続と安定した ID が必要** | Headless Service と追加の公開設計 |
| ハードフォークでは定められた時点でルールが有効になる | 有効化前に互換性のあるバイナリへアップグレードする | Canary とローリングアップグレードで、事前にフリートを準備できる |
| 鍵が権限を担う | **鍵の喪失 = 永久的な喪失** | KMS/HSM を使用し、鍵とデータで別々のバックアップ戦略を用意する |
| 検証の冗長性が設計の要点 | **CPU と IOPS を継続的に消費する** | バースト重視のリソース設定には適さない |

**この表がこのセクションの核心です**。ドキュメント 2 の具体的な推奨事項はすべて、ここから導かれます。

## ハードフォーク: Kubernetes の運用モデルと最も衝突するもの

後方互換性のないプロトコル変更は、**ハードフォーク**です。ネットワーク全体が、指定されたブロック高または時刻に新しいルールへ切り替わり、**切り替わらないノードは別のチェーンに残ります。**

Kubernetes の一般的な考え方と衝突する点は次のとおりです。

| Kubernetes の慣例 | ハードフォーク時 |
|---|---|
| ローリングアップデートによる段階的な移行 | 期限までに必要なすべてのノードが新ルールに対応すれば、有効化前には可能 |
| まず一部を Canary として試す | 有効化前にフォーク対応バイナリをテストし、適切なテストネット/メインネットの段階で動作を比較する |
| 問題があればロールバックする | ロールバックすると、そのノードは古いチェーンに残る |
| アップグレードは運用チームの予定に合わせる | **スケジュールは外部で決まる** |

**実用的な推奨事項**: ハードフォークをデプロイではなく、**期限のある移行**として扱ってください。クライアントのリリースノートを購読し、フォーク日より十分前にアップグレードし、まずテストネットで検証してください。

Ethereum は2025年に Pectra と Fusaka を実施し、より頻繁なアップグレードを進めてきました。メンテナンスの計画には、**年2回という保証されたスケジュールではなく、公開されている有効化日とクライアントのリリースノートを使用してください。**

## まとめ

- 選択したコンセンサスと信頼モデルを比較してください。**etcd/Raft はクラッシュ障害耐性を持ち**、一部のブロックチェーンは BFT を使用し、パーミッション型の Fabric では CFT の Raft または SmartBFT を使用できます。「ブロックチェーン」という呼称だけでは、ビザンチン障害耐性があるとは限りません。
- 多くのフルノード設計では検証を複製します。ライトクライアントとパーミッション型モデルは異なり、RPC/読み取り容量はベースチェーンの書き込みとは別に拡張できます。
- `prev_hash` のチェーンは改ざんを連鎖的に波及させ、**Merkle tree** は log N サイズの包含証明を可能にします（ライトクライアントの基礎）。
- **Sybil 攻撃を防ぐために**コンセンサスにはコストが必要です。参加者を制限する（コンソーシアム）ことでその必要がなくなり、分散性を犠牲にして、より高いスループットとファイナリティを持つ BFT を利用できます。
- **運用上、最も重要な概念はファイナリティです**。最新のデータは確定したデータではないため、同期状態をレディネスに含め、確認深度をアプリケーションとの取り決めにしてください。
- 状態は再実行できますが、**再実行には長い時間がかかる**ため、永続ボリュームは必須です。
- ハードフォークには外部との調整によって決まる有効化時点があります。互換性のあるクライアントを事前に準備し、有効化後のロールバックは別途評価してください。

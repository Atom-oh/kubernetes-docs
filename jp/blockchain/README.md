# ブロックチェーンの概要

> **最終更新日**: 2026年9月12日

## このセクションの内容

- **インフラストラクチャエンジニアの視点**から見たブロックチェーンのワークロードと、その運用特性が一般的なステートフルサービスと異なる理由
- Kubernetes (EKS) 上でブロックチェーンノードを実行する際に実際に直面する課題: ストレージ、P2P ネットワーキング、同期、アップグレード
- マネージド型 (Amazon Managed Blockchain) とセルフ運用の境界、および金融サービスにおける選択の変化

## このリポジトリでこのセクションを扱う理由

このリポジトリは Kubernetes と EKS のトレーニング教材です。ブロックチェーンを扱うのは、**ブロックチェーンノードが Kubernetes の運用担当者にとって特殊なワークロードだからです。**

Kubernetes のワークロードは大きく 2 種類あります。自由に停止・再起動できるステートレスなもの、またはマネージドサービス (RDS、ElastiCache) に移行できるステートフルなものです。ブロックチェーンノードは**そのどちらでもありません。**

| よくある想定 | ブロックチェーンノードの場合 |
|---|---|
| 「Pod はいつでも入れ替えられる」 | 数百 GB から数 TB に及ぶローカル状態を再構築するのに **何日も**かかることがあります |
| 「スケールアウトすればスループットが増える」 | レプリカによって RPC 読み取り容量と可用性は向上しますが、基盤となるチェーンの書き込み/コンセンサス容量が自動的に増えるわけではありません |
| 「ヘルスチェックに成功すればサービスを提供できる」 | 同期が遅れているノードはヘルスチェックに合格しても、**誤ったデータを返す**場合があります |
| 「ローリングアップデートでダウンタイムなしにデプロイできる」 | フォーク互換のリリースは有効化前にカナリア/段階的ロールアウトできますが、プロトコルの期限とフォーク後のロールバック互換性は別の制約です |
| 「バックアップからデータを復元する」 | 状態はチェーンから再生できますが、**キーを失えば取り返しがつきません** |

こうした違いが、実際の運用上の判断に影響します。それを扱うことが、このセクションの目的です。

## 対象読者と前提条件

- EKS/Kubernetes の運用経験があるインフラストラクチャエンジニアとアーキテクト
- **ブロックチェーンは初めて学ぶ方を対象とします**。ドキュメント 1 で基礎概念から説明します
- スマートコントラクト開発、トークン経済、投資判断は対象外です。**インフラストラクチャ運用の観点**から解説します

## 正確性に関する注意

このセクションで扱う不確実性は 2 種類あり、それぞれ異なる方法で対処しています。

**① 頻繁に変わるプロトコル仕様**: 固定のアップグレード周期を前提とせず、発表済みの有効化日を参照してください。ハードウェア、ステーキング、blob の扱いは変わる場合があります。以下の数値は時点を明記した目安であり、常に最新の要件を保証するものではありません。

**② 一次資料ではない数値**: ノードのハードウェア要件などの値は、公式仕様ではなくコミュニティやベンダーによる推定であることがよくあります。そのような値には出典の性質を記し、範囲で示します。

公式ドキュメントで確認できない内容は `Needs verification` ブロックに記載します。本番環境の設計に進む**前に、プロトコルの公式ドキュメントとクライアントのリリースノートで最新の値を直接確認してください。**

01총평

1.1 요약

  1. 경계를 독립 판정하는 BND-B, Shared와 Dedicated를 조합하는 EKS-4 / ACC-5 / VPC-3, Layered SCP bundle(SCP-ATT-3)은 AWS 관점에서 모두 성립합니다. 기술적으로 성립하지 않는 선택지는 없으나, 성립 조건이 문서에 적힌 것보다 복잡한 항목이 6개, 전제가 최신 동작과 어긋나는 항목이 4개 있습니다.
  2. 가장 시급하게 재검토할 항목은 Control Tower landing zone 4.0의 OU와 baseline 의존 관계입니다. 4.0에서는 AWS가 Security OU를 더 이상 생성하거나 강제하지 않고, service integration Account가 속한 OU가 Security OU로 지정됩니다. 또 IdentityCenterBaseline은 CentralSecurityRolesBaseline을, 그것은 다시 CentralConfigBaseline을 요구합니다. 이렇게 연관성이 높은 의존 관계는 "Control Tower와 내부 pipeline의 책임 분리"와 "OU-3 중첩이 적은 functional 혼합형"을 동시에 제약하므로, OU 후보를 만들기 전에 확정해야 합니다.
  3. SVPC-1(최소 VPC, Shared VPC Pool)은 CIDR quota가 아니라 participant Account 100개 / Account당 공유 subnet 100개 / NAU 64,000(최대 256,000) / 전파 route 100개(조정 불가) 순서로 먼저 막힙니다. 특히 마지막 항목은 중앙 TGW hub와 결합하는 순간 첫 번째 병목이 됩니다.

2.1 Control Tower landing zone 4.0 - [정정] 4건, [보완] 3건

무신사 문서 전제
"Landing zone 수준의 Config integration은 service integration Account에 중앙 resource를 구성하며, 일반 member Account의 Config recorder 등은 destination OU에 적용한 baseline에 따라 달라집니다."
[확인]
이 부분은 맞습니다. LZ 수준 Config integration은 service integration Account에만 Config recording resource를 배포합니다. member Account에 Config Recorder와 Delivery Channel을 배포하려면 관리 대상 OU별로 Config baseline을 따로 활성화해야 합니다.
[보완 1]
LZ 수준 Config integration은 OU Config baseline의 전제 조건입니다. LZ 수준 설정만으로는 member Account에 배포되지 않지만, 반대로 LZ 수준에서 Config integration을 비활성화하면 OU에서 Config baseline을 활성화할 수도 없습니다. "Config는 내부 pipeline이 소유한다"는 선택지를 택하려면 LZ 수준 integration을 비활성화하는 것이 아니라 integration은 활성화한 채 OU baseline을 선택적으로 적용하는 형태가 되어야 합니다.
[정정 1]
baseline 사이에는 활성화와 비활성화 순서를 묶는 의존 관계가 있습니다. 이 부분이 문서에 빠져 있고, OU 설계와 책임 분리 결정을 직접 제약합니다.

비활성화는 역순으로만 가능합니다. CentralConfigBaseline을 비활성화하려면 CentralSecurityRolesBaseline, IdentityCenterBaseline, BackupAdminBaseline, BackupCentralVaultBaseline을 먼저 모두 비활성화합니다.

영향
문서는 IAM-H1(Identity Center)을 현재 검토 방향으로, Config는 "CNAPP와 비교 후 결정"(SEC-2)으로 두고 있습니다. 그런데 Control Tower의 IdentityCenterBaseline을 쓰려면 CentralConfigBaseline이 반드시 활성화되어 있어야 합니다. SEC-2의 Config 도입 여부 결정이 IAM-H1의 구현 방식을 제약합니다. 두 결정을 독립적으로 다룰 수 없습니다.
[정정 2]
LZ 4.0은 Security OU를 생성하거나 강제하지 않습니다. 3.x와 달리 4.0은 designated Security OU를 만들지 않고, service integration Account들이 위치한 OU가 Security OU로 지정됩니다. 또한 각 service integration에 설정된 모든 Account가 동일한 부모 OU 아래에 있어야 합니다.
영향
OU-3에서 Security를 "쉽게 변하지 않는 기능 OU"로 제시했는데, 4.0에서 이 OU는 무신사가 자유롭게 설계하는 OU가 아니라 Control Tower가 특별하게 다루는 OU가 됩니다. 다음 세 가지가 따라옵니다.
  • Security OU에는 AWSControlTowerBaseline과 AWS Config Baseline을 적용할 수 없습니다(상태가 Not Applicable로 표시되며 정상입니다). BackupBaseline은 적용 가능합니다.
  • Security OU 안에 service integration Account가 아닌 일반 Account를 두면 baseline resource를 받지 못합니다. 통제하려면 managed OU로 옮겨야 합니다.
  • Control Tower는 Logging Account와 SecurityRoles Account용 Identity Center permission set만 프로비저닝합니다. Config Account와 Backup Account용 permission set은 만들어 주지 않으므로 직접 생성해야 합니다.
[정정 3]
일반 member Account를 Security OU로 옮기면 해당 OU의 enabled control이 drift 상태가 됩니다. auto-enrollment 설정과 무관합니다. 문서의 Transitional OU 설계에서, 검사 대기 Account를 절대 Security OU 계열에 두면 안 됩니다. 이 조건은 문서에 없습니다.
[정정 4]
CentralizedLogging 비활성화 동작이 4.0에서 바뀌었습니다. 3.3 이하는 Organization CloudTrail만 비활성화하고 배포된 resource를 유지했으나, 4.0은 logging Account의 Config Recorder, Delivery Channel, CloudTrail 관련 stack instance를 삭제합니다. 이후 Control Tower는 logging Account를 관리하지 않습니다. 되돌리기가 아니라 해체이므로, LZ-MIG-2 단계적 전환 중 "일단 비활성화하고 나중에 다시 활성화한다"를 rollback 수단으로 쓸 수 없습니다.
[보완 2]
3.3 이하에서 4.0으로 업그레이드할 때는 순서 제약이 있습니다. 업그레이드 과정에서 AWS Config와 SecurityRoles integration을 비활성화하지 마세요. 3.3 이하에서는 두 integration이 항상 활성화된 상태였고, 4.0에서 처음으로 선택 옵션이 되었습니다. 업그레이드가 성공한 뒤에 원하는 대로 비활성화하는 순서여야 합니다. 또한 API로 업그레이드하는 경우 AWSControlTowerCloudTrailRole이 기존 inline policy 대신 관리형 정책 AWSControlTowerCloudTrailRolePolicy를 사용하도록 먼저 교체해야 합니다.
[보완 3]
Drift 알림 경로가 바뀌었습니다. AWSControlTowerBaseline이 활성화되지 않은 4.0 환경에서는 SNS topic으로 drift 알림을 보내지 않고, management Account의 EventBridge로 보냅니다. 6.7의 "표준 준수 검증"에서 drift 신호 수집 경로를 SNS 기준으로 설계했다면 고쳐야 합니다.

2.2 Control Tower auto-enrollment - [확인] + [보완] 2건

무신사 문서 전제
"Landing zone 3.1 이상에서 auto-enrollment를 활성화하면 Account를 등록 OU로 이동할 때 해당 OU의 baseline과 control이 자동 적용됩니다. 기존 설정 충돌과 실패 복구를 자동으로 해결하는 기능은 아닙니다."
[확인]
맞습니다. 3.1 이상에서 쓸 수 있고, RemediationType을 Inheritance Drift로 설정해 활성화합니다. inheritance drift를 만들지 않고 Account를 옮기는 기능입니다.
[보완 4]
등록 해제 시 baseline resource가 자동 삭제됩니다. Account를 등록되지 않은 OU나 조직 root로 옮기면 Control Tower가 배포한 baseline resource와 control을 모두 자동으로 제거합니다. 문서의 Suspended OU를 "폐기 예정 Account의 일반 변경을 막는 위치"로 쓰려는 설계에서, 이 OU를 Control Tower에 등록하지 않으면 감사 증거 수집에 필요한 baseline까지 사라집니다. Suspended는 등록된 OU로 두고 Deny 중심 SCP로 변경을 막는 형태가 안전합니다.
[보완 5]
enrollment는 eventual consistency 방식이라 이동 Account 수에 따라 수 분에서 수 시간까지 걸립니다. 또한 auto-enrollment는 Service Catalog provisioned product를 생성, 수정, 종료하지 않습니다. Account Factory로 만든 Account를 unenroll하면 provisioned product가 management Account에 고아 상태로 남습니다. "Account 이동 → 자동 enrollment → 내부 workload bootstrap" 파이프라인에서 bootstrap 시작 조건을 이동 이벤트가 아니라 baseline 적용 완료 확인으로 두고, 고아 provisioned product 정리를 전환 체크리스트에 포함하시기 바랍니다.

RCP는 실사용 4개뿐이고 문서 크기도 5,120자로 SCP의 절반입니다. 문서는 RCP를 "지원 resource의 resource policy가 허용할 수 있는 최대 범위"로 정확히 이해했지만, RCP는 SCP와 같은 수준의 계층적 bundle 전략을 쓸 여유가 없습니다. RCP는 조직 전체에 적용하는 소수의 절대 규칙(예: 외부 principal의 S3, KMS 접근 차단, confused deputy 방어)에 한정하고, 세분화는 SCP와 resource policy에 위임합니다.
[보완 9]
Organizations에 Security Hub policy 유형이 추가되었습니다. 문서의 SEC-1 / SEC-6에서 조직 예방 control과 finding workflow를 다루는데, Security Hub 설정을 조직 정책으로 중앙 배포하는 수단이 목록에 없습니다. SCP, RCP, declarative policy, Tag Policy와 함께 검토 대상에 넣는 것이 좋습니다.

2.6 Regional NAT Gateway - [확인] + [보완] 3건

무신사 전제(하나의 ID로 자동 확장과 축소, public subnet 불필요, private NAT 미지원, 최대 60분 확장 지연, 기존 Zonal NAT 전환 시 connection reset과 IP 변경)는 [확인] 모두 사실에 부합합니다. 특히 60분 지연과 그 동안의 cross-AZ 처리, 전환 시 연결 리셋을 정확히 파악하고 있습니다.

[보완 14]
Regional NAT Gateway는 constrained AZ에서 지원되지 않습니다. AZ-2 / AZ-3 결정과 결합하는 조건이며 문서에 없습니다. 서울 리전에서 사용 예정 AZ가 constrained AZ에 해당하지 않는지 먼저 확인해야 합니다.
[보완 15]
IP와 연결 한도가 Zonal보다 유리합니다. Regional은 AZ당 IP 32개(Zonal은 8개)를 지원하고, IP 1개당 동일 목적지(destination IP + port + protocol 조합)로 맺을 수 있는 동시 연결도 55,000개 늘어납니다. EGRESS-2 / EGRESS-3 비교에서 SaaS와 외부 API 같은 소수 목적지로 대량 연결이 몰리는 e-commerce 패턴(PG, 배송사, 재고 연동)에서는 이 차이가 port exhaustion을 막는 데 직접 효과를 냅니다. 비용만이 아니라 이 항목도 비교표에 넣으시는 것을 권고드립니다.
[보완 16]
Automatic mode와 Manual mode가 있습니다. 권장은 Automatic으로, AWS가 IP와 AZ 확장을 관리합니다. Manual은 IP와 AZ별 확장과 축소를 직접 관리합니다. 고정 egress IP를 외부 파트너 allowlist에 등록해야 하는 경로(PG사, 물류 파트너)가 있다면 Manual mode 또는 IPAM public IPv4 allocation policy 연동이 필요합니다. 문서 6.7의 "외부 partner 허용 목록 dependency"와 직접 연결되는 항목입니다. Regional NAT Gateway의 route table에는 TGW를 유효한 route로 넣을 수 있습니다.

2.11 Secrets Manager와 KMS cross-account - [확인] + [보완] 3건 (Q6의 핵심)

무신사 전제(secret resource policy와 호출자 identity policy 모두 필요, cross-account secret에는 customer-managed KMS key 필요, KMS도 owner의 key policy와 caller의 IAM policy 모두 필요)는 [확인] 정확합니다.

여기에 문서가 놓친, DATA-1 vs DATA-2 선택을 실제로 바꿀 수 있는 제약 3건을 추가합니다.

[보완 22]
RDS 자동 백업은 공유할 수 없습니다. cross-account로 넘기려면 automated snapshot을 수동 snapshot으로 복사한 뒤 그 복사본을 공유해야 합니다. AWS Backup이 생성한 리소스에도 동일하게 적용됩니다. 즉 DATA-1(중앙 DB Account)에서 workload Account로 데이터를 넘기거나, DATA-2(workload 소유)에서 중앙 백업 Account로 모으는 경로 모두에 "복사" 단계가 필수이고, 그 단계에 드는 시간과 스토리지 비용, 자동화를 맡을 소유자가 필요합니다.
[보완 23]
암호화된 공유 snapshot은 직접 restore할 수 없습니다. 공유받은 계정은 snapshot을 먼저 자기 계정으로 복사한 뒤 그 복사본에서 restore해야 합니다. 제약이 더 있습니다.
  • AWS 기본 KMS key로 암호화한 snapshot은 공유 자체가 불가능합니다. 개인정보 저장소는 처음부터 customer-managed key를 써야 합니다. 이는 선택이 아니라 cross-account 복구 가능성의 전제 조건입니다.
  • 수동 snapshot은 최대 20개 계정에만 공유 가능합니다.
  • Multi-AZ DB cluster의 snapshot은 공유할 수 없습니다.
  • Oracle / SQL Server의 permanent, persistent option(TDE 등)을 쓰는 인스턴스는 공유 제약이 있습니다.
영향
(Q6 답변의 핵심) 문서는 "Development와 QA의 Production 원본 데이터 접근 차단"을 IAM, KMS key policy, resource policy, VPC endpoint policy로 강제한다고 했습니다. 방향은 정확하지만, 위 제약은 정반대 방향의 문제도 만듭니다. 즉 정당한 복구 경로(Production → 격리된 복구 Account)도 같은 제약을 받습니다. RTO를 계산할 때 "snapshot 복사 시간"을 반드시 포함해야 합니다. TB급 DB에서 이 시간은 무시할 수 없으며, 문서의 어느 곳에도 RTO / RPO 목표가 없습니다.
[보완 24]
AWS Backup cross-account copy의 전제 조건입니다. 6.6과 6.7에서 backup과 restore를 다루지만 다음 조건이 문서에 없습니다.
  • 소스와 대상 Account가 동일 Organization에 속해야 합니다.
  • Management Account에서 cross-account backup 기능을 명시적으로 활성화해야 합니다(UpdateGlobalSettings).
  • 대상 vault는 default vault가 될 수 없습니다. default vault의 키는 공유할 수 없기 때문입니다.
  • 대상 vault에 backup:CopyIntoBackupVault를 허용하는 resource policy가 필요하고, 소스 role에는 backup:CopyFromBackupVault와 backup:CopyIntoBackupVault가 모두 필요합니다.
  • AWS Backup이 완전 관리하는 리소스 유형이 아니면 customer-managed key가 필수입니다(AWS managed key policy는 불변이며 cross-account 공유 불가).
  • AWS Backup은 계정 간 직접 restore를 지원하지 않습니다. "복사 후 복사본에서 restore"의 2단계이며, 대상 Account에 해당 리소스 유형의 service-linked role이 존재해야 합니다(그 서비스를 한 번도 쓰지 않은 Account에는 없습니다).
  • cold tier로 전환된 백업은 cross-account copy를 지원하지 않습니다.
  • 대상 Account가 나중에 Organization을 떠나면 백업을 그대로 보유합니다. organizations:LeaveOrganization을 SCP로 Deny해 두어야 합니다. 이는 개인정보 유출 경로이며 문서의 규제 경계 논의에 없습니다.
[제언]
위 조건들을 종합하면, KEY-3(Hybrid: workload 소유 기본 + 공유 integration만 중앙)은 성립하지만 "개인정보를 담는 저장소의 KMS key는 workload 소유라도 customer-managed key를 강제하고, 복구용 Account를 key policy의 principal에 미리 포함시킨다"는 추가 규칙이 필요합니다. 사고 발생 후 key policy를 바꾸려면 key owner Account에 접근해야 하는데, 그 Account가 침해 대상이면 복구가 막힙니다.

Q1. 경계 산정 - Account / VPC / EKS / Data를 1:1로 맞춰야 하는 조건이 있는가

결론
BND-B(경계별 독립 판정)를 막는 AWS 제약은 없습니다. 다만 세 경계를 부분적으로 결합하도록 강제하는 조건이 4가지 있습니다.

(1) EKS cluster는 여러 VPC에 걸칠 수 없습니다

Amazon EKS는 multi-VPC cluster를 지원하지 않습니다. 따라서 EKS 경계는 VPC 경계의 하위 집합이어야 합니다. 한 cluster의 worker node를 두 VPC에 나눌 수 없습니다.

영향
RUNTIME-VPC-2(A/B 또는 Cell별 VPC)를 선택하면 A/B는 필연적으로 별도 cluster입니다(이미 그렇게 설계됨). 반대로 RUNTIME-VPC-1(같은 Shared VPC)에서는 A/B cluster가 subnet만 다르므로 route, DNS, IPAM, NAU를 공유합니다. 문서가 위험을 제대로 짚었습니다.

(2) EKS Pod Identity role은 cluster와 같은 Account에 있어야 합니다

RUN-2(Shared Cluster Account)에서 workload가 자기 Account의 resource에 접근하려면 반드시 2단 구조(cluster Account의 association role → workload Account의 target role)가 됩니다. Account 경계와 EKS 경계를 분리한 대가입니다.

영향
문서의 IAM-W4(Cross-account target role)가 RUN-2에서 선택이 아니라 필수가 됩니다. "Cross-account resource 접근이 필요한 경우에만"이라는 성립 조건을 "RUN-2 선택 시 모든 workload에 기본 적용"으로 수정하시기 바랍니다.

(3) Shared VPC에서 EKS의 SG와 IAM role은 participant Account에 있어야 합니다

cluster, node, pod용 SG를 참여 Account에서 만들어야 하고, IAM role과 정책도 참여 Account에 두어야 합니다. VPC를 공유하더라도 SG와 IAM 경계는 Account 경계와 일치합니다. 문서의 "network 권한이 완전히 0이 되는 model은 아니다"라는 인식이 정확합니다.

(4) Data 경계는 VPC 배치형 / 비배치형으로 갈립니다

문서가 "S3는 VPC에 배치되는 resource가 아니다"라고 정확히 구분했습니다. 추가로 명확히 할 점: Shared VPC subnet에서 리소스를 만들 수 있는 서비스는 명시적으로 지원되는 목록에 한정됩니다. DATA-4(Shared VPC locality) 판단에 직접 필요하므로 서울 리전 기준으로 확인해야 할 목록을 정리합니다.

Q4. EKS 가용성 - Cluster 분리 기준과 CUJ 이중화가 실질 효과를 내기 위한 AWS 측 조건

결론
A/B EKS Runtime(AVAIL-1)은 "EKS control plane, add-on, upgrade 장애"에 대해서만 유효하며, 그것도 아래 5개 조건을 모두 충족해야 합니다. 조건을 채우지 못하면 비용만 두 배가 되고 가용성은 개선되지 않습니다. 문서의 위험 인식은 정확하나 조건이 구체적이지 않습니다.

(1) EKS managed control plane은 이미 multi-AZ이며 zonal shift 대상이 아닙니다

ARC zonal shift와 zonal autoshift는 Kubernetes data plane에만 작용합니다. control plane은 AWS가 여러 AZ에 걸쳐 운영합니다.

영향
A/B의 가치는 AZ 장애 대비가 아닙니다. 문서가 "A/B cluster는 AZ 분산을 대신하지 않는다"고 명시한 것은 옳습니다. A/B가 실제로 방어하는 것은 무신사가 직접 만드는 장애입니다 - cluster upgrade 실패, add-on(CNI, CoreDNS, CSI driver) 회귀, admission webhook 오류, 잘못된 cluster-wide policy 적용, control plane API throttling. 이 목록을 명문화하고, A/B의 성공 기준을 "이 목록의 장애를 한쪽으로 격리했는가"로 정의하시길 제언합니다. "가용성 향상"이라는 추상 목표로는 POC 판정이 불가능합니다.

(2) CoreDNS가 A/B와 AZ 양쪽에서 가장 흔한 단일 실패 지점입니다

AWS 문서가 명시적으로 강조하는 항목입니다. AZ 장애 시 정상 AZ의 CoreDNS Pod가 늘어난 부하를 흡수해야 하고, A/B에서는 각 cluster가 독립적인 CoreDNS를 가져야 합니다.

[제언]
POC-2의 필수 측정 항목에 다음을 넣으시는 것을 추천드립니다.
  • CoreDNS replicaCount와 topologySpreadConstraints가 AZ에 분산되어 있는지 (CoreDNS EKS add-on은 기본값으로 분산하나 커스텀 설정 시 깨질 수 있음)
  • CoreDNS add-on의 autoscaling 활성화 여부 ({"autoScaling":{"enabled":true}}) 또는 HPA / cluster-proportional-autoscaler 구성
  • 한 AZ 제거 시 CoreDNS의 초당 쿼리 처리량과 지연
  • EC2 instance당 ENI당 Route 53 Resolver로 보낼 수 있는 패킷은 초당 1,024개이며 조정 불가입니다. 고밀도 Pod 노드에서 이 한도가 DNS 실패의 원인이 됩니다. NodeLocal DNS도 검토하는 것을 추천드립니다.

(3) ARC zonal shift는 "사전 확보된 capacity"가 없으면 오히려 장애를 만듭니다

주의 - AWS 문서가 명시적으로 경고하는 부분

zonal shift는 해당 AZ의 모든 in-cluster 트래픽을 제거하므로, 워크로드가 여러 AZ에 충분한 replica로 분산되어 있지 않으면 zonal shift 자체가 가용성 장애를 유발합니다. 사전 프로비저닝된 여유 capacity가 zonal shift 사용의 전제 조건입니다.

zonal shift가 걸리면 자동으로 이런 일이 일어납니다.

  • 해당 AZ의 모든 node가 cordon됨 (신규 Pod 스케줄링 차단)
  • Managed node group의 AZ rebalancing이 중단되고 ASG가 정상 AZ에만 node를 띄우도록 변경됨
  • EndpointSlice controller가 해당 AZ의 Pod endpoint를 EndpointSlice에서 제거
  • node는 종료되지 않고 Pod도 evict되지 않음 (shift 해제 시 즉시 복귀 가능)
  • ALB / NLB를 ARC에 등록해두면 ingress 트래픽도 정상 AZ로만 라우팅

안전장치: 어떤 workload의 endpoint가 전부 장애 AZ에만 있으면 EKS가 fail-safe로 그 AZ에 트래픽을 보냅니다. 즉 AZ 하나에만 배포된 workload는 zonal shift로 보호되지 않습니다.

[제언]
이것이 AZ-1(1-AZ worker)을 예외로도 허용하기 어려운 이유입니다. 문서는 AZ-1을 "Non-production, 재생 가능 batch, 낮은 availability를 명시적으로 수용한 경우"로 제한했는데, 여기에 "ARC zonal autoshift 대상 cluster에는 1-AZ workload를 두지 않는다"를 추가합니다. 같은 cluster에 1-AZ workload가 섞여 있으면 zonal autoshift의 practice run이 그 workload를 중단시킵니다.

(4) ARC zonal shift의 기술 제약

  • EKS Fargate에서는 동작하지 않습니다. (Fargate는 zonal health 이벤트를 인지하면 자체적으로 다른 AZ를 선호하지만 ARC 연동은 아님)
  • Self-managed Karpenter는 1.12 이상에서 지원됩니다.
  • EKS Auto Mode는 추가 설정 없이 연동되며, 장애 AZ의 node provisioning 중단, consolidation과 drift 같은 voluntary disruption 중단까지 자동 처리합니다.
  • Stateful workload는 별도 판단이 필요합니다. 정상 AZ에 새로 뜬 Pod는 장애 AZ에 바인딩된 persistent volume에 attach할 수 없습니다.
  • ARC zonal shift와 autoshift 자체는 추가 비용이 없습니다(프로비저닝한 인스턴스 비용은 계속 발생).
[제언]
문서의 AZ-1 예외 조건에 "zonal storage 전환이 준비돼야 한다"는 서술이 있는데, 이는 AZ-1만의 문제가 아니라 AZ-2와 AZ-3 전부의 문제입니다. PVC를 쓰는 workload는 AZ 수와 무관하게 zonal EBS에 묶입니다. CUJ 중 stateful workload를 따로 식별해 두시기 바랍니다.

(5) 2배, 1.5배 capacity 계산 평가

문서의 "2-AZ는 약 2배, 3-AZ는 약 1.5배" 계산은 산술적으로 맞습니다 (N-1 기준: 2-AZ는 각 AZ가 100%를 처리해야 하므로 총 200%, 3-AZ는 각 50%씩 여유가 필요하므로 총 150%). 이를 "AWS가 요구하는 고정 배수가 아니다"라고 명시한 점도 정확합니다.

[보완]
이 계산이 놓치는 항목 3개입니다.
  • node 추가 시간(scaling lag)을 계산에 포함하지 않았습니다. AWS 문서는 zonal shift 사용 시 "사전 프로비저닝된 여유 capacity"를 강하게 권고합니다. Pod priority + over-provisioning(placeholder Pod) 패턴으로 스케줄링 지연을 제거하는 방법이 표준 해법입니다.
  • "AZ 장애 시 정상 AZ의 capacity 확보 제약"은 무신사가 내부 가설로 표시했고 AWS 공식 입장으로 인용하지 않겠다고 했습니다. 이 신중함이 적절합니다. 다만 AWS 문서 자체가 "zonal impairment 시 healthy AZ에 신규 node가 추가되지 못하는 compute capacity constraint 위험"을 명시하고 있으므로, "빠른 provisioning을 복구 전제로 두지 않는다"는 무신사의 결론은 AWS 문서 방향과 일치합니다. 가설이 아니라 확인된 근거로 격상해도 됩니다.
  • 상호 의존 Pod의 AZ 공존(co-location)이 계산에 없습니다. Application A가 AZ1과 AZ2에 있고 Application B가 AZ3에만 있으면 AZ3 장애가 end-to-end 흐름을 끊습니다. topology spread constraint만으로는 부족하고 pod affinity를 함께 써야 합니다. CUJ의 서비스 그래프를 그려서 각 hop이 모든 AZ에 존재하는지 확인하는 항목을 POC-2에 추가합니다.

(6) cross-AZ 비용 분석 방법 평가

문서의 접근(Flow Logs와 ENI / AZ mapping으로 상위 경로 특정 → same-zone routing, trafficDistribution: PreferClose, topology spread, ALB IP target, NAT와 endpoint의 zonal locality, data locality 적용 → 남는 비용 비교)은 AWS가 권고하는 순서와 일치합니다. "CUR만으로 source / destination AZ pair를 알 수 없다", "AZ 수 자체가 cross-AZ 비율을 결정하지 않는다"는 판단도 타당합니다.

[보완]
두 가지를 추가합니다.
  • trafficDistribution: PreferClose는 Kubernetes 버전에 따라 필드와 동작이 다릅니다. 최신 버전은 PreferSameZone, PreferSameNode 값을 도입했습니다. EKS의 목표 Kubernetes 버전을 먼저 고정하고 해당 버전의 필드명으로 표준을 기술합니다. 버전 업그레이드 시 이 설정이 깨질 수 있습니다.
  • ALB target group의 cross-zone load balancing 비활성화가 cross-AZ 비용 절감 수단으로 문서에 없습니다. ALB는 load balancer 수준에서 cross-zone을 비활성화할 수 없지만 target group 수준에서는 비활성화할 수 있습니다. 단 제약이 많습니다: sticky session 불가, Lambda target 불가, target group 중 하나라도 특정 AZ가 비어 있으면 그 AZ로 들어온 HTTP 요청 전부 503, 빈 subnet을 만들면 ALB가 그 AZ의 IP를 DNS에 노출해 503 발생. AZ별 capacity를 확실히 보장할 수 없다면 활성화 상태로 두는 것이 AWS 권고입니다. A/B와 AZ 조합이 복잡한 무신사 환경에서는 신중히 판단하시길 권고드립니다.

Q5. VPC, Connectivity - 빠진 제약이 있는가

결론
SVPC-1과 SVPC-2 모두 AWS 기능상 성립합니다. CONN-1~5와 INSP-1~4를 traffic 요구별로 조합하는 접근도 타당하며, 중앙 TGW inspection이 무조건 필수인 조건은 AWS 관점에서 없습니다. 다만 SVPC-1의 실질 한계는 문서 예상보다 일찍 오고, CONN-4(Lattice)의 제약은 문서 서술보다 큽니다.

(1) SVPC-1이 먼저 도달하는 한계는 2.4 [정정 5]의 순서대로입니다

재확인: 전파 route 100개(조정 불가) → participant 100개 → Account당 공유 subnet 100개 → NAU 64,000 → subnet / route table 200 → CIDR 5(→50). 문서가 CIDR을 언급한 것은 방향이 맞지만 실제로 가장 늦게 오는 항목입니다. POC-3의 첫 번째 측정 항목을 "전파 prefix 수"로 바꾸시길 제언합니다.

(2) SVPC-1은 TGW 처리량 상한도 공유합니다

2.7 [보완 18] 참조. 동일 VPC에 TGW attachment는 1개만 가능하므로, 최소 VPC 전략은 모든 on-prem과 외부 트래픽을 하나의 attachment(AZ당 100 Gbps, 7.5M PPS)로 집약합니다. SVPC-2는 이를 VPC별로 나눕니다.

(3) SVPC-2에서 문서가 정확히 파악한 점

"VPC, NAT, endpoint와 VPC 간 연결 수는 줄지 않고, 중앙 pipeline의 잘못된 변경이 여러 VPC에 전파될 수 있으며, participant는 자기 ENI와 SG를 계속 소유한다"는 서술은 정확합니다. 추가할 점은 SVPC-2가 "VPC 수는 SVPC-1보다 많지만 blast radius는 작고, TGW 처리량 상한은 분리된다"는 트레이드오프를 가진다는 것입니다. 결국 SVPC-1 vs SVPC-2는 "비용 vs 격리"가 아니라 "중앙 pipeline 변경 위험 vs VPC 공통 장애 위험"의 교환입니다. 어느 쪽도 pipeline 품질에 의존하므로, POC-3에서 "중앙 pipeline의 잘못된 route 변경을 얼마나 빨리 탐지하고 복구하는가"를 두 안 모두에서 측정하시길 권고드립니다.

(4) CONN-4(VPC Lattice)의 제약이 문서보다 큽니다

문서는 "별도 control plane, protocol, quota, 비용을 검증해야 한다"고만 서술했습니다. 실제 제약은 그보다 많고, e-commerce 워크로드에 직접 영향을 줍니다.

Peered NAU 한도는 128,000(최대 512,000)이며, 동일 Region 안의 모든 peered VPC 합계에 적용됩니다. 소수 VPC 간 peering이라도 각 VPC가 크면 이 한도에 걸릴 수 있습니다. Cross-Region peering은 이 합계에 포함되지 않습니다.

(6) 중앙 TGW inspection(INSP-3)이 AWS 관점에서 "필수"인 조건은 없습니다

AWS는 특정 구현을 강제하지 않으며, INSP-4(Hybrid)를 현재 검토 방향으로 둔 것은 타당합니다. 다만 INSP-3을 선택하는 경우의 조건은 문서가 정확히 파악했습니다 (symmetric routing 보장, appliance mode, 양방향 route, TGW-attached 방식에서는 appliance mode가 항상 적용, 두 Account 소유 시 삭제 권한과 제한된 가시성).

[보완]
하나 추가합니다. Regional NAT Gateway의 route table은 TGW를 유효한 route로 지원합니다. EGRESS-2(TGW + Network Firewall)와 NAT-2(Regional NAT)를 조합할 수 있다는 뜻입니다. 문서는 두 결정을 따로 서술했는데, 조합할 수 있다고 명시해 두면 "Regional NAT는 중앙 inspection과 양립하지 않는다"는 오해를 막을 수 있습니다.

(7) 문서에 없는 결정 요소: Shared VPC에서 flow log 소유권

2.4 [보완 10] 참조. INSP-1의 증거 수집이 Shared VPC에서는 owner / participant로 쪼개지며 어느 쪽도 전체를 볼 수 없습니다. owner가 subnet 단위 flow log를 소유하고 participant의 ENI 단위 flow log 생성을 SCP로 제한하는 표준을 정하시길 제언합니다.

Q5 최종 제언
SVPC-1과 SVPC-2를 "둘 중 하나"로 보지 마시고, trust zone별로 다르게 적용하는 3안을 추가로 검토하시기 바랍니다. 일반 workload는 SVPC-1(전파 prefix가 적은 구간), on-prem과 외부 연동이 많은 workload는 SVPC-2(TGW 상한과 route 예산을 분리)로 나누면 두 안의 약점을 서로 보완합니다. 이는 문서의 VPC-3(trust zone 혼합형)을 Shared VPC 확장 방식에까지 적용한 형태입니다.

(2) 개인정보 저장 계층 VPC 분리에서 빠진 통제

문서는 "별도 VPC만으로 달성되지 않으므로 IAM, Security Group, KMS key policy, logging, 승인된 접근 경로를 함께 적용한다"고 정확히 서술했습니다. 여기에 추가할 항목입니다.

  • Shared VPC를 쓰는 경우 participant는 NAT Gateway를 describe조차 할 수 없습니다. 개인정보 저장 계층이 참여 Account 소유이고 VPC가 중앙 소유라면, 그 계층의 egress 경로를 데이터 소유팀이 검증할 수 없습니다. 규제 대응 시 "이 데이터가 어디로 나갈 수 있는가"를 데이터 소유팀이 증명할 수 없다는 뜻입니다. 개인정보 저장 계층은 VPC-1(전용 VPC, workload 소유)로 두는 것이 감사 가능성 측면에서 유리합니다. 문서의 VPC-3 방향과 일치하지만, 근거를 "격리"가 아니라 "소유팀의 egress 경로 증명 가능성"으로 보강하시길 제언합니다.
  • RCP는 개인정보 저장소의 최후 방어선으로 쓰는 것을 권고드립니다. RCP는 4개(실사용)뿐이지만 이 용도에 정확히 맞습니다: 조직 외부 principal의 S3와 KMS 접근 전면 차단, aws:SourceOrgID 조건 강제. 문서는 RCP를 일반 개념으로만 설명하고 개인정보 경계에 배치하지 않았습니다.
  • Backup vault를 destination으로 지정할 수 있는 Account를 SCP로 제한합니다.
주의 - Dev / QA 차단에서 가장 크게 빠진 경로는 backup copy입니다

cross-account backup을 활성화하면 조직의 모든 member Account 사용자가 자기 Account를 destination으로 설정할 수 있습니다. 즉 개인정보 백업이 승인되지 않은 Account로 복사될 수 있습니다. backup:CopyFromBackupVault에 backup:CopyTargets 또는 backup:CopyTargetOrgPaths 조건을 걸어 승인된 vault와 OU로만 복사되게 해야 합니다. IAM, KMS, resource policy, VPC endpoint policy를 다 막아도 backup copy 경로는 별개입니다.

(4) AWS-native security telemetry - 문서가 놓친 사실 2건

SEC-2 / SEC-6 비교표를 만들 때 어느 쪽을 지칭하는지 명확히 하지 않으면 CNAPP와의 중복 판정이 틀어집니다.
  • Security Hub CSPM은 대부분의 control에 AWS Config를 요구합니다. Config를 활성화하지 않으면 대다수 control finding이 생성되지 않습니다. 이는 2.1 [정정 1]의 Control Tower baseline 의존 관계와 합쳐져 "Config를 활성화할 것인가"가 Landing Zone, Identity Center, Security Hub CSPM 세 결정의 공통 전제가 된다는 뜻입니다. 문서는 Config를 SEC-2 안에서만 다루고 있습니다.
  • Security Hub CSPM은 활성화 이전에 생성된 finding을 소급 수집하지 않습니다. 또한 활성화한 리전에서 생성된 finding만 처리하며, CIS 벤치마크를 전체 준수하려면 지원되는 모든 리전에서 활성화해야 합니다. 서울 단일 리전 결정과 함께, 미사용 리전에 대한 control(SCP aws:RequestedRegion Deny)과 탐지(미사용 리전에서의 활동)를 어떻게 볼 것인지를 SEC-1 / SEC-5에 명시하시기를 권고드립니다.

5.1 RTO / RPO 목표 - 가장 큰 누락

문서 전체에 복구 시간 목표가 없습니다. CUJ 정의는 있으나 "장애가 고객과 business에 직접 영향을 준다"는 정성 서술에 머무릅니다. RTO / RPO 없이는 다음을 판정할 수 없습니다.

  • AVAIL-1의 A/B 전환이 충분히 빠른가 (DNS TTL + Cloudflare 전파 + Route 53 전파 + health 판단 지연의 합)
  • DATA-1 / DATA-2 중 어느 쪽이 복구 가능한가 (snapshot 복사 시간이 RTO에 들어가는지)
  • AZ-2와 AZ-3의 차이가 의미 있는가 (N-1 상태에서 목표 SLO 유지 여부)
  • Cell-local data(DATA-5)의 추가 비용이 정당한가
[제언]
CUJ별로 RTO, RPO, 허용 오류율을 정의한 표를 6장 앞에 두는 것을 권합니다. 이 표가 있으면 AVAIL-1, AZ-2 / AZ-3, DATA-1/2/3 결정이 정성 비교에서 정량 판정으로 바뀝니다.

5.2 장애 시 복구 주체(on-call ownership)

경계 판정 기준에 보안, quota, 비용, lifecycle, 장애 영향은 있으나 복구 주체가 없습니다. RUN-2와 DATA-1에서 실제로 문제가 되는 지점입니다.

  • RUN-2: Shared Cluster의 control plane과 add-on 장애는 cluster Account 오너가, workload 장애는 workload 오너가 대응합니다. 그런데 "CNI 문제인지 애플리케이션 문제인지 불분명한 상태"에서 누가 1차 대응하는지 정해 두지 않으면 야간 장애에서 시간을 잃습니다.
  • DATA-1: 중앙 DB Account 오너가 복구하지만 데이터 정합성은 workload 오너만 판단할 수 있습니다.
[제언]
판정표에 "1차 대응 주체"와 "escalation 경로" 열을 추가하고, "복구 주체가 둘 이상인 경계는 분리 후보"라는 규칙을 두시는 것을 권고드립니다.

5.3 Kubernetes 목표 버전과 업그레이드 전략

문서에 Kubernetes 버전이 한 번도 나오지 않습니다. 그런데 다음이 버전에 의존합니다.

  • trafficDistribution 필드와 지원 값 (PreferClose / PreferSameZone / PreferSameNode)
  • Karpenter의 ARC zonal shift 연동 (1.12 이상)
  • EKS Auto Mode 사용 여부와 그에 따른 node lifecycle 소유권
  • add-on 호환성 매트릭스

또한 A/B EKS Runtime의 가장 큰 존재 이유가 upgrade 격리인데, 업그레이드 전략(버전 스큐 허용 폭, A와 B의 버전 차이 유지 여부, EKS extended support 사용 여부)이 문서에 없습니다.

[제언]
A/B의 성립 조건에 "A와 B는 항상 최대 1개 minor version 차이를 유지하고, 업그레이드는 항상 한쪽만 먼저 진행한다" 같은 구체 규칙을 넣는 것을 권고드립니다. 이것이 없으면 A/B는 "cluster 2개"에 그칩니다.

5.4 ALB weighted target group 실패 처리 - [보완]

무신사 문서 서술
"Weighted target group 중 하나가 비어 있거나 unhealthy여도 ALB가 다른 target group으로 자동 failover하지 않으므로 별도의 health 판단과 전환 절차가 필요합니다."
[보완 26]
이 서술은 기본 동작 기준으로는 맞지만, ALB에 이를 완화하는 설정이 있습니다. Target group health 설정으로 DNS failover와 routing failover의 threshold를 정의할 수 있습니다.
주의 - ALB 기본 동작은 failover가 아니라 fail open입니다

healthy target이 충분하지 않으면 ALB는 모든 등록 target(unhealthy 포함)에 트래픽을 보냅니다. 문서는 "failover하지 않는다"고만 서술했는데, 실제로는 unhealthy target에도 보냅니다. A/B 전환 검증 중 B의 target이 unhealthy일 때, ALB는 트래픽을 멈추지 않고 unhealthy target으로 보냅니다.

  • 조정 가능: target_group_health.unhealthy_state_routing.minimum_healthy_targets.count(또는 .percentage)와 target_group_health.dns_failover.minimum_healthy_targets.count(또는 .percentage)를 설정하면 threshold 미달 시 동작을 제어할 수 있습니다. 콘솔에서는 "Unified configuration"으로 양쪽에 동일 임계값을 두는 것이 AWS 권고입니다.
  • 기본값이 "healthy target 1개면 healthy"이므로, 대규모 target group에서 1개만 살아 있어도 ALB는 정상으로 판단합니다. A/B의 weight 단계 상향 절차가 이 기본값에 의존하면 1개 Pod만 뜬 cluster로 트래픽을 보낼 수 있습니다.
[제언]
문서의 ALB 운영 원칙에 다음 규칙을 추가하는 것을 권고드립니다. "A/B target group에는 minimum_healthy_targets.percentage를 CUJ의 N-1 capacity 기준으로 설정하고, weight 상향 게이트를 target health가 아니라 이 threshold 통과 여부로 판정한다."

5.5 Region 미사용에 대한 통제

서울 단일 리전 결정은 명확하지만, 미사용 리전의 통제와 탐지가 6장에 없습니다.

  • 예방: SCP aws:RequestedRegion Deny (global 서비스 예외 목록 필요 - IAM, Organizations, CloudFront, Route 53, WAF global, Support 등)
  • 탐지: Security Hub CSPM은 활성화한 리전의 finding만 처리하고 소급 수집도 하지 않습니다. GuardDuty도 리전별 활성화입니다. 미사용 리전을 아예 비활성화하지 않으면 그 리전에서의 활동이 탐지되지 않습니다.
  • Region 비활성화: Account 수준에서 opt-in 리전을 비활성화하는 것이 가장 강한 통제입니다.
[제언]
SEC-1에 "미사용 리전 통제" 항목을 추가하고, SCP Deny와 리전 비활성화 중 어느 것을 표준으로 할지 결정해야 합니다. MCP endpoint가 미국 동부와 프랑크푸르트에 있다는 사실(2.12)이 이 결정과 충돌할 수 있습니다.

5.6 비용 관측성과 태그 강제 시점

문서는 Tag Policy를 통제 수단으로 언급하고 Workload ID 개념을 정의했으나, 태그가 언제 부여되는지가 없습니다. cross-AZ 비용을 workload pair 단위로 귀속시키려면 ENI 수준까지 태그가 필요하고, 이는 리소스 생성 시점에 강제되어야 합니다.

[제언]
Workload ID를 생성 시점에 강제하는 수단을 정해야 합니다. Tag Policy는 지원 리소스의 준수 검사와 강제까지는 해주지만 모든 리소스를 덮지 않습니다. IaC template 수준 강제 + SCP aws:RequestTag 조건 + Tag Policy 검사의 3중 구조를 제언합니다. Shared VPC에서 owner의 태그가 participant에게 보이지 않는다(2.4 [보완 11])는 점도 비용 귀속 설계에 반영해야 합니다.

  • 본 회신은 2026-08-30 기준 AWS 공식 문서를 근거로 작성했습니다. Quota 기본값과 서비스 동작은 변경될 수 있으므로, 실제 구축 시점에 Service Quotas 콘솔에서 적용된 quota(applied quota)를 다시 확인해야 합니다. 기본값과 계정에 적용된 값은 다를 수 있습니다.
  • 서울 리전(ap-northeast-2)의 개별 기능 지원 여부 중 다음은 문서 링크로 확인했으나 실제 콘솔과 API 확인을 권합니다: Regional NAT Gateway 지원, Route 53 Profiles 지원, Security Hub CSPM과 GuardDuty의 finding type별 coverage, Regional NAT Gateway의 constrained AZ 해당 여부.

  • 조직 책임, 비용 배분, 위험 수용 수준과 최종 선택은 무신사가 결정합니다. 본 회신은 AWS 기술 관점의 성립 여부와 적용 조건만 다룹니다.
